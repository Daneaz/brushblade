## 2 · 选了哪种做法,为什么

brief 给了两条路。**选了第一条:把 `Power()` 拆成「按面计分」,选牌时把面一起记住。**

具体是三个改动点:

1. `Power(graph, id)` → `Power(graph, id, bool attackMode = false)`。面的选取逐字抄
   `BattleEngine.EffectsOf`:`attackMode && def.AttackEffects.Count > 0 ? AttackEffects : Effects`。
   两边必须同口径,否则会出现「按攻面算的分、按护面结算的效果」。
2. 新增 `CardValue(graph, id) = Max(护面分, 攻面分)`,用在**「这张字值不值得留」**那一类
   判定上(合成门槛 `BestCastablePower`、满库弃最弱、`ResolveDropChoice`、`PickBestReward`)。
3. `PlayTurn` 的出字循环里,每张字先按血量规则定面、再用**那一面**的分排序,
   并把面透传给 `NeedsTarget` 与 `Cast`。

**为什么是这条而不是「把『字 + 面』当两个候选」**:

- 现有代码里 `Power(graph, id)` 是**一个 id 一个分**的纯函数,被 7 处调用,其中 5 处
  问的根本不是「这回合出哪面」,而是「这张字值多少、该不该留」(合成/弃牌/战利品/掉字)。
  把候选拆成「字 + 面」的二元组只在出字那一处有意义,却要求另外 5 处也跟着改签名或
  各自决定「拿哪一面比较」——那是把一个局部问题摊到全函数族。按面取值 + 一个 `CardValue`
  只在**出字**那一处引入「面」这个概念,其余 5 处继续问一个 id 一个分。
- 出字循环的形状(`pick` / `pickPower` 单变量擂台)原样保留,只多了一个并行的
  `pickAttackFace`,与它旁边 `pickDef` 的写法同型;候选集合(`Library.Concat(Pool...)`)
  完全没动。二元组做法要把这个循环改成生成候选列表再排序,是这一段唯一的结构性改写。
- 面是**每回合全局同一条规则**决定的(见 §3),不是逐字独立选的 —— 既然如此,
  「一张字两个候选」这个模型本身就是多余的:两个候选里永远只有一个是规则允许的那个。

⚠ **`CardValue` 用 Max 是刻意的,而且它与 §3 的选面规则不冲突**:Max 只回答「留哪张字」
(玩家两面都用得上,一张字的价值就是它更值钱的那一面);「这一回合出哪一面」完全由血量
规则决定,不看分。不这么做的后果与 §2.8 记的坑同型:攻面强、护面薄的双方向字会被永远
当成「库中最弱」优先弃掉、永远合不出来 —— 与「没把它加进卡池表」等价。

## 3 · 选面规则(完整措辞,已原样写进 `PlayTurn` 的注释)

> 水/土 的双方向字有两面:护面(`CharDef.Effects`,治疗/护盾,挂自己)和攻面
> (`CharDef.AttackEffects`,伤害/控制,打敌人)。真人玩家拖给自己出护面、拖给敌人出攻面;
> 此前这个机器人**只有护面这一条路**(从不给 `Cast` 传 `attackMode`)。
>
> 规则整句如下,只此一条,**每次出字前重新判一次**:
>
> **血量还在半血以上 → 双方向字出攻面(打输出);血量掉到半血或以下 → 双方向字出护面
> (治疗/护盾),把血救回半血以上,下一次出字自然又切回攻面。**
>
> 只有一面的字(纯攻击字/纯护盾字/召唤字)不受影响 —— 它们 `AttackEffects` 为空,
> `Power` / `EffectsOf` 都会退回唯一的那一面。

代码就一行:`bool preferAttackFace = battle.PlayerHp * 2 > battle.MaxHp;`

**为什么是这条规则**:brush 明确禁止「两面各打分取分高者」那种写法 —— 权重一动全盘变,
读数没人解释得清,也没人维护得动。半血这条线是真人的打法(血线安全就输出、告急就补),
而且它自带负反馈:补到半血以上就自动切回输出,不会像旧版那样一路奶到 60 回合判死。
放在**每次出字前**而不是每回合开头判一次:一回合内补完血就能立刻接着打,不用等下回合,
也不会读到过期的血量。

另外补了一处一起改才对的地方:`NeedsTarget(pickDef, pickAttackFace)` —— 面必须跟着传,
否则会「想打敌人却按护面判定成不需要选目标」,`targetIndex` 停在 −1,
`ApplyEffects` 里 `ExpandTargets` 返回空表 → **静默打空**(`BattleEngine.cs:1382` 那条
注释预告过的正是这种失败模式:不会崩,只会「点了没反应」)。

## 4 · 顺带加的两列自检(`BotProbe`)

表尾新增 `攻面出字/局` 与 `僵局判死/300` 两列,**它们是仪器的自检,不是平衡指标**:

- 攻面出字恒 0 = 双方向字的攻面又断了。这就是这次的缺口能潜伏这么久的原因 ——
  读数看上去只是「水系偏弱」,没有任何一个数字会喊出「机器人握着半套机制没用」。
- 僵局单独数出来:「60 回合分不出胜负」和「被打死」在卒层数字里长得一模一样,
  不分开数就看不见「只会奶不会打」这种残废打法。

## 6 · 顾虑(交给后续数值任务的人)

1. ⚠ **土系与木土混色的读数下降了**:土系 21.3 → 18.9,木土混色 29.0 → 27.4,
   AOE 探针 13.7 → 13.2。方向是可解释的:这三档的双方向字(`垒`/`圭`/`垚`/`㙓`/`崩`)
   护面是护盾,而护盾会攒**厚**,厚放大召唤物攻击 —— 旧机器人「无脑堆盾」在土系恰好
   撞上了一条真实的强力循环,现在半血以上改打输出,反而少攒了厚。
   **这不是 bug,是策略换了**,而且这一批读数按 spec §10.5 本来就全部作废。
   但它意味着一件事:**修完之后土系不是「读数更准了」,而是「量的是另一种打法」**。
   如果后续要让机器人贴近「会玩的土系玩家」,那条打法多半是「先堆够厚再打」,
   而那需要一条会读厚层数的规则 —— 那是新的设计决定,不在本任务授权内,没做。
2. **水系还剩 1 局僵局**(300 局里),没去追。60 回合上限本身是仪器参数,单局残留
   不构成机制缺口。
3. **半血这条线没有调过**,一次都没有。它是第一次写下就定的值,不是为了让某个读数变好
   反推出来的 —— 若后续有人想动它,请连带把「为什么是这个数」写下来,否则就退化成
   brief 禁止的那种打分调参。
4. spec §8 / §8.1 的三组读数现在**确定作废**(§10.5 已预告)。第四组读数本任务
   **没跑也没写**,按 brief 留给后续任务(数值还在动)。
5. 交接文档 §2.8 建议的那条「每个有载体的 `EffectKind` 都能拿到非零分」自检**没做**
   —— `tools/balance` 至今没有测试工程,而在 `Main()` 里塞启动 assert 会污染读数输出。
   本任务范围只到修攻面缺口,提一句备忘。
