## 0 · 一条会误导人的前提,先纠正

计划里原写「P0 之后 `prescompile` 大概率会红,把 `error CS` 清单交给 P1」。**实测是 0 条 error CS,那份清单是空的。**

原因:**C# 的 `switch` 对未覆盖的枚举值不报编译错**,而本项目相关 switch 都带 `default` / discard 兜底,连警告都没有。所以新增 `EffectKind.Charm` / `StatusKind.Charm` / `BattleEventKind.SuppressDowngraded` 之后,Presentation 是**静默走错分支**,不是编译失败。

> **P1 必须主动逐个排查下面的接线点,不能靠编译器兜底。**

## 1 · Presentation 静默缺陷清单(8 条)

### 优先级最高 —— 合并即可见,不等 P2

**1. 护盾战斗结束衰减 50% 对玩家零告知**
`Core/RunEngine.cs:545-546`。这是 P0 唯一 live 且玩家一定会撞上的规则改动,却没有任何事件、提示或说明文案。

**2. 封禁的「护甲归零 / Boss 减半」在 Presentation 零接线**

## 2 · 留给 P2 的口径说明

- **spec 的「三段式」与代码不是一一对应**:spec 把封禁写成「护甲归零 + 被动不触发 + 主动机制哑火」,但代码里 `EnemyAbility` 是**一个桶**(7 种能力全经 `IsAbilitySilenced` 拦),后两段实为同一条判断,没有独立的「被动」开关。三段式是玩家可见文案的分类,不是三套机制 —— 写卡面文案时别据此以为有三个独立开关。
- **召唤物荆棘 `Thorns` 不进 60% 反伤钳位**(`Core/BattleEngine.cs:3560`)。所以「玩家壁 + 召唤物壁(钳到 60)+ 荆棘 50」在打召唤物那条管道上仍可反弹 >100%。这是**照 spec §1.6 实现**的(那节原文只钳 `Reflect` 两级),但引擎旧注释警告的「比挨的还多」并没有被完全消灭。**荆棘要不要一并纳入钳位,需要拍板。**
- **在注释里引用文案要用「」,不要用 ASCII 双引号**。`tools/fonts/subset_fonts.py:32` 的 `_STRING_RE` 对整个 `.cs` 文本跑正则、**不区分代码与注释**,注释里用 `""` 括住中文会被当成玩家可见文案扫进字符集;若括住的字不在子集里,`test_subset_fonts_cover_charset` 就会红,而报错信息完全指不到注释这个真因。P0 已因此红过一次(commit `f4e7708`,字「故」)。

## 3 · 留给 P2 的仿真情报

P0 收尾跑的是「**新规则 + 旧数值**」,用途是隔离变量 —— P2 落地数值后若读数异常,能判断是规则还是数值的问题。

木土混色只比纯土(17.3)高 1.9、比纯木(22.4)低 3.2。可能原因(供 P2 定标参考):厚 5%/层的放大 × 召唤物基础攻偏低 × 只数收归 1 只 × 起手 2+2 张使「先攒后打」的链路窗口不足。

## 4 · 工程习惯(P0 反复踩到的)

1. **测试必须走真实链路**。P0 有三次被打回都是同型:引擎里加了正确的代码,但测试直接给字段赋值、绕开注入链路,抓不到「引擎忘了刷」。写完测试要**自己做变异检查** —— 把被测的那行代码删掉,确认测试真的变红。不变红的测试等于没有测试。
2. **`grep` 证明「调用点完整」时不要依赖变量名**。P0 的 `RefreshSummonAura` 漏了 3 处,就是因为用了 `summon.Hp =` 这种对变量名敏感的模式,而漏掉的那几处局部变量叫 `revived` / `victim`。改从 `\.Hp\s*=`、`\.Alive`、`_summons\[` 多个角度交叉扫。
3. **过期注释必须跟着改**。P0 有两次因此被打回(`EnemyDef.cs` 的「战意是玩家专属」、`EffectDef.cs`/`StatusEffect.cs` 的「主动机制哑火」)。留着与新行为矛盾的注释,下一个人会按旧语义写代码。
