## 0 · 先纠正两条会误导人的引用

1. **「形状算特性技能」这条裁定在 spec 的 §0(第 23 行),不是 §1.5。** §1.5 实际是「双方向字:效果放在哪一面」,与形状毫无关系。运行时文档与代码注释里的错误引用已在 P1 订正;但 **P0/P1 的计划文档(`docs/superpowers/plans/*.md`)里仍留有历史性的「spec §1.5」字样**,那是规划记录,读到时按本条换算。
2. **P0 计划里说「prescompile 会红、把报错清单交给 P1」是错的** —— 那份清单是空的。C# 的 `switch` 对未覆盖的枚举值**不报编译错**,相关 switch 又都带 `default` 兜底,连警告都没有。**编译器不会帮你发现漏接。**

## 1 · P1 织了一张护栏网,P2 要靠它

`Brushblade/Assets/_Project/Tests/EnumRenderCoverageTests.cs` —— 四条护栏,枚举 `EffectKind` / `StatusKind` 并要求它们被渲染:

| 护栏 | 覆盖 | 漏了的表现 |
|---|---|---|
| `EveryEffectKind_IsRenderedInCharInfoOrExempt` | `CharInfo.EffectsText` | 卡面**直接印英文枚举名** |
| `EveryEffectKind_IsRenderedInCardTraitsOrExempt` | `CardTraits.Of` | 特性段塞一条**英文枚举名的 chip** |
| `EveryStatusKind_IsRenderedInStatusTextOrExempt` | `StatusText.Of` | 详情面板里整条**凭空消失** |
| `EveryEnemyDebuff_HasBattleViewChip` | `BattleView.DrawEnemies()` | 敌人格**零视觉提示** |

**P2 新增任何 `EffectKind` / `StatusKind` 时,先跑这四条**;红了就是真实的接线要求,按提示补渲染或加豁免(豁免要写明「为什么玩家不该看到它」)。

⚠ **护栏的判据是源码文本匹配**,有三层收紧:剥注释(`StripComments`)、整词匹配(`ContainsKindRef`,堵掉 `Burn` 是 `BurnNoDecay` 前缀这类)、`MethodBody` 限定范围。它**不能**处理 verbatim(`@"..."`)与 raw string(`"""..."""`),已加守门断言 —— 谁往那几个文件里写这类字符串,护栏会红着提醒先修状态机,而不是静默退化成假绿。

⚠ **护栏只查「存在性」,不查「正确性」。** 护甲 chip 上的**数字**对不对、文案说的机制对不对,护栏一概管不了 —— 那几处只能人工核。

## 2 · P2 必须接的:与字表载体同批落地

P0/P1 已把机制和 UI 都接好,但**载体字还没入表**,所以下面这些现在不可观测。P2 让载体落地时要一并验:

| 机制 | 载体(P2 入表) | 已接好的 UI | 要验什么 |
|---|---|---|---|
| 魅惑 `Charm` | `花`(木绿,新字) | 五处全接(StatusText / BattleView chip / CharInfo / CardTraits / EnemyInfo actionNote) | 卡面、状态详情、敌人格、行动提示四处文案是否都出现 |
| 封禁(`Silence` 扩义) | `灭` / `海` / `澡` / `湮` / `沐` / `淋` | 护甲显示两处 + `SuppressDowngraded` 播报 | 对杂兵甲归零、对 Boss 减半,头行与详情两处数字一致 |
| 终极技 | `溃` / `㵘` / `崩` / `㙓` | — | 攻面/护面归属(spec §1.5) |

⚠ **新字 `花` 入表要走完整管线**:详表条目 → 配方(艹 + 化)→ **字体子集必跑**。新字不在子集里会在真机显示成豆腐块,而离线编译与 Core 单测都发现不了,只有 `pytest tools/fonts/tests/` 会红。

## 3 · P2 要处理的遗留(P1 判定可延期)

1. **`gen_char_doc.py:466`** 召唤被动侧的形状判定缺少 `!= 'Single'` 排除(伤害侧 :472 有)。全表 118 字目前 **0 次**显式写 `shape: "Single"`,故不可观测;改一个 token 的事。
2. **文档与卡面的形状措辞分叉**(范围比最初记的大):
   - 基础标签:Python `SHAPE` 表是「贯穿**:同列前后排**」「横扫**:整排**」「溅射**:相邻**」,C# `ShapeName` 只有「贯穿/横扫/溅射」;
   - 后缀:Python「非主目标 X%」/「N 发」/「N 跳,每跳 ×X%」,C#「(溅X%)」/「(共N发)」/「(共N跳,每跳×X%)」。
   语义一致、字面不同。**两边受众不同**(文档给设计者读表,展开写法正是设计者要的),所以**要么对齐、要么在文档口径说明里写明「本列为设计侧展开写法,玩家文案见 `char.shape.*`」**。这条分叉早于本次两批(`a26556f` 就存在)。
3. **`桂` 的「全场加盾 60」在卡面上不存在**(pre-existing,比上面两条更能被玩家看见):
   `CardTraits.Of` 对召唤字提前 `return SummonTraits(...)`,而 `桂` 的 effect 是 `Summon{summonShield:60}` 且**没有 passive** → `SummonTraits` 里 `if (p == null) return;` 立刻返回 → 「特性 · 技能」段**整段为空**,这张字的唯一机制只字未提。而 `gen_char_doc` 有 `summonShield` 分支,文档三处都印着「全场加盾 60」。
   连带:`CardTraits.cs:363-366` 那段 `if (e.SummonShield > 0)` 在 `Scan` 里,召唤字永远走不到 → 三个 `collection.trait.summon_shield.*` key 对应**不可达代码**。修法 3 行:`SummonTraits` 末尾加 `if (summon.SummonShield > 0) AddTrait(...)`,key 现成。
4. **`PlayerInfo.Sheet` 的护盾**已在 P1 修好(加 `shieldOverride`,与角标共用 `BattleView.ShowCarriedShield` / `CarriedShieldOverride` 判据)。**P2 若再加读 `PlayerShield` 的地方,记得走同一对属性**,别写第三份判据。
5. **`CardFaceCoverageTests`(既有测试)仍用裸 `Contains`**,有与 P1 护栏首轮同型的假绿风险(被注释或别处同名提及满足)。修它可能红出一批真实缺陷,是独立任务的工作量。**单独立项,不要塞进 P2 的数值批。**

## 4 · P1 反复踩到的工程习惯(与 P0 那份互补)

1. **变异检查的「选样」本身就是设计**。P1 的护栏首轮只用新枚举 `Charm` 验变异 —— 而新名字天然不会被别处提及,三次都红,证明不了判据够紧。换成**既有的、名字在文件里别处出现过的** Kind(`Dispel` / `ApBoost` / `Curse`)去验,护栏当场失守三次。**挑一个天然不会误判的样本去验,等于没验。**
2. **「只做了一半的告知」比不告知更糟**。P1 有两个任务因此被打回:一个让角标显示旧值、提示显示新值,同屏两个数打架;一个把有缺陷的既有播报模式复制给新事件,导致 AP 不够时弹出不相干的提示。**判据:这个改动的全部目的是「别让玩家以为是 bug」,那它有没有反而制造新的困惑?**
3. **「没造新机制」不等于「这套既有机制没缺陷」**。复用既有通道前,先确认那条通道本身是对的。
4. **同一条裁定落在两处时,两处都要核**(`CardTraits` 与 `gen_char_doc`、头行护甲与详情弹窗)。单看任一侧都发现不了分叉。
