## 0. 结论速览

1. **被动特性目前在引擎里没有任何执行路径。** `TraitForm.Passive` 只在 `TraitRules.ActiveTraits` 里被过滤掉；生产代码里没有一处调用 `AddHookListener`（只有测试调用）；`RegisterOpening` 也没有生产方调用。
2. **钩子都在结算内部同步发出**：`StatusApplied`、`EnemyHit`、`EnemyKilled`、`PlayerHit`（铁画反噬）都可能在 `ApplyEffects` 执行中途发出。监听器只要同步结算效果，就会重入 `ApplyEffects`，并且已经确认会破坏三个只在单次出字内有效的字段。
3. **两面本体与 spec 差距很大**：55 张字中有 21 张单面字（火 11、金 9、花 1）要拆成两面；绝大多数现有「附加效果」（Quench、Detonate、BurnPotency、DoubleVs、Haste、Unseal、Reflect、ArmorStrike、Immunity、TrueDamage、Chain 治疗……）按 spec 头部的说明都要作废；关键词层数 N 与 spec 的档位表普遍对不上。
4. **最关键的设计取舍是 Lv1 / Lv3 放在哪里。** 推荐 **Lv1 写进本体（chars.json），Lv3 用 `Replaces: Lv1` 表示「按 Kind 覆盖本体里的同类效果」（M0b）**。这样只读查询（NeedsTarget 等）不受影响；trace 只会在本体改动那一步变化，之后的 Lv3–Lv8 数据全部对 trace 不可见。
5. **「把效果追加到出字末尾」只能表达约一半的池词条。** 另一半是「伤害 +X%」「改为横扫」「打 N 击」「+1 回合 / +1 次」这类**修饰本体**的写法，需要新增修饰器通道（M1–M4）。
6. **专属特性共 206 条**（按 §7 配额算：白绿 1、蓝 2、紫 4、金 5、橙红 6），不是 157 条。按本文的 D1 机制集，约 **70%（≈145 条）** 可以直接覆盖；约 **25 条**只需对 D1 机制做小扩展；约 **35 条**需要独有的新机制，清单见 §4。
7. **另外发现一个 Plan A–C 都没覆盖的规则缺口**：spec §3.1「护盾回合结束时清空 / 留存护盾」与引擎现状（护盾整场延续，只有倾覆会清）不一致。浮屠、垒砌、厚德载物、坚壁、反震、碎玉、冰晶的语义都依赖这条规则。❓需要用户裁定。

## 1. 被动运行时现状

### 1.1 TraitForm.Passive 的执行路径：没有

| 位置 | 现状 |
|---|---|
| `TraitRules.ActiveTraits`（`Core/TraitRules.cs:20`） | `Where(t => t.Form == TraitForm.Active && …)`，被动特性在这里被过滤掉 |
| `BE.CastEffectsOf`（1608） | 只追加 `ActiveTraits` 的效果 |
| `AddHookListener`（BE 3721，`internal`） | 生产代码零调用。测试调用点：`BattleHookTests`、`FreezeRulesTests`、`OpeningEffectTests` |
| `ApplyDetachedEffects`（BE 3712） | 生产代码只有构造函数里的开局效果（BE 1045）这一处调用 |
| `RegisterOpening`（BE 3702） | 只有测试调用。没有任何 EffectKind 或特性能登记跨场效果 |
| `TriggerDepth` / `EnterTrigger` / `ExitTrigger`（BE 3694–3719） | 只有 `ApplyDetachedEffects` 会增减 |

被动特性的数据能走通 ConfigLoader（`TraitPipelineRoundTripTests` 断言过 `Form == Passive`），`ValidateTraitTargets`（`Data/ConfigLoader.cs:585`）对被动特性直接 `continue`，不校验目标。

**Plan A 遗留的钩子口径问题，目前仍然存在：**

- `AddPlayerCounter`（3408）：已经挂上的状态做增量时直接改 `Magnitude` 并 return，**不发 StatusApplied**。
- `GainStacks`（1253）：即使层数没有变（余数没攒够一层），也会调用 `ApplyStatus` 并**发出 StatusApplied**。
- 「灼烧满层后再施加」（Plan C 前置项）：`ApplyBurn` 会被钳到 10 层，但仍会调用 `ApplyStatus`，返回 true 并发出事件。
- `HookArgs.Amount` 的口径不统一：EnemyHit 是实际掉血，PlayerHit 是护甲折算后、护盾吸收前的伤害，SummonHit 是 taken，StatusApplied 是施加后的总量。另外没有字段能拿到「护盾吸收量」，而反震、碎玉都需要它。

### 1.3 重入风险点（逐条确认过）

监听器只要在 `OnHook` 回调里同步调用 `ApplyDetachedEffects`，就会重入 `ApplyEffects`。以下几处会被破坏：

1. **`_castCritBonus`**（659）：嵌套调用的 `finally`（3391）会把它清零，外层金系字剩下的效果因此丢掉砺刃暴击率（Plan C 前置项）。
2. **`_critMoraleGrantedThisCast`**（611）：嵌套调用一进门就重置为 false（2697），外层会再兑现一次锋芒战意（违反「每张字一次」）。
3. **`_preCastConditions`**（2736–2737）：嵌套调用会重新取快照。嵌套返回后虽然会恢复外层的快照，但嵌套调用内部读到的是**出字途中**的状态，不符合 R3。建议改成「外层快照优先」。
4. **`moraleRelease`**（2702）：嵌套的独立效果因为 `isComponent: true`，不会触发断金，这一点没问题。但如果外层是断金出字，嵌套调用里的 `DamageSingle` 也会被乘上断金加成吗？不会，`moraleRelease` 是局部变量。这一项安全。
5. **`SettlePlayerHots`**（2118）：它按下标倒序遍历 `_playerStatuses.All`，循环体里调用 `HealAlly`。`HealAlly` → `SettleOverheal` → `DamageEnemy` → EnemyHit / EnemyKilled → 监听器如果往玩家状态袋里加或删状态，**下标就会错位**。这是一个不在 ApplyEffects 里、但同样会出问题的位置。
6. **`DamagePlayerDirect` 中途**：PlayerHit 在格挡反击（4618）之前发出（4595）。如果监听器在这时同步杀死攻击者或改动格挡，后面的反弹和反击就会读到中间状态。虽然有 `Alive` 守卫，但反伤预算 `budget` 的口径会乱。
7. **`ActEnemyTurn` 开头**：TurnStarted（2276）在灼烧结算之前发出。监听器同步造成伤害（怀山「每回合开始受本体 20%」）后，敌人如果死了，`SettleBurnOn` 会直接空转，但后面没有 `CheckWin`、也没有 TurnEnded。
8. **`_events`**：嵌套结算会把事件插进外层事件序列的中间。表现层按序回放没有问题，但 `DamageEnemy` 依赖「EnemyDied 紧跟致死伤害」（4336 的注释）。如果反应在致死伤害和 EnemyDied 之间插入事件，就会打断这个判定。

### 1.4 最小设计建议：反应队列 + 重入守卫 + 构造期监听器

**数据结构**（放在 BE 内部，新开一个 partial 文件，例如 `BattleEngine.Traits.cs`）：

```text
struct Reaction { string SourceCharId; Element Element; int CardLevel;
                  IReadOnlyList<EffectDef> Effects; UnitRef Target; int Depth; string TraitKey; }
Queue<Reaction> _reactions;  bool _resolving;  // _resolving = 正在 ApplyEffects / 排空中
```

**规则：**

1. **监听器只入队，不结算。** 内置的 `TraitRuntime : IBattleHookListener` 是唯一的生产监听器。它根据 hook 找到相关的附着物（M9）、木灵、手牌里带拆合触发的字，把对应特性入队，`Depth = args.Depth + 1`。
2. **重入守卫。** `ApplyEffects` 进门时如果 `_inApplyEffects == true`，直接 `throw InvalidOperationException`（开发期必须响亮地失败）。`ApplyDetachedEffects` 只允许从「排空」路径调用。构造函数里的开局效果也属于排空路径（它不在 ApplyEffects 内部）。
3. **安全点**（排空 `DrainReactions()` 的位置，都在「一个原子动作」的末尾）：
   - `Cast` 末尾：`ApplyEffects` 之后、`RefreshSummonAura`（1497）/ `CheckWin` 之前。出字内触发（M23 的 OnHit / OnCrit / OnKill）都在这里兑现。
   - `ActEnemyTurn`：三个 return 出口统一改成「排空 → Raise TurnEnded → 再排空」，同时补上 DOT 致死时缺的 TurnEnded（Plan A 前置项）。多动作敌人（`ActOneEnemy` 的循环）建议**每次动作之后**排空，让「受击时攻击者 +灼」在它的第二次动作之前生效。
   - `ActSummonTurn` 末尾（含烧死的提前 return）。
   - `BeginPlayerTurn`：`Raise(TurnStarted)` 之后立即排空（「每回合开始获得护盾」应在玩家灼烧结算之前），`StartTurn` 发牌之后再排空一次。❓第二次排空是否需要，取决于有没有「回合开始抽牌后」类特性；目前 spec 里没有。
   - `Compose` / `Dismantle` 末尾（拆字 / 成字特性）。
   - `YieldTurn` 在 Raise TurnEnded 之后。
   - 构造函数：开局效果之后、`AdvanceOnce` 循环之前；`Restore` 的私有构造函数不需要，因为快照时队列必然为空。
4. **排空循环**：FIFO。每条反应按 `Depth` 判定。R4 规定「特性造成的伤害不再触发受击类、死亡类被动」，所以监听器对 `args.Depth > 0` 或 `Source ∈ {BlockCounter, Thorns, Reflect, Trait}` 的受击 / 死亡钩子**不入队**；StatusApplied、TurnStarted 这类钩子允许 Depth 1。另设一个单次排空上限（例如 64 条），超出就抛异常，作为死循环的保险。战斗已分胜负（`Phase` 为 Won / Lost）时清空队列、不再结算。
5. **快照**：所有安全点都在动作末尾，因此 `Capture()` 时队列必然为空。只需加一条 `Debug` 断言，不需要新的快照字段。
6. **RNG**：
   - 监听器遍历顺序固定：附着物按状态袋顺序，木灵按槽位升序，敌人按下标升序。反应按入队顺序结算，结算结果因此是确定的。
   - **建议新开第三条随机流 `_traitRandom`**（`seed ^ TraitSeedSalt`，进 `BattleSnapshot.TraitRandomState`），供特性里的「随机一名敌人 / 随机 3 次」使用。这样，加一条随机特性不会平移掉落流 `_random`；平衡对照时，「这张字的特性」和「这一局抽到了什么」互不干扰。
   - 纪律：没有命中任何特性时，一次随机数都不摇（与 `SpreadEmbers` / `Unseal` 同一条恒等硬线）。
   - 注意：木灵的暴击判定 `RollCritForSummon`（849）走的是 `_random`。群刺、林海这类「木灵各打一次」会消耗 `_random`，要么接受，要么把这条路径也改走 trait 流。❓
7. **构造期监听器**：`TraitRuntime` 在两个构造函数里**都要注册**（公开构造函数 983 与私有构造函数 1058），而且必须在开局效果和开场 `AdvanceOnce` 循环之前。`AddHookListener` 保持 internal，供测试使用。
8. **伴随修复**（放进 D1 第一个任务）：嵌套快照「外层优先」，`_castCritBonus` 与 `_critMoraleGrantedThisCast` 的保存 / 恢复；Plan A 列出的四条钩子口径问题；HookArgs 增加 `Absorbed` 字段（反震、碎玉需要）；`EnemyKilled` / `EnemyHit` 带上**正在出字的 CharId**（迎刃、铁则、割取需要「本字击杀」）。

## 2. 两面本体：现状与 spec §2.1 / §4 对照

映射（`Core/CardFace.cs`）：`CardFace.Attack` ↔ `CharDef.AttackEffects`，`CardFace.Feature` ↔ `CharDef.Effects`。`BE.FaceOf`（1624）：只有 `attackMode && AttackEffects.Count > 0` 时才是 Attack，否则是 Feature。也就是说，**单面字永远只结算 Effects**。另外 `ConfigLoader.ValidateTraitTargets`（585）会拒绝「Attack 面特性挂在没有 AttackEffects 的字上」，所以必须先拆两面，才能写「攻」行。

### 2.1 推荐的落表方式（M0b）

- `chars.json` 的本体 = **Lv1 完整写法**（攻 = 伤害 + 关键词；五行面 = 本系面关键词 + 数值）。
- 特性表的 Lv1 行只放名字（effects 为空，供 UI 显示关键词）。Lv3 行写 `替换 = Lv1`，**引擎语义**是：Lv3 特性中每条效果，替换本体里同一面、同一 Kind 的第一条效果，保持原位置（满足 R3 的「伤害 → Lv1/Lv3 → Lv5/Lv8」）。
- 为什么不把关键词放进 Lv1 特性：那样燃面、铠面的本体就是空的，`EffectsOf`（1600）会回落到 `FallbackEffects`（一发 30 伤害）；`NeedsTarget`、`AttackShapeOf`、`SummonCountOf`、`HasRevive` 这些静态只读查询也全都看不到关键词，Plan A 前置项「只读查询要能看到特性效果」就会变成必做项。
- 为什么不用「Lv3 = 追加一条增量」：火（灼 +1 层，可叠加）、金（战意可叠加；格挡 max 合并）这样可以，但冻结（已冻结不可再冻）、持续治疗（追加一条就是双倍治疗）、破甲 / 护甲（点数叠加）、种都不能这样写。

## 5. 建议的任务切分

### 5.1 trace 恒等的关键事实（`tools/trace/Program.cs`）

- 卡等级：`AllLevelOne`（73 行，220 行传入）→ **只有 Lv1 生效**。Lv3 及以上的所有特性数据对 trace 不可见。
- 机器人只调用 `battle.Cast(pick, target)`（316 行），**attackMode 恒为 false → 只打 Feature 面**；`Power`（421 行）只读 `def.Effects`。
- 读到的字：基准 1 级 = 热；耐久 / 深层 = 焚、炎、灿、燚（卡池 = FireCards 共 11 张火字）；杂食 = 塔、堡、森、淋、冰、淼（卡池 MixedCards = 塔 堡 垒 淋 沐 森 林 冰 淼 海 崩 藻 箭 **葬**）。⚠ 葬是幽灵字（chars.json 里没有），项目记忆里「硬编码字名列表」的老问题又出现了一次。
- 推论：
  - **火的拆两面必然破坏 trace。** 燃面没有伤害，「基准 1 级」只有热一张字，会直接僵局。所以 trace 机器人必须同时改成能选面，并重建基线。
  - 杂食卡池里的字只要改了 **Feature 本体**（塔 / 圭的 Reflect 作废、润面加 HoT、固面加护甲等）就会破坏 trace；只改攻击面不会。
  - 采用 M0b 以后，Lv3–Lv8 的池数据和专属数据**全部不影响 trace**。从 D1 数据任务开始，trace 不再能守住特性数据，需要另配「高等级画像」（balance 的卡 5 级画像，或者给 trace 加一个 `--card-level` 参数，但后者会破坏 ×10 的严格判据，见 `AllLevelOne` 的注释）。
  - trace 与 balance 都还没有接上跨段的 openings 携带（Plan B 前置项），必须不晚于第一条跨场特性数据落地。
