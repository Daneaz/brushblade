## 1 · 设计约束的实证依据

本次设计的每个数值都锚在既有系统的实测读数上,列在此处以便日后校准时知道该重算什么。

### 1.1 角色等级是稀缺资源

经验来源只有爬塔:每层 +10、Boss 层 +50(每 5 层一个 Boss,`EndlessRules.XpFor`)。
升级曲线 `100 + 50×(n−1)`(`MetaRules.CharacterLevel`),累计到 L 级需 `(L−1)(25L+50)` 点经验。
仿真机器人卒层 8.6~15(第 20 章 20.4),故一次爬塔约 **200~300 xp**。

| 等级 | 累计 xp | ≈ 爬塔次数 |
|---|---|---|
| Lv5 | 700 | 3 |
| Lv10 | 2,700 | 11 |
| Lv15 | 5,950 | 24 |
| Lv20 | 10,450 | 42 |
| Lv26 | 17,500 | 70 |
| Lv30 | 23,200 | 93 |

角色属性五条曲线(`MaxHpFor`/`AttackFor`/`DefenseFor`/`DodgeFor`/`SpeedFor`)**同在 Lv26 封顶**。
故门槛可用区间是 **Lv2~Lv26**,一条 4 层枝干的线性步长必须 ≤6 才能在封顶前开完。

### 1.2 墨锭是稀缺资源

产出:`FloorInk = (Boss?5:2) << (depth−1)/10`,加一场爬塔一个宝箱(`ChestRules.InkReward`)。

| 产出源 | 一次爬塔(10~15 层) |
|---|---|
| 层清算 | 26 ~ 52 |
| 宝箱(青瓷/紫檀档) | 60 ~ 120 |
| **合计** | **≈ 100~170** |

墨锭同时被卡牌升级吃(单张白卡升满 23,690)。到 Lv26 玩家累计墨锭约 10,000~15,000,
技能树现实可分到 **5,000~7,000** → 按本文定价点得起 **10~13 / 40 个节点**。

**排他性由墨锭稀缺天然产生,不设节点数上限、不做洗点**(用户 2026-09-07 拍板)。
点错的代价只是「晚一点拿到想要的」,不是永久损失;洗点是硬排他方案的补丁,此处 YAGNI。

### 1.3 三处随机决定了五行树不能加成「某系字的效果」

原始提案是「金脉枝提升所有金系字的伤害」。**该方案已被否决**,依据:

1. **起手强制五系均分**(`MetaRules.StartingLibrary`):前 5 张硬遍历 `StartingElements`,
   金木水火土**各一张**。玩家结构上不可能让起手偏向某系。
2. **战利品不筛元素**(`RunEngine` 的 `RewardRarityWeights`):候选从整个 `RewardPool`
   按**稀有度**权重抽,元素纯随机。
3. **稀有度也随机**:`RarityWeights = {150,350,300,130,50,15,5}`,白绿蓝占 80%。

结果:点满「金脉」→ 起手 6 张里只有 1 张金 → 加成覆盖率 ~1/5 且**完全不受玩家控制**。
这与 19.2.3 给养成系统定的动机(「撞墙 → 攒经验 → 解锁救命技能 → **突破**」,要求效果
确定可预期)直接冲突。

**「改为加成机制而非属性」的变体同样被否决。** 字表实测(118 条 `chars.json`)显示
效果类型与元素几乎一一独占:

| 机制 | 独占元素 |
|---|---|
| `HealSelf`/`HealAll`/`HealOverTime`/`Revive`/`Cleanse`/`Freeze`/`Slow` | **100% 水** |
| `Morale`/`Bleed`/`CritBuff`/`PierceBuff`/`ApBoost` | **100% 金** |
| `Shield`/`ShieldAll`/`Reflect`/`Immunity` | **100% 土** |
| `BurnAll`/`BurnSingle`/`BurnPotency`/`BurnSettleNow`/`Detonate` | **100% 火** |
| `Summon` | 木 11 / 土 3 / 金 2 |

即「金枝加成暴击」与「金枝加成金系字」在真实字表上是同一件事,吃同样的随机。

**结论:五行树必须先治供给,再谈强化。** 枝干的 L1/L2 改造抽卡随机本身,把覆盖率从
彩票拉到可预期;L3/L4 才敢挂强化。见 §3。

## 2 · 树结构总览

### 2.1 三棵树

| 树 | 职能 | 形状 | 节点数 |
|---|---|---|---|
| **五行树** | 单系定向供给 + 该系专属强化 | 5 枝 × 4 层 | 20 |
| **被动树** | 基础数值强化(攻击/生命/暴击/减伤) | 4 枝 × 3 层 | 12 |
| **机制树** | 改变核心玩法交互逻辑 | 4 枝 × 2 层 | 8 |
| | | | **40** |

⚠ 「机制树」= 改机制,「被动树」= 被动数值。用户 2026-09-07 明确对调过一次命名,
勿按字面直觉互换。

### 2.2 等级门槛:步长统一 6,三树错开 2 级

| | L1 | L2 | L3 | L4 |
|---|---|---|---|---|
| **被动树**(纯数值,最好懂) | **Lv2** | Lv8 | Lv14 | — |
| **五行树** | **Lv4** | Lv10 | Lv16 | **Lv22** |
| **机制树**(改规则,最需理解) | **Lv6** | Lv12 | — | — |

效果:**每 2 级就有一批新节点亮起**,Lv22 全树开放完毕(留 4 级余量到 Lv26 属性封顶)。
错开顺序同时定了新手引导次序 —— 先摸纯数值,最后才碰改规则的。

### 2.3 前置规则

**同枝 `Depth−1` 即前置**,隐式推导。不设 `Prereq` 字段:每枝是一条直链、无交叉,
显式依赖图是给任意 DAG 用的抽象,此处是给单次使用造抽象。

一个节点可点的充要条件:

1. 未点(`UnlockedPerks` 不含它)
2. `Depth == 1` 或同枝 `Depth−1` 已点
3. `CharacterLevel(meta.CharacterXp) >= UnlockLevel`
4. `meta.Ink >= InkCost`

### 2.4 定价:按层深翻倍

| | L1 | L2 | L3 | L4 | 每枝 | 全树 |
|---|---|---|---|---|---|---|
| 五行树 ×5 | 300 | 600 | 1,200 | 2,400 | 4,500 | 22,500 |
| 被动树 ×4 | 300 | 600 | 1,200 | — | 2,100 | 8,400 |
| 机制树 ×3(博闻/广纳/慧眼) | 800 | 1,600 | — | — | 2,400 | 7,200 |
| 机制树 · 一气(例外) | 1,500 | 4,000 | — | — | 5,500 | 5,500 |
| | | | | | | **43,600** |

- 机制树单价是同层的 **2.7 倍**:它层数最少(2 层)但每个节点的边际影响最大
  (起手 +1 张 ≈ 白拿一张字),用**价格**而不是层数承载分量。
- **一气单列**沿用现价 1,500/4,000:AP 是全局资源,+2 相当于每回合多打两张牌,
  它的贵是 19.2.3 定下的硬平衡线,不因改版变便宜。

## 3 · 五行树 · 20 节点

五枝结构完全对称:L1/L2 治供给,L3/L4 谈强化。

| 枝 | L1(Lv4/300) | L2(Lv10/600) | L3(Lv16/1200) | L4(Lv22/2400) |
|---|---|---|---|---|
| 金脉 | 起手金格抽取次数 +1 | 战利品候选保底 1 张金 | 金系字效果值 +15% | 战意上限 5 → **7** |
| 木脉 | 同上(木) | 同上(木) | 同上(木) | 木系召唤物速度 **+40** |
| 水脉 | 同上(水) | 同上(水) | 同上(水) | 泉上限 10 → **14** |
| 火脉 | 同上(火) | 同上(火) | 同上(火) | 灼烧每层 20 → **28** |
| 土脉 | 同上(土) | 同上(土) | 同上(土) | 厚上限 10 → **14** |

### 3.1 L1 · 供给:该系起手格「抽取次数 +1」

**不用「稀有度权重上移」这种含糊说法**,采用**抽 N 次取最高档**。只碰
`MetaRules.StartingLibrary` 中该系那一次 `DrawWeighted`,随机流可控可测。

读数(基于 `RarityWeights` 归一化 `{15%,35%,30%,13%,5%,1.5%,0.5%}`):

| 抽取次数 | 期望档位(白=1…红=7) | 紫档以上概率 |
|---|---|---|
| 1(现状) | 2.65 | 18.5% |
| 2 | 3.27 | 36.0% |
| 3 | 3.72 | 48.8% |

紫档以上翻倍,白绿蓝仍占多数 —— 温和,不破坏起手强度曲线。收益自然递减。

**「抽取次数」是全案统一概念**:基础 1 次,每条适用加成 +1 次,取最高稀有度档。
机制树「慧眼」给全局 +1,五行 L1 给单系 +1,两者叠加即 3 次。**叠加规则不需特判**。

⚠ 起手结构本身**一字不改** —— 仍是 6 张、仍五系各一 + 最高档保底一张
(2026-09-06 拍板)。L1 只改「抽到的是白还是紫」,不改格数。用户 2026-09-07
在 D1/D2/D3 三案中选定 D1。

### 3.2 L2 · 供给:战利品候选保底 1 张该系

起手每系只有 1 格,后续续航全靠战后 5 选 2。`RunEngine` 抽 5 张候选时,**先定向占 1 个坑**
(在该系内按 `RarityWeights` 加权抽),剩余 4 张照旧全池抽。

多条 L2 同时生效时,每条各占 1 坑,占满 5 坑为止(点满五系 L2 = 5 张候选五系各一)。

⚠ **定向坑与自由坑之间去重**(2026-09-07 修正,原稿写的「不去重,与起手同口径」是错的)。
战利品与起手在这一点上口径**相反**,而且这是既有规则,不是本设计新定的:

- 起手不去重 —— 格子固定 6 个,重复只是同一张字拿两份,字库本来就允许重复条目。
- 战利品去重 —— 它是「5 张候选里挑 2 张」,候选里出现两张一模一样的字等于只给了 4 个选项。
  既有的 `RollRewardOptions` 建组时就 `if (!group.Contains(id))`,`DrawWeightedReward` 抽中后
  也 `group.RemoveAt(index)`。`MetaRules.DrawWeighted` 的注释把这条差别写得很明白:
  「起手允许重复……**战后 5 选 2 那条路径要的是「不重复」**,所以它在 RunEngine 里另有一份
  会移除候选的实现,两者不可合并。」

所以定向抽走的那张必须从主池同步移除。

### 3.3 L3 · 强化:该系字效果值 +15%

判据是**打出的那张字的元素**(`CharDef.Element`)。

**乘区套在最内层的 `value` 上,先于生克与攻击力缩放:**

```
value' = value × (100 + bonus) / 100      // 整数除
        → WuxingResolver.ResolveEffect
        → ScaleByAttack / ScaleByBaseAttack
```

理由:它语义上等价于「字表里那个数字变大」,所以自动惠及所有 effect kind,无需逐分支接线。
未点时 `bonus = 0`,`value × 100 / 100 == value` **逐字节恒等**,接线那一步零断言改动。

⚠ **只作用于连续量值,不作用于离散层数/回合数。** 判据:+15% 在小数值上会被整数除截断,
读数不可预期(战意 2 层 ×1.15 = 2.3 → 2,毫无变化;7 层 → 8,凭空跳一级)——玩家看到的是
「有时有用有时没用」。

**下面这张表是穷举的:`EffectKind` 的每一个成员都必须在其中一栏。** 原稿只列了 26 个、
漏掉 8 个(2026-09-07 由 T6 的 review 发现,其中 `ApBoost`/`CritBuff`/`PierceBuff` 有现役字
利/锋/锐 在用),漏掉的后果是那类效果**静默不吃加成**,没有任何测试会红。新增 `EffectKind`
时必须同时回到这张表里给它定位。

**吃 L3(连续量值)** —— 17 条:

| 成员 | value 的语义 |
|---|---|
| `DamageSingle` / `DamageAll` | 伤害量 |
| `HealSelf` / `HealAll` / `HealOverTime` | 治疗量 |
| `Shield` / `ShieldAll` | 护盾量 |
| `Bleed` | 每回合流血量 |
| `SpendHeft` / `SpendWellspring` | 每层兑现的伤害量 |
| `Detonate` | 引爆伤害量 |
| `ArmorBreak` | 目标护甲 −N **点** |
| `DefenseBuff` | 自身护甲 +N **点** ← 与 `ArmorBreak` 是同一个量的正负两面,漏掉它是明显的不一致 |
| `Empower` | 本场攻击力 +N(剡 = +50) |
| `CritBuff` | 本场暴击率 +N **个百分点**(锋 = +20) |
| `PierceBuff` | 本场穿透 +N **点**(锐) |
| `Blind` | 目标命中率 −N**%** —— value 是百分点,不是回合数(回合数在 `Turns` 里) |

**不吃 L3(离散层数 / 回合数 / 布尔)** —— 17 条:

| 成员 | 为什么不吃 |
|---|---|
| `Morale` | 层数(上限 5,×1.15 后整数除毫无变化或凭空跳级) |
| `BurnAll` / `BurnSingle` | 灼烧层数 |
| `Freeze` / `Slow` | 冻结/减速的回合数 |
| `Silence` / `Charm` | 持续回合数 |
| `Immunity` / `Reflect` | 免疫/反伤,不是可缩放的输出量 |
| `Cleanse` / `Dispel` / `Revive` | 布尔式动作,没有可缩放的量 |
| `Summon` | 召唤只数(2026-09-05 起恒为 1) |
| `BurnPotency` / `BurnSettleNow` / `BurnNoDecay` | 灼烧的机制开关与每层威力,由火脉 L4 单独管 |
| `ApBoost` | **刻意排除**:AP 是全局硬平衡资源(利 = +1,×1.15 后整数除仍是 1,加了也没用);而且 AP 上限的定价在机制树「一气」那条硬线上,不该被五行 L3 绕过 |

实现时把「吃」的那 17 条列成 `BattleEngine.TakesElementPercent` 的 switch 白名单,
默认分支 `false`。

### 3.4 L4 · 专属:各系天花板 +40%

前四系的机制天然自限定(战意只有金系字给、厚只有土系、泉只有水系、灼烧全在火系),
提高上限不可能外溢。

| 枝 | 常量 | 现值 → 新值 | 读数 |
|---|---|---|---|
| 金脉 | `MoraleMaxStacks` | 5 → **7** | 满层攻击 +50% → **+70%** |
| 土脉 | Heft 上限(每层 +5% 伤害) | 10 → **14** | 满层 +50% → **+70%**;`SpendHeft` 爆发同步变强 |
| 水脉 | Wellspring 上限(每层 +5% 治疗) | 10 → **14** | 满层 +50% → **+70%** |
| 火脉 | `_burnPerStack` | 20 → **28** | 全场灼烧伤害 ×1.4 |
| 木脉 | 召唤物 `Speed` | +40 点 | 缺省 100 → 140,出手频率 +40% |

#### 3.4.1 木脉 L4 的三次修正(保留推理链,防日后重蹈)

木是五系里**唯一机制不独占**的系(`Summon` 木 11 / 土 3 / 金 2),也没有资源条,
所以走不了「天花板 +40%」模板。三个被否的方案:

1. **提前开召唤槽 −5 层** —— 否决:`SlotUnlockDepth` 最深 30 层,过了 30 层该节点**归零**,
   而其余四系 L4 全程生效。不对称。
2. **每层结束存活召唤物回 40% 血** —— 否决:召唤物有前后排,敌人须清完前排才能打后排
   (`SummonPassive.Taunt` 注释:「排位在先,嘲讽在后」),**后排召唤物本来就不掉血**,
   回血对它们是零。收益被站位结构吃掉一半。
3. **全部召唤物速度 +40** —— 否决:`Summon` 不是木系独占,会顺手补贴土系的碉/堡与金系那两个,
   违反专精语义。

**定案:由木系字召出的召唤物速度 +40 点。**

- **不分排位**:出手顺序走 `TurnScheduler` 的蓄能条,与前后排无关,后排远程(灶/烓)吃满。
- **不归零**:全程生效。
- **对攻 0 的召唤物同样有效**:烓/灶 攻击为 0、靠 `OnHitBurn` 输出,攻击加成对它们无用,
  但**出手更频 = 挂灼烧更频**。
- **敢给 40% 的依据**:`MetaRules.SpeedFor` 的注释指出玩家速度斜率刻意压到最小(满级 +25%),
  因为「速度是唯一同时翻倍**输出**与**资源产出**的属性 —— 一次行动 = 3 AP + 1 掉字」。
  **召唤物出手两样都不产**,那条顾虑整个不成立。上方还压着 `TurnScheduler.MaxSpeed = 400`。
- **用加算 +40 点而非 ×1.4**:乘算会让本就快的桤(Speed 150)滚到 210、慢的拉不开;
  加算对缺省 100 的是 +40%、对桤是 +27%,压住滚雪球,与 `MaxSpeed` 的距离也可控。

**判据用 `SummonState.SourceChar` 的元素**(打出的那张牌),不是 `SummonState.Element`
(召唤物自己的元素)。两者绝大多数时候一致,分叉时前者才对:技能树奖励的是「你打木系牌」,
按召唤物自身元素判会出现「打木系字、召出非木召唤物、吃不到木脉加成」的荒谬结果。
这也与 L3 是**同一判据**,五枝口径统一。

实现:在 `BattleEngine.ApplyEffects` 的 `Summon` 分支判一次、把加成写进 `SummonState.Speed`
(与 `Attack` 同为快照语义,跟着存档往返),运行期不再查表,战斗内核调度算式**一行不动**。

顺带:`SummonState.PlayerAttackPercent` 的注释提到「木土/木金混色卡组是一条真流派」
(召唤物吃战意与厚的乘区)。限定木系后,木脉 L4 **不补贴那条混色流派** —— 混色靠金/土的
战意与厚,纯木专精靠蕃息,两条路各有回报,不互相顶替。

## 4 · 被动树 · 12 节点

门槛 Lv2 / Lv8 / Lv14,定价 300 / 600 / 1,200。
数值锚点:不能压过等级曲线(Lv1→26 给 HP +500、ATK +50%、DEF 0→12)。

| 枝 | L1 | L2 | L3 | 累计 | 对照 |
|---|---|---|---|---|---|
| **元** 生命上限 | +100 | +200 | +300 | **+600 HP** | 等级 +500;与现有养元(+600)持平,不动既有平衡锚点 |
| **力** 攻击 | +5% | +10% | +15% | **+30%** | 等级 +50%;Lv26 时 150 → 195 |
| **锋** 暴击率 | +5% | +10% | +15% | **+30 百分点** | 期望伤害 +15%(暴伤 ×1.5),恰为力枝的一半 |
| **御** 护甲 | +2 | +3 | +5 | **+10 点** | 等级 12,技能 10 |

### 4.1 「御」刻意给得少

`MetaRules.DefenseFor` 的注释写明上限 12 的理由:「再高会让等级压过字表,**土系防御字
失去存在意义**」。技能再堆 10 点已到边界。可接受的原因是深层敌人打击量随
`1 + 0.10×(depth−1)` 上涨(20 层约 2.9×),护甲在深层自然贬值 —— 前期强、后期让位给字。

### 4.2 「锋」不另加上限 —— 沿用既有的 100%(2026-09-07 撤销,原提案作废)

~~原提案:暴击率钳 75%,理由是「与 `DodgeFor` 那条 25% 硬线同性质,暴击是乘性输出,
堆到 100% 是退化局」。~~ **该提案在实现 T2 时撤销。**

撤销依据(读了 `BattleEngine.EffectiveCrit` 的实现与注释才发现的):

1. **既有的 100% 上钳不是「没有钳位」,是刻意设计的。**
   `EffectiveCrit = Clamp(PlayerCritChance + CritBuff, 0, 100)`,其注释原话:
   「上钳到 100 而不是放任溢出:100 以上摇不出更多暴击,**但钳住才能让 `RollCrit` 的
   ≥100 短路成为一条必然到达的路径**(锋叠满时靠它省掉摇点)」。改成 75 会让这条
   短路路径永远不可达,`CritStatTests` 里两条守着它的测试
   (`Feng_StackedPastHundred_ClampsToHundred`、`FullCrit_NeverTouchesRandomStream`)
   随之作废。

2. **与闪避的类比不成立。** 闪避 100% 让敌人永远打不到玩家 —— 游戏无法结束,是真退化局,
   那条 25% 硬线因此必要。暴击 100% 只是伤害恒定 ×1.5,战斗照常进行,没有任何东西退化。

3. **代价与收益不对等。** 锋枝满点只给 30 点暴击率,要到 100 需要再叠 6 张「锋」字 ——
   那是玩家拿整个字库换来的 build。养成系统加一道 clamp 去砍掉一条字系统的既有 build,
   是越界。真要压这条 build,该调的是「锋」的 `CritBuff` 值,不是在读取点加钳。

所以本设计**不引入 `MaxCritChance` / `ClampCrit`**,`EffectiveCrit` 一行不动。
锋枝的 30 点直接进 `BattleConfig.PlayerCritChance`,与锋字的 `CritBuff` 照旧相加后钳 100。

### 4.3 「力」是唯一新增算式

```
PlayerAttack = AttackFor(level) × (100 + pct) / 100      // 整数除
```

`pct = 0` 时逐字节恒等。写在 `MetaRules.BuildBattleConfig` 里 ——
按该函数注释的硬要求,**GameRoot 不得手写任何一条字段赋值**。

## 5 · 机制树 · 8 节点

门槛 Lv6 / Lv12。定价 800 / 1,600(一气例外:1,500 / 4,000)。

| 枝 | L1 | L2 | 累计 |
|---|---|---|---|
| **博闻** | 字库容量 +1 | 字库容量 +1 | 容量 7 → **9** |
| **广纳** | 起手 +1 张 | 起手 +1 张 | 起手 6 → **8** |
| **慧眼** | 起手**全部**格抽取次数 +1 | 战利品候选抽取次数 +1 | 见 §3.1 |
| **一气** | AP +1 | AP +1 | 3 → **5**(封顶,硬平衡线) |

### 5.1 必须拆开的既有耦合

现在**「博闻」一条同时加起手张数和字库容量** —— `PerkRules.LibraryBonus` 同时进
`MetaRules.LibraryCapacityFor` 和 `StartingLibrary` 的追加循环(`Meta.cs:530`)。
本设计要求「字库上限」与「起手上限」是两个独立技能,故须拆成两个独立 Bonus:

- `LibraryCapacityBonus` → 只进 `LibraryCapacityFor`
- `StartingCardsBonus` → 只进 `StartingLibrary` 的追加循环

⚠ 拆分后「容量比起手多一格」这条关系(`LibraryCapacitySlack = 1`)的语义要重新确认:
点满广纳(起手 8)而不点博闻(容量 7)时,起手就会超容。**定案:容量下限钳到起手张数**,
即 `LibraryCapacityFor = max(起手实际张数, 6 + 1 + LibraryCapacityBonus)`。
否则开局即溢出,第一回合必弹 `DropChoice`,是静默的坏体验。

## 6 · 数据结构与存档

```csharp
public enum PerkTree { Wuxing, Passive, Mechanic }

public sealed class PerkNodeDef {
    public string     Id          { get; }  // "metal_1" / "power_2" / "insight_1"
    public PerkTree   Tree        { get; }
    public string     Branch      { get; }  // "metal"/"wood"/…/"power"/"vigor"/"edge"/"guard"/…
    public Element?   Element     { get; }  // 五行树的枝干;其余树为 null
    public int        Depth       { get; }  // 1..4

```

`PerkEffect` 扩为:
`MaxHp`、`AttackPercent`、`CritChance`、`Defense`、
`LibraryCapacity`、`StartingCards`、`DrawRolls`、`LootDrawRolls`、`Ap`、

聚合入口两个:`PerkRules.Bonus(meta, effect)` 与 `PerkRules.ElementBonus(meta, effect, element)`。

**存档**:`MetaState.PerkLevels`(`Dictionary<string,int>`)→ **`UnlockedPerks`(`List<string>`)**。
单级节点只需记「点没点」,等级维度整个消失。项目未上线,**不写迁移**:改键名后旧的
`PerkLevels` 键变成未知键,Newtonsoft 直接忽略 —— 技能清零、墨锭/卡等级/图鉴/经验照常读出。
走的是 `EndlessV2` 那次改名的同一条路径(`Meta.cs:37` 注释),**不是**抛 `JsonException`

### 7.1 四个硬编码常量的改法

`MoraleMaxStacks`、Heft 上限、Wellspring 上限三个改成 `BattleConfig` 字段。

⚠ **这三个不进 `BattleSnapshot`**(2026-09-07 修正,原稿写的「并进 BattleSnapshot」是错的,
而且是有害的错):

- 快照存的是**局内会变的状态**(`PlayerHp` / `Ap` / `Turn` / 护盾累计 / `_shieldAccum` …)。
  这三个上限**战斗中永不被写** —— 与 `PlayerDefense` / `PlayerDodge` / `PlayerSpeed` 同类。
- `_burnPerStack` 之所以在快照里,是因为它**真的会在局内被改**:`EffectKind.BurnPotency`
  (炽)执行 `_burnPerStack += value`。它是可变量,不是配置。这条差别正是判据本身。
- **把配置塞进快照会制造一个真 bug**:断点续爬时 `GameRoot` 用
  `MetaRules.BuildBattleConfig(_meta, …)` **重新构造** config,所以玩家在中断期间新点的
  水脉/土脉/金脉 L4 恢复后立刻生效。若这三个上限从快照读回,恢复的是**中断前的旧值** ——
  玩家花墨锭点的技能在这一次登塔里白点了,而且完全静默。

⚠ **厚与泉共用同一个上限常量和同一条代码路径**:`MaxResourceStacks = 10`
(`BattleEngine.cs:388`,注释「厚与泉的层数上限」),两者都经由共享的 `GainStacks(amount, kind, …)`
读它。**只改常量会让水脉 L4 顺手抬高厚的上限、土脉 L4 顺手抬高泉的上限** —— 互相补贴,
破坏专精语义,且这个错误是静默的(没有任何测试会红)。

故 T4 必须先把 `GainStacks` 的上限从常量改成**按 `kind` 取值**,再分别从 `BattleConfig`
的两个独立字段(`HeftCap` / `WellspringCap`)注入。两字段缺省均为 10,此时
`CapFor(kind) == MaxResourceStacks` 对两个 kind 都成立,逐字节恒等。

**恒等性硬线**(CLAUDE.md):缺省值必须等于现值(5 / 10 / 10 / 20),
此时全部既有断言逐字节不变 —— 「接线」与「配值」是两步,接线那步零断言改动。

### 7.2 五行 L3 是全案最危险的一条

`ApplyEffects` 里已经串着 `WuxingResolver`(生克倍率)、`ScaleByAttack`(整数除,早截断)、
灼烧的浮点式(晚截断)。CLAUDE.md 记着「整数除与浮点除并存是刻意的,`(double)` 不能省」,
以及 float 精度配 `Ceiling` 会整级翻车的旧账。

**故 §3.3 已把乘区位置定死在最内层 value 上**,且限定白名单。实现时不得改动
`WuxingResolver` 与 `ScaleByAttack` 的任何一行。

  「删掉任意一条注入行,967 条测试无一变红」那个洞)。

### 9.2 恒等性验收(硬线)

**未点任何节点时,全部既有测试逐字节不变。** 这是 §7.1 / §7.2 能安全接线的唯一凭据。
具体:`bonus = 0` / 上限取缺省值时,`x × 100 / 100 == x`、`max(0, x − 0) == x`。

Tests **纯追加**,不改既有断言。若某一步必须改既有断言,说明该步已越过「接线」进入
「配值」,拆成两步。

⚠ 这条硬线在 T2 实测生效过一次:spec 原 §4.2 要求的 75% 暴击钳会让 `CritStatTests`
两条既有断言变红,实现者按规矩没有自行改断言而是停下来问 —— 复核后发现是**规格错了**
(见 §4.2 的撤销记录),不是实现错了。「既有断言变红」永远先怀疑新规格,别先改断言。

### 9.3 断言 API 限制(CLAUDE.md)

禁用 `Is.AnyOf` / `Is.All.AnyOf`(Unity 自带 NUnit 没有);
`Does.Not.Contain(x)` 只在 x 是 string 时可用,集合判包含一律写
`Assert.That(list.Contains(x), Is.True/False, "…")`;
定位仓库根只能用 `TestContext.CurrentContext.TestDirectory`。

### 9.4 Presentation

无自动化测试,改完必过离线编译(`tools/prescompile`)。按 CLAUDE.md 的两类静默缺陷:
新增玩家可见状态要三处同时接;给共享交互状态赋新含义时要 grep 所有读取点。
