# 承伤与护甲 · 设计规格

> 2026-08-05 · P1~P3 机制落地的**子项目 B**
> 前置:子项目 0(统一状态容器与行动计量器)已合并
> 后续:C 召唤物被动 → A 状态操作 → D 伤害变体 → E 杂项

## 一 · 背景

`技能机制详表.md` 里 43 个字、24 种机制未落地,按引擎子系统分成 5 个子项目。本 spec 做第二个:
**承伤与护甲**,含 `ArmorBreak`(破甲)6 字与 `IgnoreArmor`(穿甲)3 字,共 **9 字**。

选它排在地基之后,是因为「甲」这个概念**不需要新建** —— 引擎里早有承伤系数 `EnemyState.DamageTaken`
(`< 1` 即减伤),实船已有四个敌人在用:墨渍 0.7、山 0.5、江 0.75、钧 0.75。
破甲/穿甲只需操作这个既有量。

### 1.1 一个必须先拆掉的陷阱

`BattleEngine.DamageEnemy` 有条既有规则:

```csharp
// 承伤减免(坚壁/「山」类)遇属性克制失效
if (enemy.DamageTaken != 1f && WuxingResolver.KeMultiplier(attacker, enemy.Element) < 1.5f)
    damage = (int)Math.Floor(damage * enemy.DamageTaken);
```

判断条件是 `DamageTaken != 1f`。破甲要把承伤**升到 1.25**,同样满足 `!= 1f` ——
于是**用克制属性打破了甲的敌人,破甲加成会被这条规则一起吃掉**,破甲白做且静默无提示。

故本 spec 第一件事就是把这个条件拆开(见口径 1)。

## 二 · 范围

### 做

| 块 | 内容 |
|---|---|
| 1 | 承伤结算拆开「减免」与「加成」两条路径 |
| 2 | `StatusKind.ArmorBreak` + `EffectKind.ArmorBreak`(破甲状态与施加手段) |
| 3 | `EffectDef.IgnoreArmor` 标记(穿甲修饰) |
| 4 | 9 个字落地到 `chars.json` |

### 不做

- **不新建「护甲」概念**。复用既有的 `DamageTaken` 承伤系数(口径 2)。
- **不实现 `Dispel`/`Cleanse`**。破甲作为 `Debuff` 进容器后天然可被将来的净化清除,但那是子项目 A。
- **不动玩家侧承伤**。玩家的减伤走 `DamageReduction` 状态,与敌人的 `DamageTaken` 是两套,本轮不打通。

## 三 · 已定口径

| # | 口径 | 理由 |
|---|---|---|
| 1 | 承伤判断从 `!= 1f` 收紧为 `< 1f`:**减免遭克失效,破甲加成始终生效** | 克制破防御、破甲加伤害,两个机制各管各的;否则破甲在克制时静默失效,玩家无从理解 |
| 2 | 「甲」= 既有的 `DamageTaken`,不新建概念 | 引擎已有且实船在用,新建会出现两套防御体系 |
| 3 | 破甲是**有时限的状态**,进 `StatusBag` | 用刚建好的地基;将来 `Cleanse` 能清、UI 能列。连击维持破甲、停手即恢复,鼓励集火 |
| 4 | 破甲**不叠层**,承伤恒为 `1.25`,重复施加只刷新时长 | 「甲破了就是破了,再砍也就那样」。六个字都带破甲,可叠会失控(集齐 = ×2.5) |
| 5 | 破甲持续 **2 回合** | 参照 Freeze 1~2 / Slow 2~3 / Bleed 3。不叠层时持续时间是唯一调节旋钮,2 回合意味着「破完须在两回合内跟上输出」 |
| 6 | 穿甲**只忽略减免,不忽略破甲加成** | 「无视防御」≠「无视一切修正」,与口径 1 同源 |
| 7 | 穿甲是**效果修饰**不是状态 | 它只作用于这一次攻击,挂在敌人身上没有意义 |
| 8 | 溶与破**同值**(`DamageSingle 6` + 破甲),靠五行属性区分(溶属水、破属土) | 用户拍板。避免引入「破甲回合数因字而异」的额外复杂度 |
| 9 | 穿甲**额外附带固定 +15% 伤害**,对有无减免的目标一律生效 | 穿甲三字已是各档满值锚点,没有加伤空间;实船只有四个敌人带减免,不给保底价值这三字在多数战斗里等同纯单攻 |

## 四 · 分步设计

### 第 1 步 · 承伤结算改写

`BattleEngine.DamageEnemy` 里那段替换为:

```
float taken = enemy.DamageTaken;

// 口径 1:减免(<1)遭克失效
若 taken < 1 且 KeMultiplier(attacker, enemy.Element) >= 1.5 → taken = 1

// 口径 6:穿甲只忽略减免
若 taken < 1 且 本次效果带 IgnoreArmor → taken = 1

// 口径 9:穿甲的固定加成,无条件生效
若 本次效果带 IgnoreArmor → taken += 0.15

// 口径 1 + 4:破甲加成始终生效,且不叠层
若 enemy.Statuses.Has(ArmorBreak) → taken += 0.25

damage = floor(damage × taken)
```

⚠ 四个条件的**顺序不可交换**:前两条都只在 `taken < 1` 时触发,必须在两个 `+=` 之前判断,
否则加成后的 `taken > 1` 会让 `taken < 1` 恒假、减免失效与穿甲忽略两条规则一起形同虚设。

三种典型组合的结果:

| 场景 | 计算 | 结果 |
|---|---|---|
| 穿甲打减免敌人(0.5) | 忽略减免 → 1,加成 → 1.15 | ×1.15(相对原 ×0.5,收益 2.3 倍) |
| 穿甲打普通敌人(1.0) | 不触发忽略,加成 → 1.15 | ×1.15 |
| 穿甲打已破甲敌人 | 1.0 + 0.15 + 0.25 | ×1.40 |

### 第 2 步 · 破甲状态

`StatusKind` 新增 `ArmorBreak`。施加时:

```csharp
enemy.Statuses.Apply(new StatusEffect
{
    Kind = StatusKind.ArmorBreak,
    Polarity = StatusPolarity.Debuff,
    Magnitude = 25,        // 百分比,当前恒为 25(口径 4 不叠层)
    TurnsLeft = 2,         // 口径 5
    SourceId = null,       // 按 Kind 去重 → 天然「不叠层只刷新」
});
```

⚠ `SourceId = null` 是实现「不叠层」的**手段**,不是疏漏。
`StatusBag.Apply` 对 `SourceId` 均为 null 的同 Kind 条目走覆盖刷新 —— 正是口径 4 要的语义。
这与 `HealOverTime`/`AttackBuff` 铸唯一序号求「可叠」是相反用法,`StatusEffect.cs` 的文档已记载这条约定。

`EffectKind` 新增 `ArmorBreak`,`value` 语义为**持续回合数**(默认 2),使「溶」这类字能单独施加。
本轮六个破甲字都写 `ArmorBreak 2`。

### 第 3 步 · 穿甲修饰

`EffectDef` 新增 `public bool IgnoreArmor { get; }`,构造参数与 `DoubleVsBurning` 同一模式
(那是为「灼」设计的既有先例)。`ConfigLoader` 的 `EffectDto` 与装配同步接上 —— 漏接是静默失败,
配置里写了也进不来(P0 的 `Turns`/`TargetAll` 就是这么漏的)。

## 五 · 测试策略

TDD。四组:

**1. 承伤结算的三条路径**
- 减免敌人(`DamageTaken 0.5`)挨非克制攻击 → 伤害 ×0.5(既有行为不变)
- 减免敌人挨**克制**攻击 → 减免失效,伤害不 ×0.5(既有行为不变)
- 减免敌人挨**穿甲**攻击 → 减免失效(新)
- 普通敌人(`1.0`)被破甲后 → 伤害 ×1.25(新)
- **减免敌人被破甲后挨克制攻击 → `taken = 1 + 0.25 = 1.25`**(口径 1 的核心断言:
  减免失效但破甲仍生效)

**2. 破甲状态语义**
- 连续施加两次破甲 → 容器里只有一条,承伤仍是 1.25(口径 4)
- 不同破甲字先后施加 → 同样只有一条(`SourceId` 均为 null)
- 破甲 2 回合后到期 → 承伤回到基础值
- 破甲是 `Debuff` 极性(为子项目 A 的 `Cleanse` 铺路)

**3. 穿甲的两重效果**
- 穿甲攻击打**已破甲**的敌人 → 破甲加成**仍然生效**,总系数 `1 + 0.15 + 0.25 = 1.40`(口径 6)
- 穿甲攻击打**无减免**敌人 → `×1.15`(口径 9 的保底加成,不是与普攻等价)
- 穿甲攻击打**减免 0.5** 敌人 → 忽略减免后再加成,`×1.15`
- 非穿甲攻击打无减免敌人 → `×1.0`,证明 15% 只属于穿甲

**4. 配置接线**
- 实船 `chars.json` 里九个字的效果能正确解析(`ignoreArmor` 标记真的从 JSON 传到 `EffectDef`)
- 这条要落在 `CharTableTests`(读真实配置),防的是 `ConfigLoader` 漏接字段的静默失败
