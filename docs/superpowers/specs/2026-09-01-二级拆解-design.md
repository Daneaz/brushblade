# 二级拆解:部件也能拆

> 2026-09-01 · 基线 `53b8418`(origin/main)

## 目标

让「字表功能解析.md」里已经写明的**二级组成**在游戏里真正可拆。今天 `蒸 = 艹 + 烝`
拆完就到头了 —— `烝` 在配置表里是 `{"id": "烝"}`,没有配方,玩家手里的部件卡没有「拆」按钮。
文档说 `蒸` 的二级是 `艹 + 丞 + 灬`,那 `烝 = 丞 + 灬` 这一层应当存在。

拆合语义因此变成两层都通:字拆成部件,部件再拆成部件。`蕉 = 艹 + 焦` 这一支本来就通
(`焦` 是可出牌字,自带 `隹 + 灬` 配方),这次要补的是**部件侧的那一半**。

## 一 · 核心障碍:`IsLeaf` 一个字段管两件事

`CharDef.IsLeaf`(= `Recipe.Count == 0`)现在同时被当成两个判据用,全库 14 处调用点:

| 真正想问的 | 调用点 |
|---|---|
| **能不能拆** | `ForgeEngine.TryDismantle` 门禁、`ForgeEngine.Suggest`、`CharInfo:26`(卡面印不印配方)、`BattleView:2766`(拆按钮) |
| **归字库还是部件池** | `ForgeEngine:97`(拆解产物归位)、`BattleEngine:770`(池中直出)、`Meta.DeckComponents:85`(每回合掉落池)、`Meta.PrerequisitesMet:500`(叠字前置)、`RunEngine:653`(战后奖励池)、`GameRoot:115/133/144`(商城重摆/商城池/宝箱池)、`MapView:98`(宝箱池) |

只要给 `烝` 配上配方,它立刻被下半张表全部判成「字」:

- `ForgeEngine:97` —— 拆 `蒸` 时 `烝` 进**字库**而不是部件池
- `Meta.DeckComponents` —— `烝` 不再算可掉落部件,**`蒸` 的原料掉不出来**
- `Meta.PrerequisitesMet` —— 合 `蒸` 要求先「拥有」`烝` 这张收集卡,**`蒸` 变得合不出来**
- `RunEngine:653` / `GameRoot` / `MapView` —— `烝` 混进战后奖励、宝箱池、商城货架

所以这不是一次纯数据改动:**必须把两个概念劈开**。

### 方案取舍

| 方案 | 做法 | 判断 |
|---|---|---|
| **A(采用)** | 新增 `CharDef.IsComponent`,由管线在 `chars.json` 上显式标 `"component": true` | 显式、自解释;管线本来就分得清「从详表来的字」和「从配方原料合成出来的部件」 |
| B | 不加字段,用 `Effects.Count == 0` 推导 | 零 schema 变更,但隐式且脆弱 —— 将来出现一个无效果的字就误判。`ComponentKin` 的注释里已经为同类事情立过规矩:「⚠ 清单是**显式**的,不许改成从 `CharDef.Element` 推导」 |
| C | 不给部件配方,改成「拆」的时候递归一次给出 `艹 + 丞 + 灬` | 保留 `IsLeaf` 语义,但丢掉了 `烝` 这一层的存在感,也满足不了「部件池的部件要有拆选项」 |

**采用 A。** 劈开后两个判据各归各位:

- `!IsLeaf` → 能拆 / 卡面印配方
- `IsComponent` → 属部件池,不进奖励池 / 宝箱池 / 商城 / 收集图鉴 / 叠字前置

两者从此正交:部件可以有配方(`烝`),字也永远不会是部件。

## 二 · 拆解范围

拍板取**文档「二级组成」列蕴含的那一批**,不做 IDS 全量展开。

全量展开会把 57 个部件里的 26 个拆开,引入 `𠅃 𭕄 㳟 龴 𠀐 𠂉 𣳾 𭠍` 这类生僻/增补平面部件
(共 40 个新部件)—— 正是 `export_chars.py` 的 `MANUAL_RECIPES` 当初刻意绕开的东西,
字体子集和玩家辨识都吃不消。

### 新增部件配方 12 条

| 部件 | 配方 | 来自 |
|---|---|---|
| 秋 | 禾 + 火 | 楸 |
| 崔 | 山 + 隹 | 熣 |
| 岂 | 山 + **己** | 桤、铠 |
| 荅 | 艹 + **合** | 塔 |
| 列 | **歹** + 刂 | 烈 |
| 喿 | **品** + 木 | 燥、澡 |
| 烝 | **丞** + 灬 | 蒸 |
| 则 | **贝** + 刂 | 铡 |
| 朵 | **几** + 木 | 剁 |
| 切 | **七** + 刀 | 沏 |
| 茾 | 艹 + **开** | 荆(见下) |
| 垔 | **覀** + 土 | 湮(见下) |

### 两条一级配方跳层的字

`荆` 与 `湮` 的一级配方本身跳过了字形的中间层,照配方展开原地打转:

- `荆` 的 IDS 是 `⿰茾刂`,`MANUAL_RECIPES` 当初改成了 `艹 + 刂`(理由:`茾` 没人认得)
- `湮` 的 IDS 是 `⿰氵垔`,`MANUAL_RECIPES` 当初改成了 `氵 + 土`(理由:`垔` 生僻)

拍板**推翻当初的绕开**,把中间层引回来:

```
荆 = 茾 + 刂 ,  茾 = 艹 + 开
湮 = 氵 + 垔 ,  垔 = 覀 + 土
```

这样文档里的二级 `艹 + 开 + 刂` / `氵 + 覀 + 土` 在游戏里真实可达。

### 新增部件条目 10 个

`己 合 歹 品 丞 贝 几 七 开 覀` —— 全是终点(拍板:只做两级,不递归)。
`品 = 口+口+口`、`合 = 亼+口` 再往下就是笔画,没有拆合语义,与「五行部件不拆」「禾 不拆」
同一条规则。

## 三 · 数据与管线

`tools/pipeline/export_chars.py`:

1. 新增 `COMPONENT_RECIPES` 表(上面 12 条),与既有的 `STACK_RECIPES` / `MANUAL_RECIPES` 同层级,
   带注释说明每条的来源字。
2. `MANUAL_RECIPES` 改两条:`荆: [艹, 刂] → [茾, 刂]`、`湮: [氵, 土] → [氵, 垔]`。
3. `build_chars` 的部件收集改成**闭包**:合成部件条目时先查 `COMPONENT_RECIPES`,有配方就写进去,
   并把它的原料也加进部件集合。新部件全是终点,一轮即可收敛 —— 但代码写成 worklist 循环,
   免得将来加第三级时静默漏掉(与 `pipeline_token_tables_drop_silently` 同类的坑)。
4. 部件条目一律加 `"component": true`,含开头硬编码的五行五条
   (`entries = [{"id": e, "element": ...}]`)。可出牌字不加这个字段。

`chars.json` 从 131 条涨到 **143 条**(74 字 + 69 部件)。

新增 12 个部件条目,不是 10 个 —— 除 `己 合 歹 品 丞 贝 几 七 开 覀` 这 10 个终点之外,
`茾` 与 `垔` **本身也是全新条目**:旧配方 `荆 = 艹 + 刂`、`湮 = 氵 + 土` 从未引用过它们,
所以它们不在原来那 57 个部件里。(2026-09-01 实施时更正:此处原写 141 / 67,是漏算了这两个。)

## 四 · Core / Data 改动

### `CharDef`

新增 `public bool IsComponent { get; }`,构造函数尾部加可选参数 `bool isComponent = false`。
`IsLeaf` 保持原样不动。

### `ConfigLoader`

`CharDto` 加 `public bool Component { get; set; }`,建 `CharDef` 时透传。

### `ForgeEngine.TryDismantle`

两处改动:

- **产物归位**(`:97`):`!idef.IsLeaf ? toLibrary : toPool` → `idef.IsComponent ? toPool : toLibrary`
- **来源放开**:现在硬性要求 `state.Library.Contains(charId)`。改成字库或部件池都行 ——
  在池里的就从池里移除、产物也全进池。容量校验:拆部件净 +1 个池位(出 1 进 2),
  按 `poolCapacity` 判;不动字库容量。

### 其余按表替换 `IsLeaf → IsComponent`

`BattleEngine:770`、`RunEngine:653`、`Meta.DeckComponents:85`、`Meta.PrerequisitesMet:500`、
`GameRoot:115/133/144`、`MapView:98`。

### 保持 `IsLeaf` 不变的三处

`ForgeEngine.Suggest`(可拆也可合 —— 拍板;部件进提示列表,但 `unlockedChars` 过滤在实战里
会把它们挡掉)、`CharInfo:26`(部件也该在卡面印配方)、`BattleView:2766`(拆按钮改成
`!def.IsLeaf`,去掉 `inLibrary` 前提,让池中部件也能拆)。

## 六 · 拆合的价值模型(2026-09-01 拍板)

讨论范围时把整张字表的可合成性点了一遍,结论记在这里,免得后人重算:

- **74 个可出牌字里只有 35 个能「跨字合成」**(不拥有本字、靠拆别的字搓出来)。
  按档看:金 10/10、橙 10/10、红 5/5 全通;白 2/12、绿 1/11、蓝 0/11 几乎全锁;紫 7/15。
- **根因是中性部件专属化**:40 个中性部件里 36 个自锁 —— 只有拆掉那个字本身才拿得到它的
  部件(`尧` 只从 `烧` 来)。拆了再合回去净收益 0。
- **拍板:不修这一条。拆是「单向变现」,不是双向合成。**
  拆的意义是把用不上的牌换成免 AP 的部件直出 + **五行部件**(五行部件能去合金/橙/红那
  25 个纯五行字)。中性部件是变现的残渣。稀有度维持现状(纯经济轴:宝箱权重 /
  集卡升级成本 / 皮肤色 / 奖励池权重),不与合成难度挂钩 —— 合成难度实际只有两个值,
  撑不起七档。

**这个模型正好解释了本次范围为什么是对的**:选中的 10 条部件配方,**每一条都恰好产出
1 个五行部件**(秋→火、崔/岂→山、荅→艹、列/则→刂、喿/朵→木、烝→灬、切→刀);
而没选的 17 个部件拆出来是纯废料(`仓 = 人+㔾`、`尧 = 𭠍+兀`、`辟 = 𡰪+辛`…),0/17 产
五行部件。文档「二级组成」的筛选条件是「比一级多给出五行信息」,与「单向变现的价值 =
五行部件」是同一个判据。

`禾` 是唯一漏网的(`丿 + 木` 能产 `木`),拍板**仍不拆** —— `丿` 是笔画不是部件,维持
`gen_char_doc.py` 里 `STOP = {'禾'}` 的既有理由。

### 已接受的代价:`荆` / `湮` 的变现率下降

引回 `茾` / `垔` 之后,这两个字**第一次拆的产出从 2 个五行部件降到 1 个**:

| | 拆一次 | 拆到底 |
|---|---|---|
| `荆` 现状 `艹 + 刂` | 艹 + 刂 = **2 个五行部件** | 同左 |
| `荆` 改后 `茾 + 刂` | 茾(废) + 刂 = **1 个** | 艹 + 刂 + `开`(废) |
| `湮` 现状 `氵 + 土` | 氵 + 土 = **2 个五行部件** | 同左 |
| `湮` 改后 `氵 + 垔` | 氵 + 垔(废) = **1 个** | 氵 + 土 + `覀`(废) |

全表唯二变差的两个字。已向用户提出,**用户复核后仍拍板引回** —— 让文档里的二级组成
`艹 + 开 + 刂` / `氵 + 覀 + 土` 在游戏里字字可达,优先级高于这两个字的变现率。

顺带更正一条口径:`Meta.DeckComponents` 只喂 `RollStartingPool`(登塔起手随机掷 2 个),
**部件早已不每回合掉落**(`BattleEngine.cs:1784`,2026-08-04 掉落改造)。中性部件的全部
来源是:登塔起手、拆字、奇遇 `GainComponents`。
