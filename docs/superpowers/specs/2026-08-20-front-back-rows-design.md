# 前后排站位系统 — 设计稿

日期:2026-08-20
状态:已与用户逐节确认,待写实现计划

## 1. 目标

给战斗引入**前后排站位**,把「打谁」从一个自由选择变成一个受阵型约束的战术决策:

- 我方召唤物有 6 个固定槽位(3 前 3 后),召唤时由玩家指定落在哪一格。
- 敌方同样分前后排,前排未清空时够不到后排。
- 新增三只在这套规则里各有定位的字怪(两只远程、一只近战刺客)。
- 少量既有字卡获得「越过阵型」的能力,成为破局手段。

## 2. 范围

**做**:Core 的槽位模型与定向裁定、敌方排位字段与生成期约束、三只新怪、三张字卡改动(含管线接线)、战斗界面布局重排、存档字段、配套测试。

**不做**:
- 存档迁移(项目未上线,见记忆「存档不需要兼容」)。
- 字表全量重新定位——只改点名的三张,其余一律走默认。
- `BattleView.cs` 的整体拆分重构(可选项,用户默认不提)。

## 3. 数据模型

### 3.1 我方:定长 6 槽数组

`BattleEngine._summons` 从紧凑 `List<SummonState>` 改为**定长 6 的数组**,**下标即槽位**:

```
槽 0  1  2   ← 前排
槽 3  4  5   ← 后排
```

- `null` = 空槽(从未使用或已被清空)。
- `Hp <= 0` = 尸体,**仍占槽**,可被「复活」就地救回,与现行为一致(引擎从不移除阵亡召唤物)。
- `Summons` 对外暴露的长度恒为 6 且含 `null`。

**为什么是定长数组,不是「紧凑 List + Slot 字段」**:事件里的 `SecondIndex`(召唤物下标)、`BattleView._summonRectByCore`(血条引用)、存档下标,现在三者是同一个数;槽位化后仍是同一个数。若走紧凑 List,槽位与下标脱钩,每一处都要转换,而这类错是运行期才炸的;定长数组的代价只是 `null` 检查,编译期就能想全。

**波及**:引擎内约 15 处 `foreach (var summon in _summons)` 需加 `null` 检查;测试里 14 处 `Summons.Count` 改用已存在的 `AliveSummonCount`。

### 3.2 敌方:紧凑 List + 排位属性 + 不变式

`_enemies` **保持紧凑 List**,排位是 `EnemyState` 上的属性,不是位置。约束靠不变式维持:

> **Front ≤ 3 且 Back ≤ 3**

由生成期(`Endless.BuildFloor`)保证,分裂期守闸维持。章节关卡路径(`enemies.json` 的 `chapters`)遭遇为手工编排且最多 3 只,天然满足,靠编排纪律维持。

**「前排从未有过」与「前排已被清空」同等对待**:两侧皆然。一场若摇出全员后排的敌人,我方单体伤害直接全场可点;我方若只有后排召唤物,近战敌人直接走随机候选池。

**为什么敌方不也改定长数组**:玩家要点空槽落位,所以**我方**的空槽必须是可点的实体;敌方玩家不往里放东西,只需要不变式。而敌方改定长数组会让 `int aoeCount = _enemies.Count;` 那条守卫失效——它靠「分裂只在 List 尾部追加」成立,分裂怪若填进中间空槽就会吃到同一发 AOE。不值得为对称性冒这个险。

### 3.3 新增字段(三个,彼此正交)

加在 `EnemyDef` 上,从 `enemies.json` 读:

| 字段 | 取值 | 缺省 | 含义 |
|---|---|---|---|
| `Row` | `Front` / `Back` | `Front` | 站位 |
| `Range` | `Melee` / `Ranged` | `Melee` | 能否越过我方前排 |
| `Focus` | `Default` / `Player` | `Default` | 够得着玩家时是否死盯玩家 |

**不做成 `Ability` 的取值**:`EnemyAbility` 是单值枚举,远程若占用它就会与「灯花 Sear」「焦痕 Scorch」互斥,而「远程的灯花」是完全合理的组合。三个正交字段没有这个问题。

`EnemyState` 开场从 `Def` 拷一份;叠字怪分裂出的克隆**继承母体排位**;分裂守闸从 `_enemies.Count < EnemyCap` 改为「**母体所在排未满**;该排满则落另一排;两排都满则不分裂」。

## 4. 定向裁定

新建 `Core/Targeting.cs`——**纯函数,不持有引擎状态**(吃列表与 RNG,返回下标)。`BattleEngine` 已 2386 行,再往里塞会更难读,而这套规则本身值得独立测试。

### 4.1 敌人 → 我方

替换现行的 `int tankIdx = FirstAliveSummonIndex();`:

| 敌人 | 我方前排有存活 | 我方前排已清空 |
|---|---|---|
| `Melee` / `Default`(现有全部近战怪) | 打前排槽序最小的存活者 | 在「存活后排召唤物 ∪ 玩家」里**均匀随机**取一 |
| `Melee` / `Player`(败笔) | 同上,被前排拦下 | **必打玩家** |
| `Ranged` / `Default`(墨溅) | 无视前排:在「存活后排召唤物 ∪ 玩家」里均匀随机 | 同左 |
| `Ranged` / `Player`(悬针) | 无视前排:**必打玩家** | 同左 |

**均匀随机的口径**:把所有存活后排召唤物**与玩家**放进**同一个候选池**抽一个,而**不是**先 50/50 决定「打后排还是打玩家」。后排站 2 只时玩家挨打概率是 1/3——站位越厚玩家越安全,符合直觉,也好测。

### 4.2 我方 → 敌方

**唯一受前排限制的是 `DamageSingle`(单体直接伤害)。其余一切对敌单体效果无视排位。**

- **受限**:`DamageSingle`
- **不受限**:`Freeze` `Slow` `Blind` `Silence` `ArmorBreak` `Dispel` `BurnSingle` `Bleed` `BurnNoDecay` `BurnSettleNow` `Detonate`
- **本来就无视**:全部 `TargetAll` / AOE

两处边界的理由:`BurnSingle`/`Bleed` 最终虽会掉血,但施加的是状态而非伤害数字,归「够得着下毒」一侧;`Detonate`/`BurnSettleNow` 必须与灼烧同侧,否则「挂得上却引不了」是条死规则。

一句话讲给玩家:**打不到后面,但够得着冻住、破甲、下毒。**

**混合字按最严的算**:一张字的效果里只要含 `DamageSingle`,它的目标就受前排限制(除非标了偷袭)。例:湮(`DamageSingle 20` + 驱散全部)受限;藤(纯 `Freeze`)全场可点。判定函数 `CanTargetBackline(def)`,与已有的 `NeedsTarget(def)` 并列。

**召唤物出手**:

| 类型 | 规则 |
|---|---|
| `Melee`(默认) | 打敌方前排中 `_enemies` 序最靠前的存活者;无前排则全场序最靠前的存活者。**站后排照样能打**,排位不影响其输出 |
| `Ranged`(灶、烓) | **优先打敌方后排**(后排中 `_enemies` 序最靠前的存活者),后排空才按 `Melee` 同规则打前排——越过前排点掉加攻怪正是远程的战术价值 |

**标了偷袭(`CanStrikeBackline`)的字**:任意存活敌人可点。

### 4.3 Boss 技能

| 技能 | 处理 |
|---|---|
| `Deluge` 淹没(全体) | AOE,无视排位,**不变** |
| `Pierce` 贯穿 / `Devour` 吞噬 | 其中的「最前召唤物」重定义为「**前排槽序最小的存活者;前排全空则取后排槽序最小的存活者**」 |
| `Topple` 倾覆 | 只打玩家,不受影响 |

## 5. 新敌人

命名沿用现有「书写事故」族系(错字鬼 / 缺笔妖 / 通假字 / 生僻字 / 焦痕 / 灯花 / 墨渍):

| 字 | 五行 | HP | ATK | Row | Range | Focus | 行为 |
|---|---|---|---|---|---|---|---|
| **墨溅** | 水 | 100 | 30 | Back | Ranged | Default | 无视前排,在「我方存活后排召唤物 ∪ 玩家」里均匀随机 |
| **悬针** | 金 | 90 | 45 | Back | Ranged | Player | 无视前排,永远打玩家 |
| **败笔** | 火 | 150 | 55 | Front | Melee | Player | 被前排拦下;我方前排一清就死盯玩家 |

数值对齐现有档位(错字鬼 140/40、灯花 120/30、叠字怪 160/50)。两只后排怪血刻意薄(90/100):它们难被够到,所以玩家一旦清了前排或掏出偷袭字,就该能迅速收掉。**这批是初值,过 balance harness 仿真再校。**

### 5.1 生成期约束(`Endless.BuildFloor`)

- 后排怪先占后排(≤3),溢出改判前排;前排同理。
- **首位仍强制从前排子池抽**——沿用现有「辅助型不单独成场」的同型规则。不加这条会摇出「全员后排」的怪场,排位规则整场失效。

## 6. 字卡改动与管线接线

`chars.json` 是管线产物,手改会被 `test_shipped_chars_json_is_regenerable_from_spec` 逮住,故一律走详表 → `extract_values` → `export_chars`。

| 字 | 现状 | 改动 |
|---|---|---|
| **刺** 金·蓝 | 单体 135,穿透 15 | 加偷袭:可点后排 |
| **灶** 火·紫 | 召唤 1(110 血 / 攻 0)+ 灼烧 2 | 召唤物标 `Ranged`;攻 0 → **20** |
| **烓** 火·金 | 召唤 1(220 血 / 攻 0)+ 灼烧 3 全体 | 召唤物标 `Ranged`;攻 0 → **30** |

**攻击力定值理由**:同档召唤物攻击力,紫档 40~70(最低是蕉 30)、金档 90。给 20/30 是明显低于同档——它们各自还带 2 层 / 3 层全体灼烧,补到同档会超模。

**錰(金档,单体 415、穿透 30)刻意不给偷袭**:一发就能秒掉 90 血的悬针,等于把后排威胁整个注销;留作日后调整余量。

**已知后果**:`StrikeOnceWithSummon` 里有 `if (summon.Attack > 0)` 这道闸,灶/烓 攻 0 时从不走 `DamageEnemy`。给了攻击力后这条分支第一次走通,它们的伤害会**开始过五行生克**(火系打木系 ×1.5、打水系 ×0.5)。这是对的行为,但现有涉及灶/烓 的测试数字会变——不是回归,是新口径。

### 6.1 管线接线

| 项 | 详表写法 | `extract_values.py` |
|---|---|---|
| 召唤物攻击力 | `` `Summon 1`(220 血/攻 30) `` | **零改动**——现有正则 `` `Summon (\d+)`\((\d+) 血/攻 (\d+)\) `` 原样吃下 |
| 召唤物远程 | 加无数值 token `` `Ranged` `` | 召唤分支里 `passive["ranged"] = True`,与 `OnHitBurnAll` 逐字同构 |
| 伤害字偷袭 | 加无数值 token `` `Backline` `` | 挂到伤害效果上 `effect["backline"] = True`,与 `DoubleVsBurning` 逐字同构 |

`` `Backline` `` **不能放进 `VALUELESS_EFFECTS`**——那会让它变成一条独立效果落进 `chars.json`,而 `EffectKind` 里没有这个值,`ConfigLoader` 会在加载期直接抛 `ConfigException`。

`ConfigLoader` 侧新增解析:`EffectDef.CanStrikeBackline`、`SummonPassive.Ranged`。

**必须补一条 pytest**,断言这三张字在生成出的 `chars.json` 里确实带上了新字段。token 表认不得的标记是**无声丢弃**的(见记忆「管线 token 表静默丢弃」),不加这条测试,漏接线会一路沉默到运行期。

## 11. 决策记录

设计过程中的六处修正,均由用户拍板:

1. **控制类不限前后排** — 受限的只有 `DamageSingle`,其余单体效果全部无视排位。
2. **柳保持前排近战** — 闪避 50 是坦克属性,不是远程属性。
3. **两边都 3+3** — 原案我方 4 前 2 后,改为敌我对称各 3 前 3 后(`EnemyCap` 本就是 6,天然吻合)。
4. **灶、烓 加基础攻击** — 攻 0 → 20 / 30。
5. **砍掉锥与焰** — 偷袭名单只留刺。
6. **布局重排** — 拆合台移到右侧竖栏,解决纵向预算。

## 12. 已知取舍与风险

- **全字表只有「刺」能点后排。** 对付悬针(专射玩家的后排怪)只剩四条路:清光前排、AOE、控制类、掏刺。这四条够用,不是死局,而且把刺抬成了独一无二的战术位。若实测后排太难够到,加字只需在详表里多写一个 `` `Backline` ``——管线标记已铺好。
- **「败笔」的辨识度偏低。** 它仍受前排限制,与普通近战怪的差异只在我方前排清空后的残局体现。这是用户明确选择的口径(而非「突进无视前排」),靠 55 的高攻做区分。
- **新怪数值全是初值**,未过仿真;需 balance harness 校准后再定稿。
- **布局重排会动 `BattleView.cs` 一大片**(该文件 2588 行)。`BuildLayout` 是天然可切的边界,但用户默认不提取,保持 surgical。
