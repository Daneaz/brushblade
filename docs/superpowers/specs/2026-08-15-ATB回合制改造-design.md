# ATB 回合制改造:玩家纳入速度制 · 设计规格

> 2026-08-15 · 推翻 `2026-08-04-状态容器与速度-design.md` 的口径 6
> (「速度只作用于敌人与召唤物,玩家仍是 AP 制」)

## 一 · 背景

`2026-08-04` 的状态容器改造给敌人与召唤物装上了行动计量器(`ActionMeter`),但玩家被明确排除在外
——当时的口径 6 是「玩家的行动预算是 AP,两套模型不混用」。结果是速度这条属性只有一半:
减速能让敌人少动,加速却没有对应的玩家侧收益,`SpeedModifier` 在玩家身上无处可施。

本 spec 把玩家也纳入调度,战斗从「玩家回合 → 敌方回合」的固定交替改为**连续推进的 CTB**:
所有单位共用一条时间轴,谁先攒满计量器谁先动。

### 1.1 现状

一个「回合」是 `BattleEngine.EndTurn()`(`BattleEngine.cs:688-953`)里的一条 265 行流水线:

```
玩家阶段(花 AP 出牌,手动 EndTurn)
  → 敌人灼烧 → 玩家灼烧 → 敌人流血 → 玩家 HoT
  → 召唤物光环治疗 → 召唤物按 ActionMeter 出手
  → 敌方辅助加攻 → 敌人按 ActionMeter 出手
  → 全体状态 TurnsLeft −1 → 缺笔妖补全
  → StartTurn:Turn+1、AP 重置、回合掉字
```

问题在于**「回合」是全局计时单位**:流血/冻结/诅咒/盲的 `TurnsLeft`、灼烧每回合 −1 层、
AP 恢复、回合掉字、缺笔妖补全、Boss 蓄力,全部挂在它上面。改成 CTB 后这个单位必须重新定义。

## 二 · 范围

### 做

| 块 | 内容 |
|---|---|
| 1 | `TurnScheduler`:连续推进的调度器,Core 纯 C# |
| 2 | 驱动接口:`AdvanceOnce` / `Forecast` / `PeekNextActor`,`EndTurn` 改为包装 |
| 3 | 时序归属重排:DOT、状态递减、缺笔妖、光环治疗各归其位 |
| 4 | 立即判负 / 立即判胜 |
| 5 | 事件 `EnemyTurnBegan` 退役,换 `ActorActed` |
| 6 | `Juice` 三段切分删除,改为逐行动者播放 |
| 7 | TAB 行动条 UI(顶部横条,预测 6~8 拍) |
| 8 | `PlayerSpeed` 作为第五条角色属性接入 |

### 不做

- **不给敌人配差异化速度**。字怪 `Speed` 仍全部 100,差异化是配值,留待引擎稳定后的平衡期。
  没有这一步,CTB 的策略价值只体现在减速字与玩家加速上——这是本次的已知局限,不是遗漏。
- **不新增任何字**,不改字表数值。
- **不做速度相关的新机制**(加速字、拖延字等)。`SpeedModifier` 的施加口已经存在。

## 三 · 已定口径

| # | 口径 | 理由 |
|---|---|---|
| 1 | 计时单位改为**每单位自己算**:状态在该单位自己行动时结算与递减 | 标准 CTB。语义自洽:被减速的敌人中的毒也跌得慢 |
| 2 | 轮到玩家 = **一整个 AP 回合**(AP 重置为 3,自由拆/合/施放直到用完或手动结束) | 拆合链路需要一回合内做多个动作,一次一个动作会把它切碎 |
| 3 | 调度用**连续推进**:算出谁最先攒满 100,全场推进那么多,该单位行动后 −100 | 出手序列可精确预测(TAB 要的就是这个),速度差表现平滑 |
| 4 | 玩家速度是**第五条角色属性**,基准 100,走 `MetaRules` 随等级成长 | 与 `PlayerDefense`/`PlayerDodge` 同型。基准 100 = 与敌人同速 = 现行的一人一手 |
| 5 | 玩家加速时 **AP 与回合掉字全部跟着翻倍** | 一次行动 = 一份完整回合,语义最自洽。代价:速度成为最强属性,养成曲线要把速度成长压得很慢 |
| 6 | 冻结**照常上行动条,轮到就跳过**并把冻结 −1 | 计量器冻住 + 状态按自身行动递减 = 永久冻结死锁。跳过语义还能在 TAB 上直接画出「它下一拍会被跳过」 |
| 7 | 通假字现形:**挨打或出手,先到先触发** | 原口径只认出手(8.3 / 2026-08-08)。加上挨打给玩家一条主动试探路径;两条旧测试也能原样活着 |
| 8 | 有效速度钳到 **[25, 400]** | 下限防死锁(速度 0 → 永不行动 → 自身状态永不递减 → 减速永不解除);上限防养成与叠加失控 |
| 9 | `MaxActionsPerTurn = 2` **删除** | CTB 下速度 200 就该是两倍频次,这是设计目标本身;上限改由速度钳位承担 |
| 10 | 存档**不考虑兼容**,直接改结构 | 项目未上线,全程测试阶段(2026-08-15 用户明确) |
| 11 | 复活 = 满血站起来,**时间轴原地继续**,不跳过剩余行动者 | 见 §4.3.1。现行 `Revive()` 隐含跳过当拍剩余敌方行动,那条福利在 CTB 下没有立足点 |

### 3.1 本次推翻的既有裁定

三条,都是有意的,不是回归:

| 原裁定 | 出处 | 现在 | 为什么 |
|---|---|---|---|
| 速度只作用于敌人与召唤物,玩家仍是 AP 制 | `2026-08-04` 口径 6 | 玩家进调度器 | 本 spec 的目的 |
| 缺笔妖补全压到回合末尾 | 2026-07-30 试玩 | 挪到它自己行动前 | CTB 下已无「回合末尾」这个位置。副作用:它补完立刻用新攻击力打这一下,强度上升一档,平衡期再调 |
| 通假现形只看「是否出手」,与命中无关 | 2026-08-08 | 出手或挨打都触发 | 见口径 7。「它出手了但打空」仍然现形,旧断言不变 |

## 四 · 设计

### 4.1 调度器

Core 内新增纯 C# 类,不认识 `EnemyState`/`SummonState`,只吃 `(有效Speed, ActionMeter)`:

```csharp
public enum ActorKind { Player, Summon, Enemy }
public readonly struct ActorRef        // Player 时 Index = -1
{
    public ActorKind Kind { get; }
    public int Index { get; }
}

sealed class TurnScheduler
{
    public ActorRef Next();                          // 推进时间到最近一个满格者,并扣掉 100
    public IReadOnlyList<ActorRef> Forecast(int n);  // 本地拷贝推演,不触真实计量器
}
```

**推进算法**(每次只吐一个行动者,`Advance` 无状态,计量器存在各单位上):

1. 若已有单位 `Meter >= 100`,按 tie-break 取第一个,`Meter −= 100`,返回它
2. 否则推进 `ticks = min over i of ceil((100 − Meter_i) / Speed_i)`,全场 `Meter_i += Speed_i × ticks`,回到第 1 步

⚠ **全程整数运算**,`ticks` 是整数;不许引入 `float` 中间值——`float` 中间精度在 Unity Mono
与 .NET 8 下不同,配上取整会整级翻车(2026-08-15 护甲缩放刚踩过)。

这条算法与「连续时间」的差别只在**同一 tick 内多人同时攒满时的排序**:连续模型按小数先后,
本算法按 tie-break。长期比例精确 —— 速度 100 对 60,五个 tick 内恰好是 5 次对 3 次。
选整数 tick 是因为它让 `ActionMeter` 保持现有语义(0~199 的整数,行动后扣 100 留余额),
`EnemySnapshot`/`SummonSnapshot` 的既有字段一个都不用动。

**有效速度** = `Speed + 所有 SpeedModifier 的 Magnitude 之和`,然后**钳到 [25, 400]**。
下限是硬要求而非保守:现行减速下钳是 `Math.Max(0, …)`,速度 0 的单位永远攒不满 → 永远轮不到
→ 它自己那拍的状态递减永远不跑 → 减速永远解不了。钳到 25(四拍动一次)自然消解,
不需要额外的跳过分支。

### 4.1.1 开局与新生单位的初始计量器

**玩家开局的第一拍要在构造期正常消费掉。** 战斗一开始 `Phase` 就是 `PlayerTurn`,玩家直接
操作 —— 那一拍没经过 `Advance`,也就没扣掉 100。若不记账,玩家行动后与所有人同时归零,
此后每次推进都三方并列、玩家优先级最小永远先手,其余单位会被饿死。

故主构造函数末尾(场上单位全部初始化之后)跑一次调度:

```csharp
var openingSlots = BuildSlots();
var openingStep = TurnScheduler.Advance(openingSlots);
if (openingStep.Actor.Kind == ActorKind.Player)
    WriteBackMeters(openingSlots, openingStep.Meters);
```

⚠ **`PlayerActionMeter` 必须始终非负**,不许用「记成负债」的写法(如 `= -Threshold`)代替
这次消费。负值会让玩家的 `need = Threshold − Meter` 严格大于 `Threshold`,`ceil` 之后至少
2 tick;而「创建即满格」的召唤物打完归零只需 1 tick 回满 —— 两者之间必然空出一整个 tick,
该 tick 里所有创建即满格的单位会在敌人和玩家之前**再打一轮**。2026-08-15 实测:开局施放
4 只召唤,出手序列是 `[0,1,2,3,0,1,2,3]` 而非 `[0,1,2,3]`。这是结构性的,与负值的具体大小无关。

⚠ **只在玩家赢下这一拍时才写回**。玩家速度若远低于场上单位,`Advance` 会选中敌人 ——
绝不能在构造期执行它的行动(会产生表现层收不到的事件,甚至开局就把玩家打死)。不写回则
退化为「玩家白拿一拍」,对慢速玩家是友好的兜底。

⚠ **只在主构造函数里做**。`Restore` 走快照里的 `PlayerActionMeter`,再消费一次会让续爬后
玩家白让一拍。

**战斗中新生的召唤物** 则相反,创建时 `ActionMeter += Speed`,**当回合就能出手** ——
这不是补偿,是既有行为本身:旧 `EndTurn` 的召唤段是 `summon.ActionMeter += summon.Speed`
后 `acts = meter / 100`,新召唤物 0 + 100 = 100 恰好够动一次。用 `Speed` 而非 `Threshold`:
带被动的召唤物(桤 `Speed` 150)旧行为是 1 次行动 + 50 点余额,用 `Threshold` 会把余额吃掉。

开局就在场的单位(敌人、`startingSummons`)**不给任何先手**,从 0 攒起。

> 这一节是 2026-08-15 执行期补写的:原 spec 通篇没定义开局初始计量器,接线任务因此返工三轮。
> 期间试过「玩家记负债」与「给非玩家单位创建时先手」两种写法,都被证伪 —— 前者制造免费轮次
> (见上),后者依赖构造那一刻的速度,而仓库里几乎所有速度测试都是「先构造引擎、再改速度」。

### 4.1.2 开局边界与旧断言的冲突

**没有任何单一初始状态能同时满足全部旧断言**,因为一部分旧断言编码的是旧实现的细节而非规则。
最典型的是减速:旧的 `SlowActs` 开关让「减速当回合立刻跳过一拍」,而共享时间轴下,减速只影响
此后的累积速率,不会把已经攒满的那一格退回去。这类差异属于口径 1「每单位自结算」的直接后果,
按「行为按新设计确实该变」处理,不得为了让旧断言变绿而回退调度模型。

判据:**结构性缺陷必须消除,开局边界差异可以接受**。前者的表征是「同一次 `EndTurn` 内某单位
凭空多打一轮」这类与稳态无关的异常,后者只影响第一次 `EndTurn`,稳态正确。

**tie-break**:同时攒满时按 `召唤物(下标升序) → Buff 能力敌人(下标升序) → 其余敌人(下标升序) → 玩家`。

⚠ **玩家排最后,方向不要再调回去。** `EndTurn` 的语义是「玩家让出行动权、推进到下次轮到我」——
玩家刚动完就让出,并列时理应排在所有人后面。本 spec 初稿把玩家定成优先级最小(并列必赢),
结果每次推进后玩家都抢在敌人前面把行动权收回去、敌人拿不到那一拍;为此先后试过三种「开局记账」
(创建时先手 / 玩家记负债 / 消费一拍),全是在给这个反向规则打补丁,补一个漏一个,返工四轮。
2026-08-15 第五轮才定位到根因是方向本身。改对方向后,四样特例机制**全部删除**,
`TurnScheduler` 的 `Advance`/`FirstFull`/`TicksUntilAnyFull` 一行未动。

Buff 敌人优先于普通敌人这一条要写测试锁死:它保住了「标点小妖先摇旗、同伴才带着加成出手」
这个既有节拍,而一旦小妖被减速,它自然排到后面——那正是新系统该有的行为。

`Forecast` 必须是纯函数:在本地拷贝上推演,不触碰真实计量器。否则 UI 每帧刷新一次预测
就会把战斗推着走。冻结单位照常进 `Forecast`,标记为「将被跳过」,UI 画成灰格。

### 4.2 驱动接口

`BattleEngine` 对外:

| 接口 | 作用 | 谁用 |
|---|---|---|
| `Forecast(int count)` | 向前预测 N 个行动者,不改任何状态 | TAB UI |
| `PeekNextActor()` | 当前队首,不改状态 | UI 高亮 |
| `YieldTurn()` | 玩家让出行动权:跑玩家侧收尾结算 | 表现层 |
| `AdvanceOnce()` | 推进并**执行一个**非玩家行动者;若下一个是玩家则跑 `BeginPlayerTurn()`、置 `Phase = PlayerTurn`、返回 `false` | 表现层逐格演出 |
| `EndTurn()` | **包装**:`YieldTurn(); while (AdvanceOnce()) {}` | 测试 + 兼容 |

`EndTurn` 保留为包装是硬要求:测试与游戏必须走**同一份实现**。若两边各留一套,就会退化成
「工装绿≠编辑器绿」——这个仓库已经因为同类问题翻过两次车(Presentation 编译、NUnit API 差异)。

`_events.Clear()` 从 `EndTurn` 开头下移到 `AdvanceOnce` 开头:逐格驱动时每次拿到的就是
**这一个单位**产生的事件;`EndTurn` 包装改为跨段累积,拿到的仍是完整一整轮。

`Phase != PlayerTurn` 时(`Won`/`Lost`/`DropChoice`)`AdvanceOnce` 直接返回 `false`。
`DropChoice`(满库决议)仍在 `BeginPlayerTurn` 的 `StartTurn` 段内产生,玩家决议后照旧继续。

### 4.3 时序归属

**玩家那一拍**

1. 玩家灼烧结算(层数 × 系数掉血,然后 −1 层)
2. 玩家 HoT 结算
3. `PlayerHp <= 0` → **立即判负**(当拍的玩家侧状态递减照跑,见下)
4. `StartTurn`:`Turn`+1、AP 重置(含封字扣减)、回合掉字
5. —— 玩家操作,`Phase = PlayerTurn` ——
6. 让出行动权(`YieldTurn`):**玩家侧**状态递减(`TickTurns` + 战意 −1 层)

第 1~4 步在 `BeginPlayerTurn()` 里,第 6 步在 `YieldTurn()` 里。

**每个敌人那一拍**

1. 该敌人灼烧结算 → 死了立即 `ResolveDefeat` + 判胜
2. 该敌人流血结算 → 同上
3. 若是缺笔妖:补全(+攻 +血,第 3 次 ×2)
4. 若冻结:跳过行动,冻结 −1,直接跳到第 6 步
5. 行动:辅助加攻 / Boss 蓄力或大招 / 普攻(含灯花挂灼烧)
6. **该敌人**状态递减

**每个召唤物那一拍**

1. 光环治疗(桃)
2. 出手(含挂灼烧、诅咒)
3. **该召唤物**状态递减

**全程**:任何一记伤害把 HP 打到 0 就当场结算 `Won`/`Lost`,不推迟到下一拍——玩家已经死了
却还要等 UI 把剩下几只怪的动画读完才弹结算,是明显的坏手感。同归于尽时**玩家阵亡优先**
(既有口径,不变)。

**通假字现形**:受到任何伤害时现形(玩家直伤 / 召唤物伤害 / DOT),**或**自己出手后现形,
先到先触发。「出手但打空也现形」的旧口径保持不变。

### 4.3.1 复活与时间轴

现行 `Revive()`(`BattleEngine.cs:577`)是 `PlayerHp = Max; Phase = PlayerTurn; StartTurn();`
——它**隐含跳过了当拍剩余的敌方行动**,并因此需要 `TickAllStatuses()` 被刻意排在判负早退之前
(否则复活后所有状态多续一拍,`Revive_DoesNotGrantExtraStatusTurn` 守着这条)。

CTB 下改为:**复活 = 满血站起来,时间轴原地继续**。不重置调度器、不跳过剩余行动者、
不补任何递减。

这样处理的好处是那条特殊逻辑整个消失:玩家侧状态只在玩家自己那拍递减,敌人侧只在各自那拍递减,
判负发生在谁那拍就只影响谁,不存在「跳过一段导致某些单位少递减一次」的口子。

代价是**现行的隐性福利没了**:原先复活等于白捡「剩下的怪本回合不再出手」,现在复活后
时间轴接着走,没行动的怪照常打。这是有意的——时间不该因为买了复活就跳过一段;
玩家买到的是满血,不是无敌一轮。

### 4.4 事件与表现层

**`EnemyTurnBegan` 退役,新增 `ActorActed(kind, index)`** 作为每个行动者的段首标记。
现行的 `EnemyTurnBegan` 语义是「一整个事件流里恰好一条」(`BattleEngineTests.cs:959` 硬断言),
逐格模型下已无意义。

`Juice.PlayRoutine`(`Juice.cs:60-85`)里那段「preRest / strikes / postRest」三段切分
**整段删除**。它现在靠 `SummonAttack` 与 `EnemyTurnBegan` 猜边界,注释里记着已经因为
「焦痕的加攻断段」翻过一次车。逐格之后每批事件天生属于一个行动者,`PhaseGap` 的停顿
改由外层循环控制。

`BattleView.OnEndTurn` 改为协程循环:

```csharp
Battle.YieldTurn();
while (Battle.AdvanceOnce())
{
    HighlightActor(Battle.LastActor);                 // 行动条上那一格亮起
    yield return _juice.PlayFor(Battle.LastEvents);   // 只播这一个单位的事件
    if (Battle.Phase is Won or Lost) break;
}
```

**TAB 行动条**:顶部横条,横向排一行小字形,最左是当前行动者(放大 + 高亮),往右是
`Forecast` 出的 6~8 拍。冻结格置灰带冰角标。竖屏宽度够放 8 格,不挤战场。

### 4.5 语义重定义与存档

| 概念 | 现在 | 改后 |
|---|---|---|
| `Turn` | 全局回合数 | **玩家行动次数**(UI「回合 N」文案不变) |
| Boss 蓄力 `BossChargeEvery = 2` | 阶段内第 N 个敌方回合 | 该 Boss **自己的行动次数**(同速下等价) |
| `MaxActionsPerTurn = 2` | 单回合行动封顶 | 删除(口径 9) |

存档:

| 快照 | 改动 |
|---|---|
| `BattleSnapshot` | **加** `PlayerActionMeter` |
| `EnemySnapshot` / `SummonSnapshot` | 已有 `ActionMeter`,不动 |
| `BattleConfig` | **加** `PlayerSpeed = 100`。战斗中永不被写(同 `PlayerDefense`/`PlayerDodge`),局内增减全走 `StatusKind.SpeedModifier` |

调度器本身不需要额外快照字段:连续推进模型的全部状态就是各单位的 `ActionMeter`,已在快照里。

## 五 · 测试策略

TDD。本次**没有恒等性硬线**(时序归属立刻就变,基准局结果也会变),所以最大的风险是
分不清「红是因为接线错」还是「红是因为行为按设计变了」。对策是把调度器与接线拆成两个
独立可验证的东西。

### 1. `TurnScheduler` 独立单测(先行,一行不碰 `BattleEngine`)

- 同速 100 三方 → 序列 `玩家 召唤 敌 玩家 召唤 敌 …`
- 我 100 / 敌 60 → `我 敌 我 我 敌 …`
- tie-break:`召唤物 > Buff敌 > 其余敌 > 玩家`(玩家排最后),同类按下标升序
- 钳位:有效速度 0 → 按 25 走,连推 100 拍不死锁;800 → 按 400 走
- `Forecast(20)` 调用前后真实计量器逐字节不变
- 整数精度:构造一组会让浮点除产生尾数的速度值,断言序列稳定

### 2. 时序归属测试(接线的验收线)

一条归属一条测试:DOT 在自己行动前烧、状态递减在自己行动后、缺笔妖补完立刻用新攻击力打、
光环治疗在该召唤物自己那拍、冻结跳过且 −1 且不死锁、立即判负、立即判胜、
立即判负时状态递减照跑、通假两种触发路径(挨打 / 出手 / DOT)。

### 3. 旧测试逐条分类,分类结果写进实现计划留痕

| 分类 | 处理 |
|---|---|
| 断言表达的行为**按新设计确实该变** | 改断言,并在测试注释里写明「2026-08-15 CTB 改造:原为 X,现为 Y,因为 Z」 |
| 断言表达的行为**仍然应该成立** | 是缺陷,改实现不改断言 |

预计重灾区:`BattleEngineTests`(137)、`DamageVariantTests`(51)、`BurnVariantTests`(44)、
`EventTests`(42)、`StatusOpsTests`(37)、`SummonPassiveTests`(33)、`BossSkillTests`(28)。
