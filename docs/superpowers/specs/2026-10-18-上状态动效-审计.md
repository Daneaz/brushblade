## Part 1 · 现状盘点(第一轮)

### 1.1 核心结论
- Core **没有通用的「状态施加」BattleEvent**。`ApplyStatus`(`Core/BattleEngine.cs:5103`)只发内部钩子 `HookKind.StatusApplied`(:5186),表现层收不到。
- 现在「上状态」的反馈分三套:
  - **A. 专门事件 + 小飘字**:`Burn` / `SummonBurn` / `EnemyBuff` / `Shield`(以及锋芒的 `MoraleGain`)。
  - **B. 前后比对 + 重绘后「chip 闪 + 状态名签」**:`TraitCueRules.AnnouncedKinds`(`Core/TraitCueRules.cs:51`)的 12 个 kind 白名单。调用链:`BattleView.AnnounceSnapshot`/`CueNewStatuses`(`Presentation/BattleView.cs:7243/7260`)→ `FlushChipCues`(:7211)→ `Juice.FlashIcon` + `Juice.StatusLabel`。调用点:出字 :7053/7095、拆 :7422/7438、合 :7465/7479、每拍推进 :7662/7664。
  - **C. 什么都不播**:chip 在出字后的重绘里静默出现(出字路径先重绘再播)。

### 1.3 施加 vs 结算
- **引燃**:`BurnSettleNow`(BattleEngine.cs:4114)→ `SettleBurnOn` 发 `BurnTick`(:5001)。Juice.cs:446 播伤害数字 + `FlameBurst`(火星粒子)+ `HitFx`(震屏 / 打击音 / 闪光)。这是「灼结算」的动效,不是「上灼」的动效。
- **出字上灼**:只有 small 号「灼+N」,又和伤害飘字挤在同一帧,所以看起来等于没有。

### 1.4 叠层
- 灼:每次 gain>0 都发 `Burn`,叠层照样飘字;顶到上限 gain=0,不飘。
- B 类:只比较「有没有」,刷新和叠层都不触发。
- 战意(锋芒以外)、厚、泉、格挡等叠层:完全没有动效。

### 1.5 最通用的现成动效
`Juice.StatusLabel(kind, mag, struck, carrier, isPlayer)`(JuiceTriggerFx.cs:111),配合 `FlashIcon(root, iconKey)`(JuiceWood.cs:46):
- chip 闪 0.45s:放大到 1.4、偏白、外圈白描环 + 赭金发光。
- 状态名签:chip 底色 + 图标 + 白色粗体名,1.3s 内上浮后淡出。
- 名称 / 图标 / 底色取自 `StatusText.Of` 和 `BattleView.BattleChipColor`,所有可见 kind 通用。

### §2 `ApplyStatus` 本身
- **签名**:`private bool ApplyStatus(StatusBag bag, StatusEffect effect, UnitRef target, UnitRef applier, bool raiseHook = true, int extraStallPush = 0)`(BattleEngine.cs:5103)。
- **调用方**:约 71 处(BattleEngine.cs 48、Fire 7、Wood 5、Metal 4、Water 4、Earth 3)。
- **能拿到的信息**:
  - 目标:`target`(UnitRef,`.Side` 为 Enemy / Player / Summon,`.Index` 为敌人下标或木灵槽位)。
  - 施加者:`applier`。
  - 最终总量:`effect.Magnitude`(已合并、已钳位)。
- **拿不到的**:本次增量没有现成值。需要在 `bag.Apply` 前后各取一次 `bag.TotalMagnitude(kind)` 相减;Burn 可以直接取 `bag.Find(Burn)?.Magnitude`。
- **合并 / 刷新(增量可能为 0)**:
  - 减速:取最强 + 最长(:5136-5144)。
  - 流血:`MergeBleed`,量取大、回合取长。
  - 燃意:`MergeKindle`。
  - 格挡:次数 / 反击取大,不累加。
  - 灼:钳到 `CombatCaps.BurnStacks`,没涨就 `raiseHook=false`(:5162-5167)。
  - 诅咒 / 种 / 标记 / 埋雷 / 致命:同源取强取长(:5169-5183)。
  - 字 ID 去重的条目被 `bag.Apply` 覆盖刷新(嘲讽、不灭、HealBlock 等)。
  - 以上情况可能出现「量没变、只刷新了回合」:钩子照发(除灼以外),而增量为 0。
- **拦截分支**:
  - 洗尽铅华:Buff 落到带 BuffBlock 的敌人身上,发 `BuffBlocked`,返回 false(:5108-5115;霜抗豁免)。
  - 免疫减益:`WardOff` 发 `DebuffWarded`,有转盾时紧跟 `Shield`(Water.cs:191-226),返回 false。
  - 冻结:已冻结 / 霜抗 / 冰滞时**静默**返回 false(:5121-5122)。
  - Boss 被冻结:改挂 IceStall,effect 被替换(:5124-5134)。
  - 被拦下时不应再发新事件(已有拦截事件)。
- **免疫(Immunity)**只挡伤害,不挡状态。

### §3 MoraleGain 的「批末飞光」
- **发出**:`FlushCritMorale`(BattleEngine.cs:1068),Source=`CritMorale`,TargetIndex = 暴击落点敌人,Amount = 实际涨的层数。
- **播放**:Juice.cs:823 把它推进 `deferred`,在整批末尾由 `PlayDeferredProc`(Juice.cs:873-886)播放:金光 `FlyOrb` 从暴击落点飞回玩家 → 停一拍(`ProcFlyDuration`)→ 飘「锋芒 战意+N」(金字形色)→ 玩家处 `RingAt` 金环 + `Sparks` + 高音「叮」→ `StepGap`。
- **建议**:保留,它是「特性来源」的演出。新事件落地后的共存方式二选一:
  - (a) Core 对锋芒这条增量不发新事件(锋芒已经有 MoraleGain);
  - (b) Presentation 在同一批里看到 `MoraleGain` 时,跳过对应玩家 Morale 的新事件,或把飞光落点那一下换成「战意 chip 闪 + 名签 +N」,避免出现两个 +N。
  - 推荐 (b)。Core 口径统一为「凡增量都发」,表现层负责去重。

### §4 对 trace / 恒等测试 / Estimate 的影响
- **Identity fingerprint 测试**:会把 `LastEvents` 逐条串进哈希(例如 `FreezeEndIdentityTests.cs:61`,格式 `{Kind}:{TargetIndex}:{Amount}:{SecondIndex}:{Absorbed}:{Source};`)。新增事件会让所有覆盖到施加状态的场景**换基线**。涉及 15 个文件:
  - CounterRefactorIdentityTests、E3CoreIdentityTests、E4CoreIdentityTests、FreezeEndIdentityTests、EarthEnemyIdentityTests、EarthHitIdentityTests
  - EarthTurnShieldIdentityTests、WardIdentityTests、RetaliateBeatEndTests、PlayerHitHookIdentityTests、SummonReplaceTests
  - WoodAuraIdentityTests、WoodHitDeathIdentityTests、WoodRosterIdentityTests、WoodSharedIdentityTests
  - 这类测试本意是「改前改后恒等」,新增事件属于刻意改事件流。按「恒等性硬线」的纪律,应拆成两步:先接线(事件存在,哈希重算并在提交里说明),再接表现。另一种做法是让 fingerprint 过滤掉新 Kind,保住旧基线不动。**推荐过滤**:改动最小,恒等对照的仍是旧语义。
- **按位置断言的测试(会坏)**:
  - `BattleEngineTests.cs:1083-1086`:要求召唤段严格是「SummonAttack, Damage, EnemyBuff」三连。焦痕的 AttackBuff 走 ApplyStatus,新事件会插进来。
  - `FireBurnOpsTests.cs:296`:`evs[k+1]` 必须是 Burn。如果新事件在 ApplyStatus 内发出、早于调用方的 `Burn`,就会插在中间。
  - `InfoHidingTests.cs:142`:Damage 后紧跟 EnemyDied。施加发生在伤害之后、死亡之前就会坏。
  - `E3CoreEventTests.cs:89`:断言 `[DebuffWarded, Shield]` 整序列。拦截分支不发,安全。
  - `GlyphTraitTests.cs:296`:断言只有 `[GlyphTrait]`。印记是 TraitRider(隐藏),只要隐藏载体不发就安全。
  - `E4CoreTests.cs:61/75`(`ev[hit+1]` 为 EndureSaved):不涉及施加,安全。
  - 另有约 78 处 `LastEvents.Count(e => e.Kind == X)` 按 Kind 计数,只数自己那一种,不受影响。
- **规避建议**:
  - 已有专门事件的(Burn / SummonBurn / EnemyBuff)不重复发新事件,由表现层把它们路由到同一套动效。这样上面三条按位置的断言基本都能保住。
  - 或者新事件统一追加在调用方事件**之后**。
- **tools/trace**:`TraceRecorder.cs:76` 把每条事件写成一行 `E ...`。新增 Kind 会让 trace 与 `out/baseline*.txt` 逐行比较时出 diff,需要重跑 baseline,或在 `TraceCompare` 里忽略新 Kind。
- **Estimate**:影子引擎的事件只在 `EstimateCast` 内部按 Kind 用 switch 汇总(Estimate.cs:134-180)。未知 Kind 直接落空,不影响签上的数字;影子事件也不会进 `LastEvents`(本体一个字节都不动,:104)。**不需要额外屏蔽**。如果想在影子里省掉开销,可以用 `IsEstimateShadow`(:63)短路。
- **钩子总线**:`HookKind.StatusApplied` 不受影响。新 BattleEvent 不应替代钩子,特性运行时依赖钩子。

### §5 隐藏载体清单(不该播)
- **`StatusText.Of` 没有对应 case**(名为空,`StatusLabel` 本来就会返回 null):
  - `ObsoleteDamageReduction`、`TraitRider`、`ShieldRecoil`
  - `BurnGrow`、`BurnHold`、`BurnBurstMark`、`BurnBacklashMark`
  - `ApRefund`、`MoraleArmor`、`MoraleShield`
  - `FrostBite`、`ThawStrike`、`ThawSlow`
  - `ShieldFrost`、`ShieldShatter`
- **可见但需要特殊处理**:
  - `ApBoost`:有名字、没有 chip,反馈是 AP 格数。建议不播,或只飘名签。
  - `SummonRanged`:没有独立 chip,而是换掉攻 chip 的射程图标;现在由 `CueNewAuras` 闪 "ranged"。
  - `FrostResist`:冻结结束时自动挂上,是结算产物,建议不播。
  - `Seal` 的 Buff 极性变体(杜门不出代价):描边 chip。
- **建议做法**:Core 侧用一个白名单(或 `StatusRules.IsHidden`)统一过滤,再加一条对账测试,保证「`StatusText.Of` 返回空名的 kind 一律不发」。

## 建议的统一方案(用户已认可)
1. **Core**:新增 `BattleEventKind.StatusApplied`,只能在末尾追加。
   - 字段:TargetIndex = 敌人下标 / 木灵槽位,玩家为 -1;SecondIndex = 阵营;Amount = (int)Kind;Absorbed = 增量。
   - 发射点:ApplyStatus 成功分支,加上 §1 的 4 处旁路。
   - 不发的情形:隐藏载体、被拦截、已有专门事件(Burn / SummonBurn / EnemyBuff)。
   - 锋芒按 §3(b) 由表现层去重。
   - 增量为 0 的刷新是否「小一档」播,由设计决定。
2. **Presentation**:Juice 里统一播「chip 闪 + `StatusLabel`」;带量状态(灼、战意、厚、泉、格挡、流血)名签后接「+N」;叠层播小一档。Burn / EnemyBuff 的现有 case 改走同一套。
3. **下线**:`CueNewStatuses` / `AnnouncedKinds` 前后比对、`CueNewAuras`(可选)、三处手动 `ChipCue`。
4. **测试**:fingerprint 过滤新 Kind,或在两步提交里换基线;补上 §4 三条按位置断言的处理;重跑 trace baseline。
5. **工序**:先请 `designer` 出稿;Presentation 改完跑 prescompile;Core 改公开枚举后,balance / chestsim / trace 都要 build。
6. **顺手修**:桂全场木灵加盾(BattleEngine.cs:4734)不发 `Shield` 事件。
