# 统一状态容器与行动计量器 · 设计规格

> 2026-08-04 · P1~P3 机制落地的**子项目 0(地基)**
> 后续子项目:B 承伤与护甲 → C 召唤物被动 → A 状态操作 → D 伤害变体 → E 杂项

## 一 · 背景

`技能机制详表.md` 里有 **43 个字、24 种机制**尚未落地。按引擎子系统分组后是 5 个彼此独立的子项目,
本 spec 只做地基那一个。

P0 的 spec(`2026-08-03-技能机制P0-design.md` §4)当时写下:

> **状态存储逐字段加**(不引通用状态容器 —— 这些状态语义异构……
> 等 P1~P3 状态涨到十几种时再重构)

现在到了那个点。子项目 A(`Dispel`/`Cleanse`/`Immunity`/`Silence`,11 字)**全部依赖**「能枚举状态并按增益/减益分类」,
而当前 12 个状态载体散在 `EnemyState` 与 `BattleEngine` 两处,逐字段写下去就是一长串 if。

### 1.1 两个会让子项目 A 落空的现状

调查发现,当前引擎里 `Dispel` 与 `Cleanse` **无事可做**:

| 机制 | 现状 |
|---|---|
| `Dispel`(削增益) | 敌人的增益只有加攻,且是 `enemy.Attack += N` **直接写死进字段** —— 没留下「谁给的、加了多少」,**无法还原** |
| `Cleanse`(清减益) | 玩家**没有任何持续减益**。唯一负面效果 `_apPenaltyNextTurn` 是一次性的,不是状态 |

故本 spec 把「加攻可追溯」纳入地基范围。玩家减益留待 D/E 引入(`Blind`/`HealReduction` 等)。

## 二 · 范围

### 做

| 块 | 内容 |
|---|---|
| 1 | 统一状态容器 `StatusEffect` + 极性分类,迁移现有 7 种状态 |
| 2 | 行动计量器(速度),`Slow` 迁为 `SpeedModifier` |
| 3 | 标点小妖 / 焦痕的加攻改为可驱散的 `AttackBuff` |
| 4 | 快照结构随之迁移 |

### 不做

- **不新增任何字**。43 字属于后续子项目。
- **不实现 `Dispel`/`Cleanse`**。本 spec 只备好它们所需的枚举与分类能力。
- **玩家减益**:等 D/E 引入具体机制时再加。
- **缺笔妖的成长不改**(见口径 5)。

## 三 · 已定口径

| # | 口径 | 理由 |
|---|---|---|
| 1 | 容器只装「有极性、有时限、有来源、可被清除」的状态 | 护盾/计量器/全局系数不是状态,进来会让抽象被特例污染 |
| 2 | 速度叠加用**加法** | 乘法让重度减速无限趋近却打不满,表达不了完全停滞 |
| 3 | `Freeze` 期间**不累积**计量器 | 保持现有「节拍原地暂停」语义 |
| 4 | 单回合行动次数**封顶 2**,超出部分计量器清零 | Speed 500 一回合打 5 次既难看也难平衡 |
| 5 | 缺笔妖补全**保持直接改 `Attack`** | 那是形态变化不是增益,驱散它讲不通;且 `×2` 是乘法,塞进加法增益要靠等效换算,平白失真 |
| 6 | 速度只作用于**敌人与召唤物**,玩家仍是 AP 制 | 玩家的行动预算是 AP,两套模型不混用 |

## 四 · 分步设计

### 第 1 步 · 状态容器

```csharp
public enum StatusKind
{
    Burn, Bleed, Freeze, SpeedModifier,      // 减益(当前都作用于敌人)
    HealOverTime, DamageReduction, AttackBuff // 增益
}

public enum StatusPolarity { Buff, Debuff }

public sealed class StatusEffect
{
    public StatusKind Kind { get; set; }
    public StatusPolarity Polarity { get; set; }
    // 量值,按 Kind 解读:Burn=层数、Bleed/HoT=每回合量、
    // DamageReduction=百分比、SpeedModifier=速度点数、AttackBuff=攻击加成
    public int Magnitude { get; set; }
    public int TurnsLeft { get; set; }   // -1 = 段内持久(减伤)
    public string SourceId { get; set; } // 字 ID:减伤按此去重、驱散按此追溯
    public bool TargetAll { get; set; }  // 仅 HealOverTime 用
}
```

持有方两处,都是 `List<StatusEffect>`:`EnemyState.Statuses`、`BattleEngine._playerStatuses`。

**迁移映射**:

| 现状 | 迁为 |
|---|---|
| `EnemyState.Burn`(层数) | `Burn`,`Magnitude` = 层数 |
| `EnemyState.Bleed` + `BleedTurns` | `Bleed`,`Magnitude` = 每回合伤害,`TurnsLeft` = 剩余回合 |
| `EnemyState.FreezeTurns` | `Freeze`,`TurnsLeft` = 剩余回合 |
| `EnemyState.SlowTurns` + `SlowActs` | `SpeedModifier`,`Magnitude` = −50,`TurnsLeft` = 剩余回合 |
| `BattleEngine._hots` | `HealOverTime`,三元组拆入 `Magnitude`/`TurnsLeft`/`TargetAll` |
| `BattleEngine._damageReductions` | `DamageReduction`,`Magnitude` = 百分比,`SourceId` = 字 ID,`TurnsLeft` = −1 |

`DamageReduction` 的「同字不叠、乘法叠加」靠 `SourceId` 去重实现 —— 与现在的
`Dictionary<字ID,百分比>` 是同一语义,只换载体。

**不进容器的三样**:

| 留在外面 | 为什么 |
|---|---|
| `Shield`(`_shieldNormal`/`_shieldPersist`) | 是**资源**不是状态:有独立吸伤顺序与跨段规则,Cleanse/Dispel 本就不该碰 |
| `ActionMeter` | 单位固有字段,像 Hp;进容器的是修改它的 `SpeedModifier` |
| `_burnPerStack` | 全局系数(炽抬高),不属于任何单位 |

### 第 2 步 · 行动计量器

`EnemyState` 与 `SummonState` 各加两个字段:

```csharp
public int Speed { get; internal set; } = 100;      // 基准 100
public int ActionMeter { get; internal set; }       // 累积;每满 100 行动一次
```

**有效速度** = `Speed + 所有 SpeedModifier 的 Magnitude 之和`,下限 0。

⚠ 基数是单位自己的 `Speed` 字段而**不是**常量 100 —— 现在所有单位都是 100,但将来若出现天生快/慢的字怪,
写死 100 会让它们的 `SpeedModifier` 算错。`Magnitude` 是**绝对点数**(−50 表示减 50 点),不是百分比,
避免「基数不同则同一个减速效果不同」的隐式耦合。

`EndTurn` 的敌方行动段改为:

```
若 Freeze 生效 → 不累积、不行动(节拍暂停)
否则:
    ActionMeter += 有效 Speed
    actions = min(ActionMeter / 100, 2)   // 口径 4 封顶
    ActionMeter -= actions * 100
    若 ActionMeter >= 100 → ActionMeter = 0   // 封顶后不留到下回合
    行动 actions 次
```

**等价性**:`SlowActs` 初值 `false` ⇔ 计量器从 0 起。Speed 50 时第一回合累积 50 不足 100 → 跳过;
第二回合到 100 → 行动。与现有「跳一回合、动一回合」逐拍一致。

对照表:

| 有效 Speed | 效果 |
|---|---|
| 100 | 每回合 1 次(默认) |
| 50 | 每 2 回合 1 次(= 旧 `Slow`) |
| 25 | 每 4 回合 1 次 |
| 200 | 每回合 2 次 |
| 150 | 每 2 回合 3 次 |
| 300+ | 每回合 2 次(封顶) |

现有的 `SlowTurns` / `SlowActs` 字段与 `slowSkip[]` 预处理数组一并删除。

### 第 3 步 · 加攻改为可驱散

`enemy.Attack` 改为 `BaseAttack + 所有 AttackBuff 的 Magnitude 之和`。

| 位置 | 来源 | 处理 |
|---|---|---|
| `BattleEngine.cs:599` | 标点小妖给同伴加攻 | → `AttackBuff`,可驱散 |
| `BattleEngine.cs:881` | 焦痕受击自燃(`ScorchGain`) | → `AttackBuff`,可驱散 |
| `BattleEngine.cs:660` `:666` | 缺笔妖补全 `+2` / 满进度 `×2` | **不改**(口径 5) |

### 第 4 步 · 快照迁移

破坏性变更;v0.7 无线上存档需兼容。

| 快照 | 删 | 加 |
|---|---|---|
| `EnemySnapshot` | `Burn`、`Bleed`、`BleedTurns`、`FreezeTurns`、`SlowTurns`、`SlowActs` | `Statuses`、`ActionMeter`、`BaseAttack` |
| `BattleSnapshot` | `Hots`、`DamageReductions` | `PlayerStatuses` |
| `SummonSnapshot` | — | `ActionMeter` |
| `RunSnapshot` | `CarriedDamageReductions` | `CarriedStatuses`(跨战斗持久的增益) |

`HotSnapshot` 随 `_hots` 一起删除,并入 `StatusEffect` 的序列化。

## 五 · 测试策略

TDD。三组:

**1. 等价性证明(最重要)**
现有 **558 条必须全绿**,尤其那 26 条 P0 新机制测试(`Bleed_*`/`Freeze_*`/`Slow_*`/`HealOverTime_*`/
`DamageReduction_*`)。这是「纯搬迁不改行为」的唯一凭据。**不允许为迁就重构而修改这些断言** ——
断言变了就说明行为变了,那是缺陷不是适配。

**2. 速度新行为**
- Speed 50 与旧 `Slow` 逐拍一致(跳、动、跳、动)
- Speed 200 一回合行动两次
- Speed 300 被封顶到 2 次,且计量器不留余额到下回合
- `Freeze` 期间不累积,解冻后从原节拍继续
- 多个 `SpeedModifier` 加法叠加(−50 与 −25 → 有效 Speed 25)

**3. 为子项目 A 铺的路**
- `AttackBuff` 可按 `Polarity` 枚举
- 移除 `AttackBuff` 后攻击力还原到 `BaseAttack`
- 缺笔妖的成长**不**出现在可驱散列表里(口径 5 的守卫)

**4. 快照往返**
新结构的 `Capture`/`Restore` 全字段往返,含跨战斗携带的增益。

## 六 · 风险

| # | 风险 | 应对 |
|---|---|---|
| 1 | 本子项目会碰 `BattleEngine` 几乎所有结算路径(`EndTurn` 六段顺序、`Cast` 施加、快照往返),是本轮风险最高的重构 | 纯内部改造,外部行为由 558 条测试钉住 |
| 2 | 「一回合行动多次」是全新战斗节奏 | 当前无字提供加速,该路径暂不会在实战触发;等 C 的 `SummonHaste` 才启用 |
| 3 | 状态从值类型字段变为引用对象列表,可能引入别名共享 bug(快照恢复时两个单位共享同一条目) | `Capture`/`Restore` 深拷贝;加往返测试 |
| 4 | `Attack` 由字段变为计算属性,热路径上每次读取都要遍历状态列表 | 战斗规模是个位数单位、状态个位数条目,可忽略;若实测有问题再缓存 |

## 七 · 验收标准

1. `coretests` **558 条全绿且断言未被修改**,`prescompile` 无 `error CS`
2. 新增测试覆盖速度五种情形与驱散三项
3. 快照往返无字段丢失(含跨战斗携带)
4. `EnemyState` / `BattleEngine` 中不再有 `Burn`/`Bleed`/`BleedTurns`/`FreezeTurns`/`SlowTurns`/
   `SlowActs`/`_hots`/`_damageReductions` 这些独立状态字段
