本文不为此加任何补偿机制;日后若要补,补在 L1 上而不是把 L2 改回去。

## 2 · 五条机制的规格

数值一律走 `PerkNodeDef.Value` → `PerkRules.ElementBonus` → `BattleConfig` 字段,
**缺省 0 = 关**。五个字段全 0 时引擎行为与改前逐字节相同(§4)。

### 2.1 水脉 L2 · 溢流

**效果**:一次治疗中,每个受治疗单位各自算出自己的溢出量;每个溢出量 > 0 的单位
**各自**按 `溢出量 × OverhealDamagePercent / 100` 对**各自独立随机**的一个存活敌人
造成伤害。

**溢出量的定义**:`名义治疗量 − 实际回血量`。名义值是已经吃过泉放大之后的值
(`AmplifyByWellspring` 的输出),不是字表基础值。

**伤害口径**:不吃生克、不吃攻击力缩放、不能暴击、不吃敌人护甲——与灼烧结算同一条
口径。理由:溢出量本身已经是被攻击力和生克塑造过的治疗量,再乘一次是双重计价。

**触发范围**——「所有治疗类,光环除外」:

| 治疗来源 | 代码位置 | 触发? |
|---|---|---|
| 字的 `HealSelf` | `ApplyEffects` case `HealSelf` | ✅ |
| 字的 `HealAll` | `ApplyEffects` case `HealAll` → `HealPlayerAndSummons` | ✅ 玩家与每只召唤物各自算 |
| 持续治疗每回合的跳(单体) | `SettlePlayerHots` → `HealAlly` | ✅ |
| 持续治疗每回合的跳(全体) | `SettlePlayerHots` → `HealPlayerAndSummons` | ✅ |
| 召唤物自愈(藻,`Regen`) | `ActSummonTurn` → `HealAlly(s, regen)` | ✅ |
| **召唤物光环治疗**(`HealAlly` 被动) | `ActSummonTurn:1780` → `HealPlayerAndSummons(heal)` | ❌ **排除** |
| 木脉 L2「归根」 | 本文 §2.4 | ✅ |
| 复活(`Revive`) | `ApplyEffects` case `Revive` | **不涉及** |

复活直接写 `revived.Hp = (revived.MaxHp + 1) / 2`,既不走治疗入口、也**永不溢出**,
因此不需要为它写任何分支或测试断言 —— 但要在实现里留一句注释说明为什么它不在表里,
否则下一个人会以为是漏了。

**实现要点**:`HealPlayerAndSummons` 与 `HealAlly` 各加一个 `bool overflowToDamage = true`
参数;唯一传 `false` 的调用点是 `ActSummonTurn` 的光环那一行。默认 true 而不是默认
false,是因为「排除」只有一处,把默认值定在多数那边能让日后新增的治疗来源自动接上。

⚠ `HealPlayerAndSummons` 现在对召唤物只写 `summon.Hp = Math.Min(...)`,不算溢出量。
要改成先算 `over = amount - (summon.MaxHp - summon.Hp)`(下钳 0)再写。

**读数**:满场(玩家 + 6 只召唤物)群治时最多 7 次独立结算、7 条 `Damage` 事件。
这是用户在两案之间明确选的那一案(另一案是求和后打一下),不要在实现里"顺手优化"
成合并一次。

### 2.2 火脉 L2 · 余烬

**效果**:敌人死亡时,把它身上剩余的灼烧层数按 `BurnSpreadPercent / 100`(默认 100,
即全额)转给一个随机存活敌人。转移是**叠加**到目标已有层数上,遵循既有 `ApplyBurn`
的累加语义与 `MoraleCap` 无关的层数规则。

**钩子**:`BattleEngine.ResolveDefeat(int enemyIndex)` —— 它是灼烧结算致死、流血致死、
引爆致死、斩杀、普通伤害致死**五条路径唯一的汇流点**(`ResolveDefeat` 的 5 个调用点
已核对)。写在这里就自动覆盖「玩家打死」「召唤物打死」「DOT 烧死」全部情形,这正是
用户对原方案的扩展要求。

**引爆的自洽性**:`Detonate` 分支在调 `ResolveDefeat` **之前**已经
`enemy.Statuses.Remove(StatusKind.Burn)`,所以引爆致死时没有层数可蔓延。这是**正确**
的——那些层数的伤害已经一次性兑现过了,再蔓延等于收两遍钱。实现时不要"修"它。

**灼烧结算致死**:`SettleBurnOn` 先 `burn.Magnitude -= 1` 再判死,所以蔓延出去的是
**已减 1 之后**的剩余层数。同样是正确的——那一层刚刚结算过。

**无目标时**:场上没有其他存活敌人则静默丢弃层数,不报错、不发事件。

### 2.3 金脉 L2 · 锋芒

**效果**:玩家的攻击暴击时,战意 +`MoraleOnCrit` 层(默认 1),上限仍是
`BattleConfig.MoraleCap`(5,金脉 L4 抬到 7)。

**每张字至多 +1 层** ⚠。`ApplyEffects` 顶部置 `_critMoraleGrantedThisCast = false`,
`RollCrit()` 里首次摇到暴击时兑现并置 true。理由:`DamageAll` 分支对每个目标各摇一次
暴击(`BattleEngine.cs:2328` 的 `crit: RollCrit()` 在 `for` 里),不加这条限制的话
一张群攻字暴击 5 个目标就能顶满上限,战意从「维持型资源」退化成「开局一张群攻就满」。

**召唤物的暴击不算**:只改 `RollCrit()`,`RollCritForSummon()` 一字不动。召唤物有自己
的暴击袋子(`summon.Statuses` 的 `CritBuff`),让它也涨玩家战意会让木+金 build 白拿双份。

**已核对的 `RollCrit()` 调用点**(全部在 `ApplyEffects` 的调用链内,故 per-cast 标志
覆盖完整):`BattleEngine.cs:2306`(`DamageSingle` 多段)、`:2328`(`DamageAll`)、
`:2904`(`SpendResource`,即厚积薄发/涌泉相报)。实现时要重新 grep 一遍确认没有新增。

**战意首回合宽限**:`AddPlayerCounter` 在「从 0 新建」那一支置 `_moraleGraceTurn`。
锋芒复用 `AddPlayerCounter(StatusKind.Morale, n, cap)`,因此自动继承这条既有行为 ——
不要绕开它直接改 `Magnitude`。

### 2.4 木脉 L2 · 归根

**效果**:召唤物阵亡时,玩家回复 `summon.MaxHp × SummonDeathHealPercent / 100`
(默认 20%)。

**是一次完整治疗**(用户 2026-09-13 裁定):吃泉放大(`AmplifyByWellspring`)、攒泉
(`GainWellspring`,按放大前的基数,与 `HealSelf` 同口径)、也吃水脉 L2 的溢流转伤害。
即走 `HealAlly(Targeting.PlayerTarget, amplified)`,不另开通路。

**钩子**:召唤物死亡目前**没有**统一汇流点,散在两处,且两处都已经在调
`RefreshSummonAura()`:

- `SettleSummonBurn`(`BattleEngine.cs:1810`)—— 自焚死亡
- `DamageSummon`(`BattleEngine.cs:3749`)—— 挨打死亡

抽一个 `private void OnSummonDeath(int slot)`,内容 = 归根治疗 + `RefreshSummonAura()`,
把两处的 `RefreshSummonAura()` 调用替换掉。这个抽取本身是必要的(不是顺手重构):
没有汇流点就必然要在两处各写一份同样的治疗逻辑,而这一层最常见的静默 bug 就是
「同一份逻辑两条路径,只改了其中一条」。

⚠ 顺序:先治疗,后 `RefreshSummonAura()`。治疗可能触发溢流打死敌人,而光环刷新读的是
召唤物存活集合,与敌人无关 —— 两种顺序结果相同,但固定成「治疗在前」以便测试可断言。

**复活后再死亡照常触发** —— 每一次真实死亡都算一次,不去重。

### 2.5 土脉 L2 · 反震

**效果**:玩家受到伤害时,被护盾吸掉的部分按 `ShieldReflectPercent / 100`(默认 20%)
反弹给攻击者。

**钩子**:`DamagePlayerDirect`(`BattleEngine.cs:3654-3657`)已经算出了
`absorbed = fromNormal + fromPersist`,直接用。

**结算形状**照抄既有「镜」那一段:

```csharp
DamageEnemy(enemyIndex, bounced, Element.Heart,
    bypassDefense: true,    // 折返不是挥击,不吃敌人护甲
    allowBarb: false);      // 同理不算挥击,不触发铁画的反噬
```

守卫也照抄:`_enemies[enemyIndex].Alive` 才反。

**不并入「镜」的 60% 总量钳**(`MaxReflectPercent`)。理由:镜按*打过来的总伤害*折返,
反震按*被护盾吸掉的量*折返,**基数不同,不能并轴**。反震自己被护盾存量天然限制住
(吸不了就反不了),不需要另设上限。两者同时生效时各算各的、分别发一次 `DamageEnemy`。

**位置**:排在既有反弹那一段**之后**,共用同一个 `_enemies[enemyIndex].Alive` 语境。
`allowReflect == false` 的那条路径(铁画反噬)**同样不触发反震** —— 那一记本就不是
敌人的挥击,反震跟着 `allowReflect` 一起 gate。

## 4 · 恒等性硬线

**五个 config 字段全为 0 时,引擎行为必须与改前逐字节相同。** 这条不是"最好如此",
是验收条件——既有 1700 余条测试里有大量依赖固定种子的断言。

具体到每条:

| 机制 | 关闭时必须做到 |
|---|---|
| 溢流 | `HealPlayerAndSummons` / `HealAlly` 不多算一个除法、不发额外事件 |
| 余烬 | `ResolveDefeat` 仍然只有 `_events.Add(EnemyDied)` 一句的效果 |
| 锋芒 | `RollCrit()` 仍然只是 `RollCritWith(EffectiveCrit)` |
| 归根 | `OnSummonDeath` 退化成一句 `RefreshSummonAura()` |
| 反震 | `DamagePlayerDirect` 不多一次 `DamageEnemy` |

⚠ **最危险的一条是随机流**。溢流与余烬都要摇随机数选目标。`GameRandom` 的既有消费方
只有三处(`StartTurn` 的回合掉字、`AttackHits`、`EnemyState` 构造时的 Boss 阈值浮动),
**多摇一次就会平移整条随机序列**,让所有依赖种子的既有测试一起变红。

所以两处都必须**先判开关、再判有没有可打的目标,最后才摇**:

```csharp
if (_config?.OverhealDamagePercent is not > 0) return;   // 关 → 一次随机都不摇
if (overflow <= 0) return;
int dmg = overflow * _config.OverhealDamagePercent / 100;
if (dmg <= 0) return;                                    // 截断成 0 也不摇
int target = PickRandomLivingEnemy();
if (target < 0) return;
```

顺序不能换。`PickRandomLivingEnemy` 从 `FreezeRandomLivingEnemy`
(`BattleEngine.cs:2857`)里抽出来共用,那份实现已经是正确的惯用法
(收集存活下标 → `_random.Next(list.Count)`)。

## 8 · 未决与风险

- **五行 L3/L4 覆盖率**:见 §1.2。已知、已拍板、本次不补。
- **溢流的数值量级未经仿真**:50% 是拍脑袋的起点。水系满泉时治疗量放大 50%~70%,
  满血状态下溢出可能相当可观。上线后要用 `tools/design` 的仿真跑一轮再定。
- **余烬在单 Boss 战完全无效**:这是机制的形状决定的(要有第二个目标才蔓延),
  不是缺陷。若日后觉得水脉/火脉强度失衡,调的是 `BurnSpreadPercent`,不是加特例。
- **反震与「镜」叠加的天花板**:两者都满时理论上可以把一记重击反出很高的总量。
  护盾存量是天然限制,但没有实测读数。同样留给仿真。
- **锋芒让同一张群攻字的后续目标多吃 10% 攻击**(全分支终审复核,2026-09-13,不改代码):
  `DamageAll` 那句 `DamageEnemy(i, ScaleByAttack(...), attacker, crit: RollCrit(), pierce: ...)`
  里,C# 按书写顺序求值参数——目标 i 的伤害数值先算完,`RollCrit()` 才摇;摇中暴击
  会经 `GrantMoraleFromCrit()` **立刻**给玩家加一层战意,而战意通过 `AttackPercent`
  实时抬高 `EffectiveAttack`。于是「目标 0 摇中暴击」会让**目标 1**(同一张群攻字、
  同一次结算)吃到多出的攻击力加成,目标 0 自己吃不到——伤害是先算数值后摇骰,战意
  本来就是「摇中即生效」的即时资源,这是没人特意选择过、但也说不上错的涌现,不是 bug。
  日后如果要消掉它:在 `ApplyEffects` 里把这一拍摇到的暴击只记一个标志位(不立刻调
  `AddPlayerCounter`),等整张字的 `for` 循环结算完、所有目标的伤害都已经算完数值之后,
  再统一调一次 `AddPlayerCounter` 兑现战意——这样任何一个目标暴击都不会污染同一次
  结算里其他目标的伤害。本次不改,理由是改动面会牵动 `ApplyEffects` 的暴击兑现时机,
  而单张群攻字的这点误差对整体强度可忽略。
