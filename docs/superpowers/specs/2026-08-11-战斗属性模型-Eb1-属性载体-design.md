# E-b1 属性载体 设计

> 战斗属性模型五步拆分的第 1 步。父项目:把玩家从「字牌数值即伤害」改造成持有真实属性的战斗实体,
> 为 Buff 组 6 字(剡 锋 锐 战 利 戮)铺地基。

**日期**:2026-08-11
**上游**:用户裁定「真属性制 + 全面重新平衡」「不加 MATK/MDEF,五行就是类型轴」
**下游**:E-b2 暴击 → E-b3 Buff 组 5 字 → E-b4 命中/闪避/防御改造(含 锐)→ E-b5 全面重新平衡

---

## 一 · 为什么先做这一步

Buff 组 6 字卡在「玩家没有攻击力」这件事上:`剡`(本场攻击 +50%)、`战`/`戮`(战意每层 +10% 攻击力)
都需要一个能被放大的攻击属性,而今天**字牌的数值直接就是伤害**,没有任何中间量。

父项目的四个部分——属性载体、暴击、防御改造、重新平衡——如果一起做,
「引入属性」和「重算数值」会在同一批提交里炸开:任何一条测试变红都分不清是公式错了还是数值调了。
所以拆开,并且**把机械迁移与数值重平衡严格分离**:E-b1 只搬管道,一个数字都不改。

## 三 · ATK 的语义

**ATK 放大「你造成的伤害」。**

| 吃 ATK | 不吃 ATK |
|---|---|
| `DamageSingle` / `DamageAll` | 护盾(`Shield`) |
| 灼烧每层伤害 | 治疗(`HealSelf` / `HealAll` / `HealOverTime`) |
| 流血(`Bleed`) | 冻结 / 减速 / 致盲 / 沉默 的**回合数** |
| 召唤物攻击力 | 驱散条数、免疫次数、复活数 |
| | 灼烧**层数**(只放大每层伤害,不放大层数) |
| | `BurnPotency`(它抬的是系数本身) |
| | 反弹百分比与反弹伤害(按挨到的伤害反,不是玩家输出) |
| | 荆的反伤(召唤物被动固定值,不是攻击力) |

水系(治疗)与土系(护盾)吃不到 ATK 是**刻意的**:它们改吃 DEF/HP(E-b4 起)。
这正是多属性存在的意义——不同流派堆不同属性。

## 四 · 数据流

沿用生命属性今天已有的链路(`MetaRules.MaxHpFor`),不发明新形状:

```
MetaState.CharacterXp
  → MetaRules.CharacterLevel(xp)              升 n+1 级需 100 + 50×(n−1) 经验(既有)
  → MetaRules.AttackFor(level)                【新】角色属性
  + <被动技能加成>                             【口子】本次恒为 0
  → BattleConfig.PlayerAttack                 【新字段】
  → BattleEngine.EffectiveAttack              = PlayerAttack + AttackBuff 状态之和
  × <进阶角色特长条件乘数>                      【口子】本次恒为 1.0
  → ScaleByAttack(v)                          → 喂进现有结算
```

### 4.1 成长曲线

```csharp
/// <summary>攻击成长:100 + 2×(等级−1),上限 150。与 MaxHpFor 同形同封顶级(26 级)。</summary>
public static int AttackFor(int level) => Math.Min(150, 100 + 2 * (level - 1));
```

| 等级 | HP | ATK | 伤害倍率 |
|---|---|---|---|
| 1 | 50 | 100 | ×1.00 |
| 11 | 70 | 120 | ×1.20 |
| 26 | 100 | 150 | ×1.50(封顶) |

叠上字卡等级的 ×1.9,满级玩家总伤害成长 ×2.85。

### 4.2 基准取 100 的理由

基准 10 时每 +1 ATK 就是 +10%,等级成长与局内增益都没法做细。取 100 后:

- 等级成长可以 +2/级这样的粒度
- 百分比与固定值可互换:`剡` 的「+50%」就是 `+50`,`战意` 的「每层 +10%」就是每层 `+10`
  ——E-b3 因此不需要额外的百分比通道,直接用固定值加法即可

## 五 · 公式与恒等性

`WuxingResolver.ResolveEffect` 今天是 `floor(base × 相生 × 相克)`。
**ATK 不进这个式子**,而是在它之前把 `base` 缩放一次:

```csharp
private int EffectiveAttack =>
    _config.PlayerAttack + _playerStatuses.TotalMagnitude(StatusKind.AttackBuff);

/// <summary>按玩家攻击力缩放一个输出值。AttackBaseline 时逐字节恒等。</summary>
private int ScaleByAttack(int value) => value * EffectiveAttack / AttackBaseline;   // 整数除
```

`AttackBaseline = 100`。`EffectiveAttack == 100` 时 `value * 100 / 100 == value`,**逐字节相同**。

> **这是 E-b1 唯一的验收硬线**:全部现有测试原封不动地绿,一条断言都不改。
> 现有 Core 战斗测试一律直接 `new BattleConfig()`,`PlayerAttack` 取默认 100,天然恒等;
> `GameRoot` 注入真实等级,1 级时 `AttackFor(1) == 100`,同样恒等。

`StatusKind.AttackBuff` 已存在(敌人侧的标点小妖加攻、焦痕自燃在用),玩家侧直接复用,
不新增枚举值。

## 六 · 生效时机

**出牌时快照**:出牌那一刻把 ATK 算进去,之后 ATK 再变不影响已落地的东西。
于是「先开增益再输出」的出牌序成为技巧。

| 结算点 | 时机 | 为什么零新增字段 |
|---|---|---|
| `DamageSingle` / `DamageAll` | 出牌时 | 缩放 `value` 后再进 `ResolveEffect` |
| 流血 | 出牌时 | `StatusEffect.Magnitude = value` 本就是施加时定死的 |
| 召唤物攻击力 | 召唤时 | `SummonState.Attack` 本就是创建时常量 |

### 6.1 灼烧是例外:结算时读,回溯生效

灼烧的每层伤害不存在状态上——它是 `BattleEngine._burnPerStack` 这个**全场全局标量**
(基准 2,`炽`/`BurnPotency` 抬它),而且**今天就已经是回溯生效的**:
`炽` 一抬,场上已挂着的层全部跟着变强。

所以灼烧沿用这个既有口径:

```csharp
int tick = (int)Math.Floor(burn.Magnitude * _burnPerStack
    * (EffectiveAttack / (double)AttackBaseline)
    * WuxingResolver.KeMultiplier(Element.Fire, enemy.Element));
```

引爆(`Detonate`)的 `N(N+1)/2 × 系数` 同口径乘上同一个倍率。

**这不是新的不一致,是沿用 `炽` 已经确立的口径。** 真做「每层快照」需要给 `StatusEffect`
加字段并拆开合并的层(`ApplyBurn` 的相加、`RefreshBurn` 的 Max、引爆的 `N(N+1)/2` 全要重写),
且与 `炽` 的回溯口径正面冲突。

> **取整口径说明**(免得被当成缺陷):直接伤害走整数除 `value * atk / 100`(早截断),
> 灼烧走浮点后 `Math.Floor`(晚截断)。两者不同**是既有代码路径决定的**——
> 灼烧今天本来就是 `Math.Floor(Magnitude * _burnPerStack * KeMultiplier(...))` 这个浮点式子,
> 把 ATK 比值插进去是改动最小、且恒等性最稳的做法;直接伤害那边则是在整数 `value`
> 进 `ResolveEffect` 之前缩放。`ATK == 100` 时两条都逐字节恒等,这才是硬线;
> 非 100 时的舍入差异是两条链路本就存在的差异,不在本项目内统一。

**已知后果**:`剡` 会回溯放大已挂满的灼烧,火系爆发链会比今天更狠
(用户已两次确认接受 258/387 那条链)。E-b5 重平衡时重新评估。

## 七 · 三个口子

本次只留形状,不实现。

| 口子 | 形状 | E-b1 的值 | 将来 |
|---|---|---|---|
| 被动技能加属性 | 加数:`AttackFor(lv) + bonus` | `0` | 「后续可能会开通被动技能增加角色属性」 |
| 进阶角色特长 | **条件乘数**:如「火系攻击 ×1.5」 | `1.0` | 19.2.2 燎原使/锋锐使等 |
| 局内增益 | 加数:`+ AttackBuff 状态` | **本次实现机制** | E-b3 的 剡/战意 |

「特长」的形状与另外两个不同——它是**按属性条件的乘数**而非加数(「火系攻击 ×1.5」)。

**这个口子不需要写任何预留代码。** 伤害链路本来就带着攻击属性——
`WuxingResolver.ResolveEffect(base, recipeElements, attacker, defender)` 的 `attacker` 就是它,
`ScaleByAttack` 的每个调用点都在这个属性可见的作用域里。将来接特长时按 `attacker` 分支即可。

刻意**不**加一个恒为 1.0 的乘数参数:那是给单次未来用途写的投机代码,
而它想守的信息(攻击属性)本来就在手边。

## 十 · 已知副作用:整数除吃掉小数值的加成

字表数值在 6~30 区间,整数除会让低数值的字在攻击成长前几十级毫无反应:

| 卡面 | ATK 102(+2%) | ATK 110(+10%) | ATK 150(+50%) |
|---|---|---|---|
| 6 伤 | 6 | 6 | 9 |
| 7 伤 | 7 | 7 | 10 |
| 20 伤 | 20 | 22 | 30 |
| 30 伤 | 30 | 33 | 45 |

这不是缺陷,是「整数伤害 + 个位数量级」的必然。

**不用 `ceil` 绕过**:`ceil(7 × 1.02) = 8` 等于 +14%,小数值反而超额收益,方向是错的。

真正的解法是抬高整个字表的数值量级(6 伤 → 60 伤),**那正是 E-b5 该做的事**
——真属性制天然要求更大的数字。E-b1 必须保持恒等,动不了量级,所以本项目内不解决。

## 十一 · 组件边界

不新建 `CombatStats` 容器。生命今天就是 `BattleConfig.PlayerMaxHp` 这样的平铺字段,
ATK 跟随同一模式加 `BattleConfig.PlayerAttack`。为一个字段造容器是给单次使用做抽象。

E-b2(暴击)与 E-b4(命中/闪避/DEF)各自再加字段后,若确实到了三四个属性并肩,
届时再抽容器——那时抽有真实依据,现在抽是猜。

涉及的文件:

### 新增测试

| 测试 | 守什么 |
|---|---|
| `AttackFor` 曲线:1 级 100、11 级 120、26 级 150、40 级仍 150 | 成长与封顶 |
| `ScaleByAttack` 恒等:ATK=100 时任意值原样返回 | **恒等性硬线** |
| ATK=150 时 `DamageSingle 20` 打出 30 | 直接伤害吃 ATK |
| ATK=150 时流血 `Magnitude` 为 1.5 倍 | 流血在**施加时**吃 ATK |
| ATK=150 时召唤物 `Attack` 为 1.5 倍 | 召唤物在**创建时**吃 ATK |
| 先挂灼烧再抬 ATK,灼烧跳动按新 ATK | 灼烧**回溯**生效 |
| 抬 ATK 后已在场的召唤物攻击力**不变** | 召唤物**不**回溯 |
| ATK=150 时护盾/治疗/冻结回合数**不变** | 负向:不该吃的没吃 |
| 快照往返后 ATK 增益仍在 | 存档兼容 |

### 变异检查(项目标准)

至少覆盖这两个方向(注意:不存在「白名单」这种数据结构,「吃不吃 ATK」纯粹取决于
**哪些结算点调了 `ScaleByAttack`**,所以变异要在调用点上做):

- **删**:把某个该吃的调用点的 `ScaleByAttack` 去掉 → 必须有测试红(正向覆盖)
- **加**:给护盾 / 治疗 / 冻结回合数任一个**加上** `ScaleByAttack` → 必须有测试红(负向覆盖)

后者尤其重要。只写正向断言的话,把护盾也乘上 ATK 不会有任何测试发现
——这是子项目 D 的白名单方向性教训,同一类漏洞在本项目里换了个形状。
