# 开场走调度 · 同速优先级反转 · 设计规格

> 2026-08-17 · **推翻** `2026-08-15-ATB回合制改造-design.md` 的 tie-break 方向
> (「并列时玩家排最后」),以及三处配套的「方向不要再调回去」注释:
> `TurnScheduler.cs:34-37`、`BattleEngine.cs:717-723`、`BattleEngine.cs:1499-1502`

## 一 · 背景

### 1.1 症状

用户报告:**战斗开场直接就是玩家行动,没有先走行动条。**

### 1.2 根因

`BattleEngine` 构造函数(`:375`):

```csharp
            Phase = BattlePhase.PlayerTurn;
            StartTurn();
```

开场**完全绕过调度器** —— 玩家拿到一次「免费先手」,而此时全场计量器都还是 0。
所以既看不到条流动,玩家也不是「攒满了才动」。

2026-08-15 的 ATB 改造把玩家纳入了调度,但**开场那一拍没纳入**;这两行是改造前 AP 制的遗留
(那时玩家先动是天经地义的)。

### 1.3 用户同时拍板的第二条

> 敌我双方默认初始速度是 100。速度相同时行动优先级为**玩家 > 召唤物 > 敌方**。

这与现行 priority(`召唤物 0 / Buff 敌 1 / 其余敌 2 / 玩家 3`,玩家**最后**)完全相反,
并且直接撞上 `TurnScheduler.cs:34-37` 的警告:

> ⚠ **玩家排最后**…曾把玩家定成优先级最小(并列必赢),结果每次推进后玩家都抢在敌人前面把
> 行动权收回去、敌人拿不到那一拍 —— 那是 2026-08-15 四轮返工的根因,三种「开局记账」
> (创建时先手 / 玩家记负债 / 消费一拍)全是在给这个反向规则打补丁。**方向不要再调回去。**

## 二 · 为什么这次可以调回去(附实测)

**那段警告描述的病,病根是「玩家优先 + 免费先手」这个组合,不是玩家优先本身。**

### 2.1 三种组合的序列推演

| 组合 | 序列 | 判定 |
|---|---|---|
| **现状**:玩家最后 + 免费先手 | 玩家(免费) → 敌 → 玩家 → 敌 … | 开场那次凭空多出来,玩家看不到条流动 |
| **只反转 tie-break**:玩家优先 + 保留免费先手 | 玩家(免费) → **玩家又动** → 敌 … | 全场同时满格时玩家必赢,敌人那一拍被抢掉 —— **正是警告描述的现象** |
| **本 spec**:玩家优先 + 去掉免费先手 | 玩家 → 召唤 → 敌 → 玩家 → 召唤 → 敌 … | 每人每轮恰好一次,**无需任何记账** |

### 2.2 实测:三种改法各自会红多少条(共 1062 条 Core 测试)

推演不足以拍板,所以三种改法各跑了一次全量测试:

| 改法 | 失败数 | 红因 |
|---|---|---|
| 只去掉免费先手(构造函数改 `Phase = Opening`、不 `StartTurn`) | **537** | AP = 0、字库空、`Turn = 0` —— 97 个测试构造点都依赖「构造后立即可操作」 |
| 只反转 priority | **199** | 玩家 `EndTurn` 后立刻抢回行动权,敌人拿不到那一拍 —— **实测复现了那段警告** |
| **两个一起**(构造函数末尾 `while (AdvanceOnce()) { }` + priority 反转) | **32** | 见 §2.3 |

「互相成全」不是修辞:单独做任一个都会大面积红,一起做才自洽。

第三种改法还有一个决定性的好处:**97 个测试构造点一个都不用改** ——
`StartTurn()` 由 `BeginPlayerTurn()` 提供,构造完 AP / 字库 / `Turn = 1` 全都在位。

### 2.3 那 32 条的根因,以及它印证了什么

32 条里约 12 条是召唤物相关(`EndTurn_EveryLivingSummonGetsItsOwnStrike`、`OnHitBurn*`、
`OnHitCurse*`、`SummonAttack_*`、`SummonAura_HealsOnItsOwnTurn`…),根因是同一个:

**新召唤的召唤物会延迟一轮才出手。** 它 `ActionMeter` 从 0 起,而玩家插到了它前面:

```
召唤物刚上场 meter = 0;敌人 meter = 100(上一轮攒的)
玩家 EndTurn:
  敌人满格 → 敌人动
  全场推 1 拍 → 玩家 100、召唤 100 → 玩家 priority 更小 → 玩家赢 → 玩家回合开始
  ← 召唤物这一轮没动
```

而 `BattleEngine.cs:1499-1502` 的注释写着:

> 新召唤物从 0 起攒计量器,与场上所有单位同口径(2026-08-15 第五次审查订正:
> **不再需要「创建即满格」的头寸 —— 那是在给反向的 tie-break 打补丁**,priority
> 方向调过来之后,新召唤物自然会在下一次推进里跟大家同时摸满、同回合出手)。

**「创建即满格」曾经存在过,是配「玩家优先」用的**,后来因为把 priority 改成「玩家最后」
才被删掉。现在方向调回来,这个头寸也要跟着回来 —— 它不是补丁,是那一整套设计的组成部分
(见口径 3)。

## 三 · 已定口径

| # | 口径 | 理由 |
|---|---|---|
| 1 | 同速 tie-break 改为 **玩家 0 / 召唤物 1 / Buff 敌 2 / 其余敌 3** | 用户拍板。保住「Buff 敌先于普通敌」= 辅助先摇旗、同伴才带着加成出手 |
| 2 | 去掉开场的免费先手:构造函数末尾改为 `while (AdvanceOnce()) { }`,让调度决定开场 | 用户拍板。也是口径 1 能成立的前提(§二)。`StartTurn()` 由 `BeginPlayerTurn()` 提供,不需要构造函数直接调 |
| 3 | **召唤物上场即满格**(`ActionMeter = TurnScheduler.Threshold`) | 用户拍板。这是恢复 2026-08-15 删掉的那个头寸 —— 它与「玩家优先」配套,当初删它正是因为改了 priority 方向。召唤术的价值就在「立刻有个肉盾并反击」,延迟一轮等于砍它一刀 |
| 4 | **不加** `BattlePhase.Opening`。改为暴露 `OpeningTicks`,表现层自己补开场动画 | 用户拍板。`Opening` 语义更干净但实测红 537 条(§2.2);而开场的 pre 快照**恒为全 0**(开场的定义),所以表现层能自己造出 pre、用当前 meter 作 post、用 `OpeningTicks` 定时长,零额外测试改动 |
| 5 | 开场第一次行动**照常走 `BeginPlayerTurn`**,含玩家侧 DOT 结算 | 用户拍板。「状态在该单位自己行动时结算」是 ATB spec 的口径 1,玩家不该例外 |
| 6 | 开场条流动时长 = `OpeningTicks × ActionBarBaseMs`(同速时 = 1 × 0.5 秒) | 用户拍板。与局中每一拍同一个公式,不引入「第一拍特殊」的分支 |
| 7 | tie-break **只管同速**。速度不同时纯按谁先攒满排 —— **敌人速度高于玩家时,开场可能是敌人先行动** | 用户拍板。这是去掉免费先手后必然且正确的行为:旧系统的免费先手会**掩盖速度差**。详见 §3.1 |
| 8 | 存档 `Restore` 路径**不受影响** | `Restore` 走私有构造 + 快照灌值,不经过开场逻辑;召唤物的 `ActionMeter` 也从快照来,不套口径 3 |
| 9 | **复活**路径的召唤物仍从 0 起(`BattleEngine.cs:1315` 的 `revived.ActionMeter = 0` 不动) | 口径 3 只管「新召唤上场」。复活是把死掉的那只拉回来,它已经在时间轴上待过,不该拿新单位的头寸 |

### 3.1 口径 7 的展开:免费先手掩盖了速度差

`TurnScheduler.Advance` 的排序是两级的:

1. **先比谁先攒满** —— `TicksUntilAnyFull` 取 `ceil((100 − meter) / speed)` 的最小值。速度快的拍数少,先满。
2. **同拍满格的才比 priority** —— `FirstFull` 在满格者里取 priority 最小的。

口径 1 只作用在第 2 级。所以:

| 场面 | 开场第一个行动者 |
|---|---|
| 敌我同速(**当前全部字怪 `Speed` 都是 100**) | 玩家 —— 全场同拍满格,玩家 priority 最小 |
| 敌人速度 > 玩家 | **敌人** —— 它拍数更少,第 1 级就赢了,轮不到比 priority |
| 玩家被减速(`SpeedModifier` 为负) | 同上,敌人先动 |
| 玩家加速 | 玩家先动,且可能**连动两次**才轮到敌人 |

这正是速度这条属性**应该**有的表达力。旧系统里玩家的免费先手把它压平了 ——
无论敌人多快,玩家总是先动一次。

⚠ 眼下这条的实际影响为零:ATB spec §二「不做」明确写了「不给敌人配差异化速度,
字怪 `Speed` 仍全部 100」。但它会在两处立刻生效:**减速字**(`EffectKind.Slow`,−50)
让敌人变慢而不是变快,所以只会加强玩家;而以后给 Boss 配高速、或者玩家吃到减速时,
「敌人先动」就会真实发生 —— 那时不需要改任何代码。

## 五 · 实现要点

### 5.1 priority 重排

`BattleEngine.BuildSlots`:

| 单位 | 旧 | 新 |
|---|---|---|
| 玩家 | 3 | **0** |
| 召唤物 | 0 | **1** |
| Buff 敌 | 1 | **2** |
| 其余敌 | 2 | **3** |

相对次序「Buff 敌先于普通敌」保持不变。

### 5.2 构造函数

```csharp
            Phase = BattlePhase.PlayerTurn;
            // 开场走调度(2026-08-17):不再直接开玩家回合 —— 那是改造前 AP 制的遗留,
            // 等于给玩家一次免费先手。现在全场从 0 攒,谁先满谁先动;轮到玩家时
            // AdvanceOnce 的玩家分支会跑 BeginPlayerTurn → StartTurn(AP/发牌/Turn+1)。
            while (AdvanceOnce()) { }
```

⚠ `Phase = BattlePhase.PlayerTurn` 这行**必须保留** —— `AdvanceOnce` 的准入要求它,
且它是枚举第 0 项(默认值),写出来是为了让意图显式。

### 5.3 `OpeningTicks`

```csharp
        /// <summary>开场那次推进跨了多少拍(2026-08-17)。表现层用它把开场的条动画
        /// 从 0% 播起来:pre 恒为全 0(开场的定义),post 是构造完的当前计量器,
        /// 时长 = OpeningTicks × ActionBarBaseMs。
        /// 同速时恒为 1;玩家被减速或敌人更快时会更大。</summary>
        public int OpeningTicks { get; private set; }
```

在构造函数的 `while` **之前**置 0,`while` 里第一次 `AdvanceOnce()` 之后取
`LastAdvanceTicks` 写入(只取第一次 —— 开场可能推进多轮,但条动画只需要第一段)。

### 5.4 召唤物上场即满格

`ApplyEffects` 的 `EffectKind.Summon` 分支(约 `:1503`),`new SummonState(...)` 之后:

```csharp
                            newborn.ActionMeter = TurnScheduler.Threshold;
```

原处 `:1499-1502` 那段「不再需要创建即满格的头寸」的注释要**整体改写**成记录 §2.3 的结论。

两条上场路径都要覆盖:`_summons.Add(newborn)` 与 `_summons[slot] = newborn`(原地顶替)。

### 5.5 表现层的开场动画

现成先例:`BattleView.cs:542-553` 的 `enteredReviving` 分支 —— 复活后补跑被打断的循环,
用的正是「`BeginAnim()` + `StartCoroutine(...)` + `return`(本帧不走完整 switch)」这套。

开场同型:进战斗后若还没播过开场动画,`BeginAnim()` → 播一次
`FillActionBars(全 0 快照, 当前快照, Battle.LastActor, Battle.OpeningTicks)` → `OnAnimDone`。

⚠ `BattleView.cs:520-522` 那段注释写着「满格未动的敌人(**调度优先级 1/2,高于玩家的 3**)」——
priority 一改它就成了谎言,必须同步改。

### 5.6 那 32 条失败的处置

**逐条推演新序列后重算断言,不许为了变绿而改数字。** 分类:

| 类别 | 条数 | 处置 |
|---|---|---|
| 召唤物出手时序 | ~12 | 口径 3(上场即满格)落地后应自动恢复 —— **先实现口径 3,再看还剩几条** |
| 速度节奏(`Speed150/200/300/50`、`Slow_*`、`SpeedModifiers_StackAdditively`) | ~8 | 相位变了(玩家在开场消费了一拍),重算 |
| `LastAdvanceTicks_*`(4 条,上一批刚加的) | 4 | 重算:开场第一个行动者从敌人变玩家 |
| Buffer / 快照往返 / 杂项 | ~8 | 逐条看 |

```bash
python3 -m pytest tools/pipeline/tests/ tools/fonts/tests/ tools/icons/tests/ -q
```

**用户 Play 验收**(自动化盖不到):

1. 开场是否先看到全场条从 0% 涨到满、然后才轮到行动 —— 这是本次要解决的症状
2. 同速局一轮下来是否是「玩家 → 召唤 → 敌」
3. 开场 0.5 秒的节奏是否合适
4. 召唤字打出去,召唤物是否**当轮**就反击(口径 3 的可见证据)
5. 打出减速字之后,敌人的条是否明显涨得比玩家慢(口径 7 第 1 级排序在局中的证据)
