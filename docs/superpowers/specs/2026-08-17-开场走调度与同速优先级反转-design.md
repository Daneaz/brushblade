# 开场走调度 · 同速优先级反转 · 设计规格

> 2026-08-17 · **推翻** `2026-08-15-ATB回合制改造-design.md` 的 tie-break 方向
> (「并列时玩家排最后」),以及三处配套的「方向不要再调回去」注释:
> `TurnScheduler.cs:34-37`、`BattleEngine.cs:717-723`、`BattleEngine.cs:1499-1502`

## 一 · 背景

### 1.1 症状

用户报告:**战斗开场直接就是玩家行动,没有先走行动条。**

### 1.2 根因

`BattleEngine` 构造函数(`:375`):

```csharp
            Phase = BattlePhase.PlayerTurn;
            StartTurn();
```

开场**完全绕过调度器** —— 玩家拿到一次「免费先手」,而此时全场计量器都还是 0。
所以既看不到条流动,玩家也不是「攒满了才动」。

2026-08-15 的 ATB 改造把玩家纳入了调度,但**开场那一拍没纳入**;这两行是改造前 AP 制的遗留
(那时玩家先动是天经地义的)。

### 1.3 用户同时拍板的第二条

> 敌我双方默认初始速度是 100。速度相同时行动优先级为**玩家 > 召唤物 > 敌方**。

这与现行 priority(`召唤物 0 / Buff 敌 1 / 其余敌 2 / 玩家 3`,玩家**最后**)完全相反,
并且直接撞上 `TurnScheduler.cs:34-37` 的警告:

> ⚠ **玩家排最后**…曾把玩家定成优先级最小(并列必赢),结果每次推进后玩家都抢在敌人前面把
> 行动权收回去、敌人拿不到那一拍 —— 那是 2026-08-15 四轮返工的根因,三种「开局记账」
> (创建时先手 / 玩家记负债 / 消费一拍)全是在给这个反向规则打补丁。**方向不要再调回去。**

## 二 · 为什么这次可以调回去(附实测)

**那段警告描述的病,病根是「玩家优先 + 免费先手」这个组合,不是玩家优先本身。**

### 2.1 三种组合的序列推演

| 组合 | 序列 | 判定 |
|---|---|---|
| **现状**:玩家最后 + 免费先手 | 玩家(免费) → 敌 → 玩家 → 敌 … | 开场那次凭空多出来,玩家看不到条流动 |
| **只反转 tie-break**:玩家优先 + 保留免费先手 | 玩家(免费) → **玩家又动** → 敌 … | 全场同时满格时玩家必赢,敌人那一拍被抢掉 —— **正是警告描述的现象** |
| **本 spec**:玩家优先 + 去掉免费先手 | 玩家 → 召唤 → 敌 → 玩家 → 召唤 → 敌 … | 每人每轮恰好一次,**无需任何记账** |

### 2.2 实测:三种改法各自会红多少条(共 1062 条 Core 测试)

推演不足以拍板,所以三种改法各跑了一次全量测试:

| 改法 | 失败数 | 红因 |
|---|---|---|
| 只去掉免费先手(构造函数改 `Phase = Opening`、不 `StartTurn`) | **537** | AP = 0、字库空、`Turn = 0` —— 97 个测试构造点都依赖「构造后立即可操作」 |
| 只反转 priority | **199** | 玩家 `EndTurn` 后立刻抢回行动权,敌人拿不到那一拍 —— **实测复现了那段警告** |
| **两个一起**(构造函数末尾 `while (AdvanceOnce()) { }` + priority 反转) | **32** | 见 §2.3 |

「互相成全」不是修辞:单独做任一个都会大面积红,一起做才自洽。

第三种改法还有一个决定性的好处:**97 个测试构造点一个都不用改** ——
`StartTurn()` 由 `BeginPlayerTurn()` 提供,构造完 AP / 字库 / `Turn = 1` 全都在位。

### 2.3 那 32 条的根因,以及它印证了什么

32 条里约 12 条是召唤物相关(`EndTurn_EveryLivingSummonGetsItsOwnStrike`、`OnHitBurn*`、
`OnHitCurse*`、`SummonAttack_*`、`SummonAura_HealsOnItsOwnTurn`…),根因是同一个:

**新召唤的召唤物会延迟一轮才出手。** 它 `ActionMeter` 从 0 起,而玩家插到了它前面:

```
召唤物刚上场 meter = 0;敌人 meter = 100(上一轮攒的)
玩家 EndTurn:
  敌人满格 → 敌人动
  全场推 1 拍 → 玩家 100、召唤 100 → 玩家 priority 更小 → 玩家赢 → 玩家回合开始
  ← 召唤物这一轮没动
```

而 `BattleEngine.cs:1499-1502` 的注释写着:

> 新召唤物从 0 起攒计量器,与场上所有单位同口径(2026-08-15 第五次审查订正:
> **不再需要「创建即满格」的头寸 —— 那是在给反向的 tie-break 打补丁**,priority
> 方向调过来之后,新召唤物自然会在下一次推进里跟大家同时摸满、同回合出手)。

**「创建即满格」曾经存在过,是配「玩家优先」用的**,后来因为把 priority 改成「玩家最后」
才被删掉。现在方向调回来,这个头寸也要跟着回来 —— 它不是补丁,是那一整套设计的组成部分
(见口径 3)。

| 9 | **复活**路径的召唤物仍从 0 起(`BattleEngine.cs:1315` 的 `revived.ActionMeter = 0` 不动) | 口径 3 只管「新召唤上场」。复活是把死掉的那只拉回来,它已经在时间轴上待过,不该拿新单位的头寸 |

### 3.1 口径 7 的展开:免费先手掩盖了速度差

`TurnScheduler.Advance` 的排序是两级的:

1. **先比谁先攒满** —— `TicksUntilAnyFull` 取 `ceil((100 − meter) / speed)` 的最小值。速度快的拍数少,先满。
2. **同拍满格的才比 priority** —— `FirstFull` 在满格者里取 priority 最小的。

口径 1 只作用在第 2 级。所以:

⚠ **第 1 级的关键细节:`ticks` 是全场共用的最小值。** 所以「谁先攒满」比的不是速度大小,
而是**拍数**;只要玩家一拍就能攒满(`speed >= Threshold`),敌人再快也是**同拍满格**,
于是落到第 2 级、玩家赢。

| 场面 | 开场第一个行动者 |
|---|---|
| 敌我同速(**当前全部字怪 `Speed` 都是 100**) | 玩家 —— 同拍满格,玩家 priority 最小 |
| 敌人速度 > 玩家,但玩家 `speed >= 100` | **仍是玩家** —— 双方都 1 拍满格,tie-break 生效 |
| 玩家 `speed < 100`(被减速)且敌人 `>= 100` | **敌人** —— 玩家一拍攒不满(如 25 需 4 拍),敌人 1 拍就满 |
| 玩家加速 | 玩家先动,且可能**连动两次**才轮到敌人 |

也就是说「敌人先动」的真实条件是**玩家一拍攒不满而敌人能**,不是「敌人更快」。
速度更快在这个模型里体现为**出手更频繁**(多轮累积),而不是「第一拍就先动」——
玩家 100 / 敌人 200 的局面是「玩家先动,然后敌人连动两次」,不是「敌人先动」。

这正是速度这条属性**应该**有的表达力。旧系统里玩家的免费先手把它压平了 ——
无论敌人多快,玩家总是先动一次,而且之后的频率差也被「每回合固定一轮」抹掉一部分。

⚠ 眼下这条的实际影响为零:ATB spec §二「不做」明确写了「不给敌人配差异化速度,
字怪 `Speed` 仍全部 100」。但它会在两处立刻生效:**减速字**(`EffectKind.Slow`,−50)
让敌人变慢而不是变快,所以只会加强玩家;而以后给 Boss 配高速、或者玩家吃到减速时,
「敌人先动」就会真实发生 —— 那时不需要改任何代码。

## 五 · 实现要点

### 5.1 priority 重排

`BattleEngine.BuildSlots`:

| 单位 | 旧 | 新 |
|---|---|---|
| 玩家 | 3 | **0** |
| 召唤物 | 0 | **1** |
| Buff 敌 | 1 | **2** |
| 其余敌 | 2 | **3** |

相对次序「Buff 敌先于普通敌」保持不变。

### 5.2 构造函数

`Phase = BattlePhase.PlayerTurn` 那行**必须保留** —— `AdvanceOnce` 的准入要求它,
且它是枚举第 0 项(默认值),写出来是为了让意图显式。紧随其后的 `StartTurn()` 换成
推进循环,完整代码见 §5.3(它要同时记回放数据,两者是同一段)。

### 5.3 `OpeningSteps`:开场的逐拍回放数据

构造函数把开场推进跑完了,所以表现层拿到引擎时**过程已经结束**。要把过程演出来,
Core 必须留下每一拍的回放数据 —— 否则玩家只会看到「进战斗即已打完」(§5.7)。

```csharp
    /// <summary>开场推进的一拍(2026-08-17)。构造函数在开场就把推进跑完了,
    /// 表现层靠这些数据把过程逐拍播出来。字段与表现层 AdvanceRoutine 每轮需要的
    /// 东西一一对应:谁动、跨了几拍(定条动画时长)、推进后全场计量器(条的终点)、
    /// 这一拍产生的事件(交给 Juice 播)。</summary>
    public readonly struct OpeningStep
    {
        public ActorRef Actor { get; }
        public int Ticks { get; }
        public int PlayerMeter { get; }
        public IReadOnlyList<int> SummonMeters { get; }
        public IReadOnlyList<int> EnemyMeters { get; }
        public IReadOnlyList<BattleEvent> Events { get; }
    }
```

```csharp
        /// <summary>开场每一拍的回放数据,按发生顺序(2026-08-17)。
        /// 同速开局只有一条(玩家自己那一拍);携带满格召唤物或敌人更快时会有多条。
        /// **不进快照** —— 断点续爬恢复的是战斗中途,没有「开场」可回放。</summary>
        public IReadOnlyList<OpeningStep> OpeningSteps { get; }
```

构造函数:

```csharp
            Phase = BattlePhase.PlayerTurn;
            // 开场走调度(2026-08-17):不再直接开玩家回合 —— 那是改造前 AP 制的遗留,
            // 等于给玩家一次免费先手。现在全场从 0 攒,谁先满谁先动;轮到玩家时
            // AdvanceOnce 的玩家分支会跑 BeginPlayerTurn → StartTurn(AP/发牌/Turn+1)。
            //
            // 每拍都记进 _openingSteps:AdvanceOnce 每次开头都 _events.Clear(),
            // 不记的话开场抢先行动的单位(携带的满格召唤物、以后的高速敌人)表现全丢,
            // 玩家只会看到「进战斗即已打完」。见 spec §5.7。
            bool more;
            do
            {
                more = AdvanceOnce();
                _openingSteps.Add(CaptureOpeningStep());
            } while (more);
```

`CaptureOpeningStep()` 读 `LastActor` / `LastAdvanceTicks` / 三处 `ActionMeter` / `_events`,
各拷一份(不能存引用 —— `_events` 下一拍就被清)。

### 5.5 表现层的开场回放

现成先例:`BattleView.cs:542-553` 的 `enteredReviving` 分支 —— 复活后补跑被打断的循环,
用的正是「`BeginAnim()` + `StartCoroutine(...)` + `return`(本帧不走完整 switch)」这套。
开场同型,新增一个 `OpeningRoutine()` 协程:

```
pre = 全 0 的计量器快照        // 开场的定义
foreach step in Battle.OpeningSteps:
    yield return FillActionBars(pre, step 的计量器, step.Actor, step.Ticks)
    if step.Events 里有非 ActorActed 的:
        _juice.Play(step.Events, ...) ; 等它播完 ; 停顿 0.12s
    DropActingBar(step.Actor, step 的计量器)
    pre = step 的计量器
Refresh()
OnAnimDone(开场死掉的敌人下标)
```

这与 `AdvanceRoutine` 的循环体结构一致 —— 差别只在数据来源(回放 vs 现场推进)。
`FillActionBars` / `DropActingBar` 直接复用,不必改。

进入条件:`_run.Phase == RunPhase.InBattle` 且这一场还没播过开场(用 `_lastBattleIndex`
同款的本地标记守,不必让 Core 记状态)。

⚠ 两处要同步改的注释:
- `BattleView.cs:520-522` 写着「满格未动的敌人(**调度优先级 1/2,高于玩家的 3**)」—— priority 一改就成谎言
- 开场若把敌人打死了,`OnAnimDone` 要收到那些下标,否则 `_dyingEnemies` 的着色残留会撞上下一场同下标的新敌人(`BattleView.cs` 里那条既有的坑)

### 5.8 ⚠ 范围扩张:`EnemyDef` 需要 `Speed` 配置通道

> 那 6 条必须逐条重算 —— 照旧分类去复核会误判成「违规改断言」。
>
> 下面这段对 `Speed200` / `Speed300` 仍然成立,`EnemyDef.Speed` 通道也仍然必需。

那两条速度节奏测试的红**不是断言错**,是 helper 的构造顺序与新语义冲突。`HastedEngine`:

```csharp
            var engine = new BattleEngine(...);   // ← 构造函数现在已经跑完开场推进
            engine.Enemies[0].Speed = speed;      // ← 速度是构造【之后】才设的
```

于是开场那一拍敌人以**默认速度 100** 参与,少攒了 100 —— `Speed200_ActsTwicePerTurn` 实测
`Expected: 10, But was: 5`(敌人只动 1 次)。**断言「速度 200 出手两倍」是设计意图,没错。**

修法只能是把速度移到构造之前,但:

- `EnemyState.Speed` 是 `{ get; set; } = 100`,**没有构造通道**;`EnemyState` 由 `BattleEngine`
  构造函数内部创建,测试拿不到那个构造点
- `EnemyState.ActionMeter` 是 `internal set`,Tests 是独立 asmdef,**测试也无法把计量器拨回开场态**
- `enemies.json` 里**没有 speed 字段** —— 敌人速度至今没有任何配置通道

所以本次必须加一处:**`EnemyDef` 增加 `Speed`(可选,默认 0 → 由既有的
`EffectiveSpeed` 回落到 100),`EnemyState` 构造时从 def 取。**

这是范围扩张,但不是 scope creep:

1. 没有它,那 8 条只能「迁就断言改数字」,把「速度 200 = 出手两倍」这个设计意图的验证丢掉
2. **不改任何现有数值** —— 默认 0 回落 100,`enemies.json` 一个字不动,全部字怪仍是 100
3. 口径 7 说的「以后给 Boss 配高速」迟早需要这个通道,现在只是把它打开而不去用它

### 5.7 ⚠ 方案固有副作用:构造函数可能返回一个已经结束的战斗

`CarriedSummons_CountTowardCap` 的失败是 `Expected: SummonCapFull, But was: BattleOver` ——
上一层带过来 **6 只满格召唤物**,构造函数里 `while (AdvanceOnce())` 让它们在开场直接把
新战斗的弱敌全秒了,**构造函数返回时 `Phase` 已经是 `Won`**。

这个行为**逻辑上正确**(CTB 语义:攒满了就该动;携带的召唤物 meter 从快照恢复,可能是满格),
但带来两个后果:

1. `RunEngine.NewBattle` 可能返回一个 `Phase == Won` 的引擎 —— 表现层必须能处理
   「进战斗即胜利」而不卡死。
2. **构造期间产生的事件只剩最后一批** —— `AdvanceOnce` 每拍开头都 `_events.Clear()`,
   所以那几只召唤物的攻击表现播不出来,玩家只看到瞬间胜利。

可达性:携带召唤物满格(上一场 `Won` 时循环 break,可能正好留着满格的)+ 新战斗敌人弱到能被
6 只召唤物秒杀(无尽模式早期层)。**两个条件都可达**,不能当成理论情形。

**本次处置(用户拍板:做完整回放)**:

1. Core 记 `OpeningSteps`(§5.3),表现层 `OpeningRoutine` 逐拍回放(§5.5)——
   那几只召唤物的攻击照常演出来,玩家看到的是「它们攒满了 → 出手 → 敌人倒下 → 胜利」
2. 表现层还要兜住 `Phase == Won`:开场回放播完直接进结算,不卡死
3. `CarriedSummons_CountTowardCap` 改成反映新行为(新战斗开局即被携带召唤物打赢)

之所以不选「接受限制」:开场抢先行动**结果已经生效**(敌人真的死了、玩家真的挨打了),
只是表现没播 —— 这类「状态变了但玩家没看见」的缺口在这个项目里踩过多次
(飘字/掉血还没到就先灰、死亡着色残留撞下一场同下标新敌人),代价是玩家不理解发生了什么。
