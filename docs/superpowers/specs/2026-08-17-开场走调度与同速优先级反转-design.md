# 开场走调度 · 同速优先级反转 · 设计规格

> 2026-08-17 · **推翻** `2026-08-15-ATB回合制改造-design.md` 的 tie-break 方向
> (「并列时玩家排最后」),以及 `TurnScheduler.cs:34-37` / `BattleEngine.cs:717-723`
> 两处「方向不要再调回去」的警告注释

## 一 · 背景

### 1.1 症状

用户报告:**战斗开场直接就是玩家行动,没有先走行动条。**

### 1.2 根因

`BattleEngine` 构造函数(`:375`):

```csharp
            Phase = BattlePhase.PlayerTurn;
            StartTurn();
```

开场**完全绕过调度器** —— 玩家拿到一次「免费先手」,而此时全场计量器都还是 0。
所以既看不到条流动,玩家也不是「攒满了才动」。

2026-08-15 的 ATB 改造把玩家纳入了调度,但**开场那一拍没纳入**;这两行是改造前 AP 制的遗留
(那时玩家先动是天经地义的)。

### 1.3 用户同时拍板的第二条

> 敌我双方默认初始速度是 100。速度相同时行动优先级为**玩家 > 召唤物 > 敌方**。

这与现行 priority(`召唤物 0 / Buff 敌 1 / 其余敌 2 / 玩家 3`,玩家**最后**)完全相反,
并且直接撞上 `TurnScheduler.cs:34-37` 那段警告:

> ⚠ **玩家排最后**:EndTurn 的语义是「玩家让出行动权、推进到下次轮到我」,玩家刚动完就让出,
> 并列时理应排在所有人后面。曾把玩家定成优先级最小(并列必赢),结果每次推进后玩家都抢在敌人
> 前面把行动权收回去、敌人拿不到那一拍 —— 那是 2026-08-15 四轮返工的根因,三种「开局记账」
> (创建时先手 / 玩家记负债 / 消费一拍)全是在给这个反向规则打补丁。**方向不要再调回去。**

## 二 · 为什么这次可以调回去

**那段警告描述的病，病根是「玩家优先 + 免费先手」这个组合，不是玩家优先本身。**

三种组合的出手序列(全场速度 100、计量器全 0 起步):

| 组合 | 序列 | 判定 |
|---|---|---|
| **现状**:玩家最后 + 免费先手 | 玩家(免费) → 敌 → 玩家 → 敌 … | 开场那次凭空多出来,玩家看不到条流动 |
| **只反转 tie-break**:玩家优先 + 保留免费先手 | 玩家(免费) → **玩家又动** → 敌 … | 全场同时满格时玩家必赢,敌人那一拍被抢掉 —— **正是警告描述的现象** |
| **本 spec**:玩家优先 + 去掉免费先手 | 玩家 → 召唤 → 敌 → 玩家 → 召唤 → 敌 … | 每人每轮恰好一次,**无需任何记账** |

推演第三行(以玩家 + 1 召唤 + 1 敌为例,全部速度 100):

```
开场:  全场 meter = 0,无人满格
  → 推进 1 拍(条从 0% 匀速涨到 100%,这是用户要看到的那一段)
  → 全场 meter = 100,玩家 priority 最小 → 玩家行动,扣 100
  → 玩家 0 / 召唤 100 / 敌 100

玩家 EndTurn:
  → FirstFull 命中召唤(玩家 0 未满)→ 召唤行动,扣 100 → 召唤 0
  → FirstFull 命中敌 → 敌行动,扣 100 → 敌 0
  → 全场 0,无人满格 → 推进 1 拍 → 全场 100 → 玩家赢 → 轮到玩家
```

所以当初三种「开局记账」都是在抵消那次免费先手。**真正的解法是把免费先手删掉** ——
而那恰好就是用户要的「开场先走行动条」。两条要求互相成全。

## 三 · 已定口径

| # | 口径 | 理由 |
|---|---|---|
| 1 | 同速 tie-break 改为 **玩家 0 / 召唤物 1 / Buff 敌 2 / 其余敌 3** | 用户拍板。保住「Buff 敌先于普通敌」= 辅助先摇旗、同伴才带着加成出手 |
| 2 | 去掉开场的免费先手,开场第一拍**走调度** | 用户拍板。也是口径 1 能成立的前提(见 §二) |
| 3 | 新增 `BattlePhase.Opening`,**加在枚举末尾** | `PlayerTurn` 是枚举第 0 项 = `Phase` 的默认值,单纯删掉构造函数那行赋值**不起作用**。加在末尾是为了不让既有值的序号漂移(与 `StatusKind.ObsoleteDamageReduction` 那条教训同源:序号漂移 = 静默存档损坏) |
| 4 | 开场第一次行动**照常走 `BeginPlayerTurn`**,含玩家侧 DOT 结算 | 用户拍板。「状态在该单位自己行动时结算」是 ATB spec 的口径 1,玩家不该例外。跨战斗带灼烧进场时开场先掉一次血 —— 那本来就是惩罚 |
| 5 | 开场条流动时长 = **1 拍 × `ActionBarBaseMs`(0.5 秒)**,不加例外 | 用户拍板。与局中每一拍同一个公式,不引入「第一拍特殊」的分支 —— 那类例外正是上次四轮返工的源头 |
| 6 | 存档 `Restore` 路径**不受影响** | `Restore` 走的是私有构造 + 快照灌值,`Phase` 由快照决定,不经过开场逻辑 |

## 四 · 范围

### 做

| 块 | 内容 |
|---|---|
| 1 | `BattlePhase` 加 `Opening`(末尾) |
| 2 | `BuildSlots` 的 priority 重排为 玩家 0 / 召唤 1 / Buff 敌 2 / 其余敌 3 |
| 3 | 构造函数改为 `Phase = BattlePhase.Opening`,**不调** `StartTurn()` |
| 4 | `AdvanceOnce` 允许从 `Opening` 推进 |

| 7 | 测试:priority helper + 顺序断言 + 新增开场用例 |

### 不做

- **不改任何速度数值**。敌我基准速度都是 100(已经是现状),本次不做差异化配速。
- **不给开场加任何例外分支**(不特调时长、不跳过 DOT、不记账)。见口径 4/5。
- **不动 `EndTurn` / `YieldTurn` 的既有语义**。
- **不改存档结构以外的兼容处理** —— 项目未上线,`BattlePhase` 直接加值(见 memory:存档不需兼容)。

## 五 · 实现要点

### 5.1 `BattlePhase.Opening`

```csharp
    public enum BattlePhase
    {
        PlayerTurn,
        Won,
        Lost,
        DropChoice,
        /// <summary>开场:计量器全 0、还没推进过任何一拍(2026-08-17)。
        /// **加在末尾**是刻意的 —— PlayerTurn 是第 0 项即默认值,而既有值的序号一旦漂移
        /// 就是静默存档损坏(同 StatusKind.ObsoleteDamageReduction 那条教训)。</summary>
        Opening,
    }
```

⚠ Core 里有 **16 处** `BattlePhase.PlayerTurn` 判断、Presentation 里有 **6 处**。
`Opening` 绝不能被任何一处误当成「玩家可操作」。实现时要逐处过一遍:
凡是「玩家能否出字 / 能否结束回合 / 能否点敌人」的守卫,`Opening` 都必须落在**否**的一侧。

### 5.2 `AdvanceOnce` 的准入

现在开头是:

```csharp
            if (Phase != BattlePhase.PlayerTurn && Phase != BattlePhase.DropChoice)
                return false;   // Won / Lost:战斗已结束
            if (Phase == BattlePhase.DropChoice) return false; // 等玩家决议
```

要放行 `Opening`。注意 `Opening` 与 `PlayerTurn` 在这里的语义不同:
`PlayerTurn` 进来是「玩家已让出行动权」,`Opening` 进来是「还没开始」。两者都该推进。

### 5.3 表现层的开场推进

`Opening` 阶段:锁输入(同动画期间)、渲染一次(条全 0%)、然后跑 `AdvanceRoutine`。

`AdvanceRoutine` 的既有循环**天然适用** —— 它就是「推进直到轮到玩家」。所需的只是一个入口:
进入战斗后若 `Phase == Opening`,走一次 `BeginAnim()` + `StartCoroutine(AdvanceRoutine())`。

⚠ 开场那次推进里,`FillActionBars` 的 `pre` 快照必须是**全 0** —— 这正是「条从 0% 涨起来」
的来源。所以拍 `pre` 一定要在第一次 `AdvanceOnce()` **之前**,与既有循环的顺序一致,不需特殊处理。

### 5.4 测试影响

- `TurnSchedulerTests` 的 4 个 helper(`Player`/`Enemy`/`Summon`/`Buffer`)的 priority 实参要改
- **11 处出手顺序断言**要按新序列重算 —— 逐条推演,不许为了变绿而改数字
- 新增:开场用例(全场 0 起步、第一个行动者是玩家、`Ticks == 1`)
- 新增:`Opening` 阶段玩家不能出字 / 不能结束回合
