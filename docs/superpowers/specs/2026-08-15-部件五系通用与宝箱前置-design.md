## Part 1:部件五系通用

### 1.1 规则

同系部件在**配方匹配**上完全等价。**变体各自保留、在池中并存**,靠「位形」区分形象。

| 系 | 等价组 | 代表字 |
|---|---|---|
| 水 | 水、氵、冫 | 水 |
| 木 | 木、艹 | 木 |
| 金 | 金、钅、戈、刂 | 金 |
| 土 | 土、山、石 | 土 |
| 火 | 火、灬 | 火 |

清单外的部件(禾、东、丰、乍、令……)**不参与**:既不作替代,也不被替代。

> ⚠ **必须是显式清单,不许从 `CharDef.Element` 推导**。`禾` 的 element 也是 `Wood`,
> 靠 element 推会让 `木` 能顶 `利 = 禾+刂` 里的 `禾`,把形声部件当成五行部件用。
> 这是本设计最容易被"简化"掉的地方,实现时留注释。

### 1.2 不做归一化(2026-08-15 拍板,推翻初稿)

拆字产出**保持原部件**:拆 `点(占+灬)` 得 `灬`,拆 `灯(火+丁)` 得 `火`,两者在池中并存、
各自显示。`ForgeEngine.TryDismantle` 的入池那句**不动**,`Meta.DeckComponents` 也**不动**。

初稿写的是"拆字产出归一化成五行基本字、池里只剩 5 种",与设计板的位形/转位展示互斥,已废弃。

### 1.3 代码改动(两处)

1. **合成等价匹配** —— `ForgeEngine.TryCompose` 消耗原料那段循环。
   配方要 `冫` 时,池/库里的 `水`、`氵`、`冫` 都可消耗。
   **消耗优先级:先精确匹配,精确没有再按上表组内顺序取**。理由是可预期性 ——
   玩家池里同时有 `冫` 和 `水` 且要合 `冰(冫+水)` 时,先吃掉更"专用"的 `冫`。

2. **`ForgeEngine.Suggest` 同步** —— 它自己走一套原料匹配,不改的话拆合台的提示
   会与实际能合出的字对不上(明明能合的显示成"差原料")。

其余不动:拆字、掉落、起手池、存档结构。

### 1.4 配方撞车(已知,不阻塞)

按等价关系归并后有 4 组配方等效:

| 等效配方 | 撞车的字 | 原配方 |
|---|---|---|
| 土+火 | 灿 / 灶 | 火+山 / 火+土 |
| 土+木 | 柘 / 杜 | 木+石 / 木+土 |
| 水+水 | 沝 / 冰 | 水+水 / 冫+水 |
| 炎+金 | 锬 / 剡 | 钅+炎 / 炎+刂 |

**不阻塞**:合成是玩家指定目标字(`TryCompose(charId, …)`),不是从原料反推产物。
拿着 `水+水` 时 `Suggest` 会把 `沝` 和 `冰` 都列为可合成,玩家自己选 —— 这正是
需求里"用水+水也可以合成冰"想要的效果。

### 1.5 存档兼容

不改数据结构、不改拆字产出,**不需要存档迁移**。老存档的池原样可用,
唯一变化是以前合不出来的字现在合得出来了。

### 1.6 UI(表现层)

依设计板的三个元素:

**a. 位形指示器** — 部件卡左上角,虚线小方框内一个色块,标出该部件在字中占的位置。
设计板的实现见 `PART_POS`(左/右/上/底/整 五种 inset)。

**b. 同源徽标** — 部件卡右上角 `≈X` 小胶囊。
显示规则:**取组内代表字;自己就是代表字时,取组内下一个**。
所以 `火` 显示 `≈灬`、`灬` 显示 `≈火`(与设计板一致),`钅/戈/刂` 显示 `≈金`、`金` 显示 `≈钅`。

**c. 转位说明条** — 拆合台底部,`火 ⇄ 灬` + 文案「同源变体 · 位形互换」。
**纯静态说明,不是可点操作**(2026-08-15 拍板):等价匹配在合成时自动生效,
没有按钮、不花 AP。它只负责把"这两个通用"这件事告诉玩家。

**位形表**(表现层数据,设计师可调;设计板已给的 4 个标 ✅):

| 部件 | 位形 | | 部件 | 位形 |
|---|---|---|---|---|
| 水 | 整 | | 金 | 整 |
| 氵 | 左 ✅ | | 钅 | 左 |
| 冫 | 左 | | 戈 | 右 |
| 木 | 整 | | 刂 | 右 |
| 艹 | 上 | | 土 | 整 ✅ |
| 火 | 左 ✅ | | 山 | 整 |
| 灬 | 底 ✅ | | 石 | 整 |

> `火` 取「左」而非「整」是跟随设计板 —— 它与 `灬` 的「底」形成对照,展示价值更高。
> 能独立成字的部件(水/木/金/土/山/石)一律「整」。

美术占位:融合形象由设计师后出,届时只换贴图,**不动本节的数据口径**。

## Part 2:宝箱叠字前置解锁

### 2.1 规则

宝箱产出的字,其配方里的**非部件原料**必须已在 `MetaState.OwnedCards` 里,否则该字
不进本次开箱的候选池。

- 判定层:**图鉴/永久解锁**(`OwnedCards`,首次获得即入),不是局内字库。
- 只查**直接原料**。`㙓 = 土+垚` 只要求 `垚`;而拿到 `垚` 本身就必须先有 `圭`,
  链式约束自然成立,不需要递归。
- **部件原料不参与判定**(`IsLeaf` 的都靠掉落获得,不需要前置)。

举例(需求原文):
- 未拥有 `圭` → 开不出 `垚`(土+圭)、也开不出 `桂`(木+圭)
- 未拥有 `垚` → 开不出 `㙓`(土+垚)

### 2.2 落点

`ChestRules.TryOpen` → `DrawWeighted` / `DrawUniform` 的候选池构造处
(`Chest.cs:206-208`、`243-253`)。`TryOpen` 手上已有 `meta`,往下传即可。

### 2.3 两条兜底(已拍板)

1. **滤空/滤到不够 → 回退到"配方只含部件的字"填满**。
   先从滤后池抽,不够的名额从无前置要求的字里补,**开箱永远出足数**。
   这是"隐藏限制"的本意:玩家不该感知到自己被挡了。

2. **保底稀有度与前置冲突 → 前置优先**。
   保底只在前置已满足的字里找;找不到就取次高稀有度。规则不被穿孔,
   代价是新玩家前期开高级箱手感偏弱(接受)。

### 2.4 写入路径盘点(分支级审查修正)

全仓 `OwnedCards` 的写入点只有三处:`Shop.cs`(购卡)、`Chest.cs`(开箱,本次已加前置)、
`GameRoot.cs` 的起始集合(局外初始化)。战后奖励选字(`RunEngine.RollRewardOptions`)
**不写** `OwnedCards`,它只填局内战斗字库,不构成产出路径(此前这里误写成"它是另一条
会写 OwnedCards 的产出路径",已核实为误判)。

商城池(`GameRoot.ShopCardPool`)= 玩家**已拥有**的非叶子字,买卡只是给已拥有的字加
重复份,天然不会绕过前置。

`MetaRules.PrerequisitesMet` 仍然独立成方法:不是因为有已知口子要堵,而是留出复用点 ——
将来若真要给某条新产出路径(不止战后奖励)加同一条限制,判定逻辑可以直接调这里。

## 测试计划

Core/Data 走 TDD,先失败测试再实现。

**Part 1**
- 等价匹配:池里 `水+水` 能合 `冰`(配方 `冫+水`);`氵+冫` 也能合 `冰`
- 负向:池里 `木+木` 不能合 `冰`(跨系不等价);`木` 不能替代 `利` 里的 `禾`(清单外不参与)
- 消耗优先级:池里同时有 `冫` 和 `水`,合 `冰` 消耗的是 `冫`
- 撞车共存:池里 `水+水` 时,`Suggest` 同时列出 `沝` 与 `冰`,且两者都真能合出
- `Suggest` 与 `TryCompose` 一致性:Suggest 说可合成的,TryCompose 必须真能合
- 不变量:拆字产出不变(拆 `点` 仍得 `灬` 而不是 `火`)

**Part 2**
- 无 `圭` 时开箱不出 `垚`/`桂`;有 `圭` 后能出
- 无 `垚` 时不出 `㙓`
- 部件字不受前置影响
- 滤空兜底:`OwnedCards` 只有起始集合时,赤霄匣(16 张)仍出满 16 张
- 保底冲突:紫字全被前置挡住时,保底取次高稀有度而不是硬塞紫字
- 确定性:同种子同 `OwnedCards` → 同结果(前置过滤不得引入顺序不确定性)

- 全量 coretests(当前 982 条)必须绿
- 改完 Presentation 必须过 `prescompile`
