# 部件五系通用 + 宝箱叠字前置 — 设计

**日期**:2026-08-15
**状态**:已拍板,待实现

两件相互独立的改动,放在一份 spec 里是因为它们都动 `ForgeEngine` / `Meta` 附近的数据流,
分开做会让第二次改动踩在第一次的半成品上。实现顺序:Part 1 → Part 2。

## Part 1:部件五系通用

### 1.1 规则

同系部件在**配方匹配**上完全等价;**拆字产出**统一归一化成五行基本字。

| 系 | 等价组 | 归一化目标 |
|---|---|---|
| 水 | 水、氵、冫 | **水** |
| 木 | 木、艹 | **木** |
| 金 | 金、钅、戈、刂 | **金** |
| 土 | 土、山、石 | **土** |
| 火 | 火、灬 | **火** |

清单外的部件(禾、东、丰、乍、令……)**不参与**:既不归一化,也不接受替代。

> ⚠ **必须是显式清单,不许从 `CharDef.Element` 推导**。`禾` 的 element 也是 `Wood`,
> 靠 element 推会把 `利 = 禾+刂` 变成 `木+金`,把一个形声部件当成五行部件用。
> 这条是本设计最容易被"简化"掉的地方,实现时留注释。

### 1.2 三处配套改动

缺任何一处系统都是坏的 —— 归一化让池里只剩五行基本字,不做等价匹配就会导致
`利`(配方要 `刂`)永远合不出来。

1. **拆字归一化** —— `ForgeEngine.TryDismantle`,`ForgeEngine.cs:97` 入池那句。
   拆 `冰(冫+水)` → 池里进 `水`+`水`;拆 `利(禾+刂)` → `禾`(原样) + `金`(归一)。
   只归一化**入池**的部件;入库的低阶字(如 `森 = 林+木` 的 `林`)不受影响。

2. **合成等价匹配** —— `ForgeEngine.TryCompose` 消耗原料那段循环。
   配方要 `冫` 时,池/库里的 `水`、`氵`、`冫` 都可消耗。
   **消耗优先级:先精确匹配,精确没有再按组内清单顺序取**。理由是可预期性 ——
   玩家池里同时有 `冫` 和 `水` 且要合 `冰(冫+水)` 时,先吃掉那个更"专用"的 `冫`。

3. **`Meta.DeckComponents` 归一化** —— 出阵表所需部件表。
   它是掉落池与起手池的唯一来源(`RollStartingPool`),不归一化就会继续掉 `刂`/`氵`,
   与"拆出来只有五行基本字"自相矛盾。

另需同步 **`ForgeEngine.Suggest`**:它自己走一套原料匹配,不改的话拆合台的提示
会与实际能合出的字对不上(可合成的显示为差原料)。

### 1.3 配方撞车(已知,不阻塞)

归一化后有 4 组配方变得相同:

| 归一化配方 | 撞车的字 | 原配方 |
|---|---|---|
| 土+火 | 灿 / 灶 | 火+山 / 火+土 |
| 土+木 | 柘 / 杜 | 木+石 / 木+土 |
| 水+水 | 沝 / 冰 | 水+水 / 冫+水 |
| 炎+金 | 锬 / 剡 | 钅+炎 / 炎+刂 |

**不阻塞**:合成是玩家指定目标字(`TryCompose(charId, …)`),不是从原料反推产物。
拿着 `水+水` 时 `Suggest` 会把 `沝` 和 `冰` 都列为可合成,玩家自己选 —— 这正是
需求里"用水+水也可以合成冰"想要的效果。

### 1.4 存档兼容

老存档的部件池里可能存着 `氵`/`刂` 等非归一部件。等价匹配保证它们照样能用,
归一化只作用于**新拆出来的**部件。因此**不需要存档迁移**,也不需要新增字段。

### 1.5 美术占位

拆出来的部件统一显示为 金/木/水/火/土 五个基本字(用户 2026-08-15 指示)。
后续设计师会出一版"融合形象"部件图,届时替换显示层,**不动本设计的数据口径**。

## Part 2:宝箱叠字前置解锁

### 2.1 规则

宝箱产出的字,其配方里的**非部件原料**必须已在 `MetaState.OwnedCards` 里,否则该字
不进本次开箱的候选池。

- 判定层:**图鉴/永久解锁**(`OwnedCards`,首次获得即入),不是局内字库。
- 只查**直接原料**。`㙓 = 土+垚` 只要求 `垚`;而拿到 `垚` 本身就必须先有 `圭`,
  链式约束自然成立,不需要递归。
- **部件原料不参与判定**(`IsLeaf` 的都靠掉落获得,不需要前置)。

举例(需求原文):
- 未拥有 `圭` → 开不出 `垚`(土+圭)、也开不出 `桂`(木+圭)
- 未拥有 `垚` → 开不出 `㙓`(土+垚)

### 2.2 落点

`ChestRules.TryOpen` → `DrawWeighted` / `DrawUniform` 的候选池构造处
(`Chest.cs:206-208`、`243-253`)。`TryOpen` 手上已有 `meta`,往下传即可。

### 2.3 两条兜底(已拍板)

1. **滤空/滤到不够 → 回退到"配方只含部件的字"填满**。
   先从滤后池抽,不够的名额从无前置要求的字里补,**开箱永远出足数**。
   这是"隐藏限制"的本意:玩家不该感知到自己被挡了。

2. **保底稀有度与前置冲突 → 前置优先**。
   保底只在前置已满足的字里找;找不到就取次高稀有度。规则不被穿孔,
   代价是新玩家前期开高级箱手感偏弱(接受)。

### 2.4 已知口子(本次不做)

战后奖励选字(`RunEngine.RollRewardOptions`)是另一条产出路径,同样会写 `OwnedCards`,
本次**不加**前置限制 —— 需求明确说的是"开箱限制"。若将来发现玩家靠战后奖励绕过叠字链,
再按同一判据补一层即可(判定函数应设计成两处都能调用)。

## 测试计划

Core/Data 走 TDD,先失败测试再实现。

**Part 1**
- 归一化:拆 `冰` 得 `水+水`;拆 `利` 得 `禾+金`(清单外部件不动)
- 等价匹配:池里 `水+水` 能合 `冰`(配方 `冫+水`);`氵+冫` 也能合 `冰`
- 负向:池里 `木+木` 不能合 `冰`(跨系不等价);`禾` 不能被 `木` 替代(清单外不参与)
- 消耗优先级:池里 `冫`+`水` 合 `冰`,消耗的是 `冫` 而不是两个 `水`
- `DeckComponents` 归一化:出阵表含 `利` 时返回 `禾`+`金`,不含 `刂`
- `Suggest` 与 `TryCompose` 一致性:Suggest 说可合成的,TryCompose 必须真能合

**Part 2**
- 无 `圭` 时开箱不出 `垚`/`桂`;有 `圭` 后能出
- 无 `垚` 时不出 `㙓`
- 部件字不受前置影响
- 滤空兜底:`OwnedCards` 只有起始集合时,赤霄匣(16 张)仍出满 16 张
- 保底冲突:紫字全被前置挡住时,保底取次高稀有度而不是硬塞紫字
- 确定性:同种子同 `OwnedCards` → 同结果(前置过滤不得引入顺序不确定性)

- 全量 coretests(当前 982 条)必须绿
- `prescompile` 必须过(若动到 Presentation 的配方显示)
