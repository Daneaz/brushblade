# 火系 DOT 三分化(子项目 E-a)设计

**日期**:2026-08-09
**范围**:落地火系「攻 · DOT」表里仅剩的三个 ⚠ 字 —— 炑 / 燥 / 灱,字表可用字数 129 → 132。
**前置**:子项目 D「伤害变体」已合并(commit `0190055`),基线 coretests 743 / pytest 238 / prescompile 0 error。

---

## 一 · 为什么需要这个设计

详表里这三个字原本的配置是:

| 字 | 详表原案 | 降级方案 |
|---|---|---|
| 炑 | `BurnSingle 2` + 刷新既有层 | `BurnSingle 3` |
| 燥 | `BurnSingle 2` + 减疗 50% | `BurnSingle 3` |
| 灱 | `BurnSingle 2` + 减疗 50% | + `DamageSingle 9` |

三处问题,都在开工前的核查里发现:

1. **燥 与 灱 的配置逐字相同**(同为 🟣紫、同为 `BurnSingle 2` + 减疗 50%)—— 同槽位重复。
2. **减疗几乎没有靶子**。引擎里唯一会回血的敌人是缺笔妖(`EnemyAbility.Regrow`,每回合 +3;第 3 次补全直接 `Hp = MaxHp`)。对「回满」施加百分比减疗没有意义。这与子项目 A 的净化「零靶子」同型。
3. **降级方案本身也撞车**:燥 与 炑 的降级都是 `BurnSingle 3`;灱 的降级(2 层 + 单体 9)与已实现的 蒸(2 层 + 单体 9)逐字相同。

**用户裁定(2026-08-09):放弃减疗,三个字换机制。**

三个字的字义天然同质(炑 = 木燃、燥 = 干燥、灱 = 火气上升,全是「助燃」),所以分化必须落在**作用方向**上,而不是字义上。

## 二 · 灼烧的现有模型(设计的前提)

`BattleEngine.EndTurn` 第一段:

```
for 每个存活敌人:
    burn = enemy.Statuses.Find(StatusKind.Burn)
    tick = floor(burn.Magnitude × _burnPerStack × KeMultiplier(Fire, enemy.Element))
    enemy.Hp -= tick
    burn.Magnitude -= 1          ← 每回合掉一层
    若 Magnitude <= 0 则移除
```

要点:

- `Magnitude` = **层数**,`TurnsLeft = -1`(段内持久),靠结算自减而非回合递减
- `_burnPerStack` 基础 2,`EffectKind.BurnPotency`(炽 / 炼)本场全局抬高
- **灼烧属火,只结算相克不结算相生**(相生已在施加时体现)
- 因此 N 层烧完的总伤害是 **N(N+1)/2 × 系数** —— 层数越高,衰减浪费越多

## 三 · 三分化方案

| 字 | 配方 | 效果配置 | 作用方向 |
|---|---|---|---|
| **炑** | 火 + 木 | `BurnSingle 2` + `BurnNoDecay` | **延长** —— 本场灼烧不再每回合 −1 |
| **燥** | 火 + 喿 | `BurnSingle 2` + `BurnPotency 1` + `BurnSettleNow` | **加速** —— 系数 +1 并立即兑现一次 |
| **灱** | 火 + 刀 | `BurnSingle 4` + `Detonate` | **兑现** —— 把剩余层数的全部未来伤害一次打出 |

三者互不重叠,也不与既有的 `BurnPotency`(炽 ⚪白 / 炼 🟢绿)、`DoubleVsBurning`(灼 ⚪白 / 烬 🔵蓝)撞车 —— 后两者是「带灼烧时伤害翻倍」,方向是**伤害修饰**而非 DOT 本身。

稀有度维持详表原案的 🟣紫。

### 3.1 `BurnNoDecay`(炑)

新 `StatusKind.BurnNoDecay` + 新 `EffectKind.BurnNoDecay`。

- 挂在**敌人**身上,`TurnsLeft = -1`(段内持久),`Magnitude = 1`(只作布尔用)
- 灼烧结算里的 `burn.Magnitude -= 1` 变成条件执行:目标带 `BurnNoDecay` 时不减层
- **不叠加**:同字重复施加只刷新(`SourceId` 用字 ID,与 `ArmorBreak` / `Curse` 同约定)
- **只作用于敌人身上的灼烧**。玩家身上的灼烧(灯花 `Sear` / Boss 灼身)走 `_playerStatuses`,是另一段结算,**不受影响** —— 炑 是玩家出的牌,没有理由让自己身上的灼烧也不衰减
- ⚠ 它同时让 `BurnSettleNow`(燥)变成「免费兑现」:立即结算本该扣一层,不衰减之下不扣。这是 §4.2 那条爆发链的根

### 3.2 `BurnSettleNow`(燥)

新 `EffectKind.BurnSettleNow`。**不需要新 `StatusKind`** —— 它是一次性动作,不留状态。

- 对目标立即执行一次完整的灼烧结算(与回合末同公式、同事件)
- 实现上必须把 `EndTurn` 里内联的灼烧结算循环体抽成私有方法 `SettleBurnOn(int enemyIndex)`,两处共用 —— **不留两份实现**
- 燥 的三个效果按 `BurnSingle 2` → `BurnPotency 1` → `BurnSettleNow` 的顺序结算,所以立即兑现的那一下已经吃到 +1 系数

⚠ `BurnPotency` 是**本场全局**的(改 `_burnPerStack`),不是单目标的。燥 的主价值在这里 —— 它是 炼(🟢绿,`BurnSingle 1` + `BurnPotency 1`)的紫档升阶。

### 3.3 `Detonate`(灱)

新 `EffectKind.Detonate`。**不需要新 `StatusKind`**。

- 伤害 = **剩余层数的全部未来伤害** = `floor(N(N+1)/2 × _burnPerStack × KeMultiplier(Fire, enemy.Element))`,其中 N = 引爆时的层数
- 引爆后**层数清零**(移除 `Burn` 条目)
- 口径:只改变兑现**时机**,不改变**总量**。价值在抢杀、以及防止敌人被别的牌提前打死而浪费层数
- 灱 自带 `BurnSingle 4`,所以对空白目标也有 `4×5/2 × 2 = 20` 伤的地板 —— 正好在紫档单攻上沿(16–20),单张不废

**结算顺序**:`BurnSingle 4` 先加层,`Detonate` 后引爆 —— 所以自带的 4 层也参与兑现。

**⚠ 与 燃 的关系(2026-08-09 用户裁定 `BurnSingle 4` 后核过)**:燃 也是 🟣紫 的 `BurnSingle 4`,
表面看 灱 = 燃 + 白送引爆、同档压死。实际不是 —— 两者**留下的场面状态相反**:

- **燃 铺状态**:4 层留在目标身上,能被 `灼`/`烬`(`DoubleVsBurning`,带灼烧时伤害翻倍)与 `炑`(不衰减)接力
- **灱 收状态**:引爆后目标身上**一层不剩**,与整个灼烧流派**反协同**

同样 20 点总伤,燃 是铺、灱 是收。这是真分化,不是压死。

⚠ **通则**:同一个字的多个效果按 `CharDef.Effects` 数组顺序依次结算(引擎现状即如此)。燥 与 灱 都依赖这一点,详表里那两行的 token 书写顺序**就是结算顺序**,不能随手调换。

## 四 · 数值与平衡风险

### 4.1 单张收益

以系数 2、心属性敌人(克制 ×1.0)为例:

| 场景 | 炑 | 燥 | 灱 |
|---|---|---|---|
| 空白目标 | 2 层永久 = 4 伤/回合,不封顶 | 上 2 层 + 系数→3,立即 6 伤,剩 1 层 | 上 4 层 → 引爆 **20 伤**(紫档单攻上沿) |
| 目标已有 5 层 | 5 层永久 = 10 伤/回合 | 立即 21 伤,剩 6 层 | 上 4 层 → 9 层 → 引爆 **90 伤** |

### 4.2 ⚠ 三字自身构成爆发链(必须验证)

这三个字**彼此的乘算关系很强**,而且比初估的更强 —— 每一张都在给同一个池子加层:

```
燃  BurnSingle 4                    → 4 层
炑  BurnSingle 2 + BurnNoDecay      → 6 层,且从此不衰减
燥  BurnSingle 2 + Potency + 立即结算 → 8 层,系数 2→3
    立即结算 8 × 3 = 24 伤,但因不衰减,层数仍是 8
灱  BurnSingle 4 + Detonate         → 12 层
    引爆 12×13/2 × 3 = 234 伤
```

四张牌合计约 **258 伤**。作为对比,紫档单攻 16–20,金档 40,橙档 48。

⚠ **`BurnNoDecay` 是这条链的根**,而且它单独就已经是无界的:层数永不衰减,意味着每回合 N × 系数 的伤害**打到战斗结束**,且后续每张灼烧牌都是净增。它还让 `BurnSettleNow` 变成「免费兑现」—— 立即结算本该扣一层,不衰减之下不扣。

**这不必然是问题** —— 需要同时持有四张牌、四点 AP、且目标活到第四张,是合理的构筑回报。但它把 Boss 战变成「一套秒」的风险是真实的,**必须在实现前用仿真验证**,而不是靠估算。

具体要验的:

1. `tools/balance` 仿真跑一轮,对比加入三字前后的卒层曲线(新手 / 卡 3 级 / 卡 5 级三画像)
2. 特别看 **Boss 层**:成语 Boss 是分阶段血池,一套 ~258 伤会不会直接跨掉两个甚至三个阶段
3. `BurnNoDecay` 无上限是链条的根 —— 若仿真显示失控,**第一个该动的阀门是给 炑 加回合数上限**(`BurnNoDecay(turns N)`),而不是砍引爆公式

### 4.3 炑 的相生口径

`炑 = 火 + 木`,**木生火**,所以 炑 在 `WuxingResolver` 里会吃 ×3。但:

- `BurnSingle` 走 `ApplyBurn(targetIndex, value)`,**不过生克**
- `BurnNoDecay` 是状态,也不过生克

所以**现配置下 ×3 无任何效果**。⚠ 但详表 §169「全表最终只有 5 字吃到 ×3」那句必须加注说明 炑 是「配方吃 ×3 但效果不走生克故无影响」,否则下一个人会以为名单漏了。**若日后给 炑 加伤害成分,×3 立刻生效,数值要重算。**

## 六 · 管线

`tools/pipeline/extract_values.py` 需要认三个新 token。按现有的表结构:

- `BurnNoDecay` / `Detonate` / `BurnSettleNow` 都是**无数值**的标记 → 进 `VALUELESS_EFFECTS`
- 三者都**不需要** `turns` / `targetAll` / `hitCount`,不动那三张白名单

⚠ **子项目 D 的教训**:管线侧的手写 token 表(`SUMMON_PASSIVE` / `DURATION_KINDS` / `TARGET_ALL_KINDS` / `VALUELESS_EFFECTS` / `EXECUTE_TOKENS`)认不得的标记会被**静默丢弃、零报错**。D 因此漏掉过柳的 `Dodge`。本子项目的三个 token 必须逐张表核过,并且测试要写**正向 + 负向**两种(只写正向的话,把整个白名单判断删成 `if True` 都没有测试会红)。

## 九 · 测试要点

按本项目的既有标准,**每条测试都要做变异验证**(把它声称守着的那处实现改坏,确认它变红)。子项目 A~D 累计抓到 13 处零判别力的测试,每一轮评审都在实现者自报之外又找到存活变异。

必须覆盖:

1. **`BurnNoDecay` 真的阻止了减层** —— 变异:去掉条件判断让它照常减层,必须红
2. **`BurnNoDecay` 不影响伤害计算** —— 只挡减层,tick 公式不变
3. **`BurnNoDecay` 不叠加**(同字重放只刷新)
4. **`BurnSettleNow` 与回合末结算同公式** —— 抽方法后两处行为逐位一致;变异:让立即结算少减一层,必须红
5. **`BurnSettleNow` 吃到同一张牌的 `BurnPotency`**(结算顺序)
6. **`Detonate` 的公式是 N(N+1)/2** —— 变异:改成 N × 系数(即只结算当前层),必须红
7. **`Detonate` 后层数清零**
8. **`Detonate` 走克制不走相生**(用非心属性敌人构造可分辨场景 —— ⚠ 子项目 D 的教训:同属性对同属性倍率恒 1.0,与心相同,测不出来;要用真正被克/克制的属性)
9. **`Detonate` 对无灼烧目标** —— 自带 4 层,应当有 20 伤地板
10. **三字组合的爆发链**(§4.2)—— 至少一条端到端测试钉住那条链的实际总伤,防止日后某处改动静默放大。⚠ 断言要**逐段断**(每张牌打完后的层数与伤害),不要只断最终血量:只断总数的话,「层数算多了但系数算少了」这类互相抵消的错会蒙混过关
11. **`BurnNoDecay` 不影响玩家自己身上的灼烧**(§3.1)—— 变异:让它也作用于 `_playerStatuses`,必须红
12. **`Cast` 不传目标下标不抛异常** —— 三个字都是单体,`NeedsTarget` 白名单必须补(⚠ 子项目 A 因漏了 `Dispel` 出过 `_enemies[-1]` 崩溃的 Critical,D 又发现 `Silence` 进了白名单但零判别力)
13. **真实配置守卫**(`CharTableTests`)—— 三个字从 `chars.json` 读出来的效果与详表一致
