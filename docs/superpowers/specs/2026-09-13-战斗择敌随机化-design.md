# 战斗择敌随机化 + 木 L4 择伐(2026-09-13)

用户 2026-09-13 提出五条战斗体验诉求,本稿是拍板后的设计。规则改动全部落在
`Core/Targeting.cs` 这一处唯一裁定点,外加技能树木枝 L4 的一次换节点。

## 0. 诉求与现状对账

| 用户诉求 | 代码现状 | 处置 |
|---|---|---|
| 敌方攻击是固定的,不是随机 | 部分属实:近战被前排拦下时返回 `FirstAliveSlot`(前排槽序最小者),恒定;够得着后排那一支已是均匀随机 | §1 |
| 两个嘲讽召唤物应随机其一 | **已实现**(`frontTaunters[random.Next]` / `taunters[random.Next]`) | §1 顺带扩大生效范围 |
| 我方攻击敌方也应随机 | 属实:`PickByRow` → `FirstAliveInRow` 取 `_enemies` 下标序最小的存活者,恒定 | §2 |
| 木系技能扩展:召唤物优先攻击相克敌方 | 无此机制 | §3 |
| 敌方「锁人」应先打嘲讽召唤物,再打玩家 | 优先级**已正确**(`taunters` 判定排在 `focus == Player` 之前),但扫描区间是 `[frontRow, Count)`,只含后排 —— 前排嘲讽对远程锁人完全不可见 | §1 一并修掉 |

第 1 条与第 5 条同根:`PickAllyTarget` 里远程分支的候选池与嘲讽扫描区间都从
`frontRow` 起算,前排召唤物被整体排除在远程攻击之外。

## 1. 敌方选我方目标(`Targeting.PickAllyTarget`)

统一成一条口径:**先按排位定出「够得着的那一段」,段内有嘲讽就收窄到嘲讽者,再均匀随机。**

### 1.1 近战被前排拦下

改前返回 `blocker`(= `FirstAliveSlot(summons, 0, frontRow)`),恒打前排第一只。
改后候选段 = 前排 `[0, frontRow)` 的全部存活者,段内嘲讽者优先,然后随机。

前排只有 1 只时结果与改前逐位相同,且**不摇随机数**(见 §4 的单候选短路纪律)。

### 1.2 远程,或近战且前排已空

候选段从 `[frontRow, Count)` 扩成 `[0, Count)`,候选池 = 全部存活召唤物 ∪ 玩家。
嘲讽扫描区间同步扩到 `[0, Count)`。

`AttackFocus.Player`(锁人)的判定位置不动 —— 仍排在嘲讽之后、随机池之前。
扫描区间扩大后,「锁人先吃前排嘲讽」自然成立,不需要为它写特例分支。

### 1.3 不动的部分

- `FrontmostSummon`(Boss 洞穿 / 吞噬)仍取确定的最前者。那是另一条口径,与「打谁」无关。
- 「站位先于嘲讽」(2026-09-03 拍板)不变:后排嘲讽者仍挡不住近战,近战仍先吃前排。

### 1.4 已知后果

远程敌人从此能打到前排召唤物。前排肉盾的实际承压变大,通关难度上升。
这是用户 2026-09-13 明确选择的口径(「漏了,应含前排」),后续若数值失衡,
调的是敌人数值或远程怪占比,**不是回退这条规则**。

## 2. 召唤物选敌(`Targeting.PickEnemyTargetForSummon`)

`PickByRow` 从「取该排第一个存活」改成「取该排全部存活者里随机一个」。

**排位规则保留**:远程仍先后排、近战仍先前排,只是同排内不再恒取下标最小者。
用户 2026-09-13 拍板「排位先筛,同排内随机」。

签名新增 `GameRandom random` 参数。该函数改前是纯函数、不吃 RNG;
全仓库调用点只有 `BattleEngine.StrikeOnceWithSummon`(`BattleEngine.cs:2080`)一处。

同排候选只有一只时不摇随机数(同 §4)。

## 3. 木 L4:蕃息 → 择伐

### 3.1 节点

`wood_4` 改名**「择伐」**(旧名「蕃息」废止)。效果:**场上全部召唤物**出手时按生克三档择敌。
作用域是全量召唤物,不限木系 —— 用户 2026-09-13 在「只木系」与「全量」之间改选了全量。

### 3.2 三档择敌

优先级:**相克(召唤物克敌人) > 中立(互不克,含心) > 被克(召唤物被敌人克)**。
取最高的非空档作候选池。

判据直接复用 `WuxingResolver.KeMultiplier(召唤物元素, 敌人元素)` 的返回值
(1.5 / 1.0 / 0.5)当排序键 —— 相克环仍只有一份来源,不在 `Targeting` 里另抄一张表。

### 3.3 与排位、与既有偏好的次序

三档是**全覆盖**的:任何存活敌人必落入某一档,所以它永远生效,
与 `preferUnfrozen` / `preferUnslowed` 那种「筛不出来就退回全体」的弱筛子性质不同。

因此它**不能**放在既有筛子那一层(那一层会压过排位)。正确次序:

```
排位先筛(远程→后排 / 近战→前排)
  → 该排内按三档取最高非空档
    → 档内再走控场偏好(preferUnfrozen / preferUnslowed)与贯穿选列
      → 剩余候选随机一个
```

近战召唤物因此不会为了追相克敌人而越过前排。这与 §2 用户选定的「排位先筛」一致。

未点择伐时三档不参与,行为退化为 §2。

### 3.4 连带删除

「蕃息」整条链路作废,一并删干净(留着就是幽灵配置):

- `Core/BattleEngine.cs`:`BattleConfig.WoodSummonSpeedBonus`(:210)、消费点(:2861)
- `Core/Meta.cs`:`WoodSummonSpeedBonus = PerkRules.ElementBonus(…)`(:309)
- `Presentation/PerkInfo.cs`:`SummonSpeedText` 及其 switch 分支
- `Tests/WoodSummonSpeedTests.cs`:整个文件
- `Tests/PerkInjectionTests.cs`:`EmptySave_GivesNoSummonSpeedBonus`、
  `OtherBranches_DoNotGrantSummonSpeed` 等 4 处断言
- `strings.zh-CN.json`:`perk.node.wood_4.desc` 改写、`perk.detail.summon_speed` 删除

删 `PerkEffect` 成员是安全的:存档存的是 `UnlockedPerks` 里的节点 id 字符串,
枚举序号不进档(同 2026-09-13 删 `ElementLootGuarantee` 的判据)。
`BattleConfig.BaseSummonSpeed` 与 `SummonPassive.Speed` **保留** —— 那是召唤物的基础速度,

## 4. RNG 分流

`BattleEngine` 新增第二条随机流 `_targetRandom`,专供 §1、§2、§3 的目标选择。

- 构造:由同一颗 `seed` 派生(`new GameRandom(seed ^ TargetSeedSalt)`,`TargetSeedSalt` 为
  文件内常量)。两条流因此仍由单一种子完全决定,可复现性不变。
- 存档:`BattleSnapshot.TargetRandomState`(uint),与 `RandomState` 并列;
  `Restore` 走 `GameRandom.FromState`。私有构造签名加一个 `GameRandom` 参数。
  项目未上线,存档不需迁移。
- `_random` 的消费序列在**绝大多数**既有战斗里逐位不变:暴击、命中、回合掉字、
  Boss 抖动、入场冻结等既有断言不受影响。

  ⚠ 不是全部。改前 `PickAllyTarget` 吃的就是 `_random`,在「后排有召唤物且候选 ≥2」时
  摇过数;把它切到 `_targetRandom` 等于从 `_random` 流里**拿掉**这部分消费,
  那一小撮用例会位移。按 `Targeting.cs` 现有注释,没有后排召唤物的战斗改前就一次都不摇,
  所以受影响的只是带后排召唤物的用例,需要逐条复核而不是批量重算。
  分流的收益是把位移面从「几乎所有战斗」压到这一撮。

**单候选短路照旧**:`pool.Count == 1 ? pool[0] : pool[random.Next(pool.Count)]`。
这是纵深防御的第二层(第一层是 `GameRandom.Next(≤1)` 不碰内部状态),
两层任一在位都够,但两层都要写 —— 与 `Targeting.cs` 现有纪律一致。

## 5. 测试

`Targeting` 是纯函数,主体测试落在 `Tests/TargetingTests.cs`(Core 单测,毫秒级)。

新增用例:

1. 近战 + 前排 2 只存活 + 无嘲讽 → 多次调用两个槽位都出现过
2. 近战 + 前排 2 只嘲讽 → 只在这两只之间随机,不外溢
3. 近战 + 前排 1 只 → 不摇随机数(比对 `GameRandom.State` 前后相同)
4. 远程 + 前排有召唤物 → 前排槽位出现在候选里(改前恒不出现)
5. 远程 + `Focus.Player` + 前排有嘲讽 → 打嘲讽,不打玩家(第 5 条诉求的直接钉子)
6. 远程 + `Focus.Player` + 全场无嘲讽 → 打玩家
7. 召唤物近战 + 敌方前排 2 只 → 两只都出现过
8. 召唤物远程 + 后排 2 只 → 两只都出现过;后排空时退前排
9. 择伐关 → 三档不参与,分布与 §2 相同
10. 择伐开 + 同排既有相克又有中立 → 只打相克
11. 择伐开 + 同排只有被克 → 照打被克(档位全空不阻止出手)
12. 择伐开 + 近战 + 相克敌人全在后排 → 仍打前排(排位压过三档)
13. 择伐开 + 心系召唤物 → 全部敌人同档,退化为均匀随机

`PerkInjectionTests` 增 `CounterTargeting` 的三态(未点 / 点亮 / 别枝点亮不给)。

回归:`tools/coretests` 全量。§4 的分流把 `_random` 的位移面压到「带后排召唤物」的用例,
这一撮要逐条看是不是只有目标变了。**不带召唤物的战斗若也变红,说明分流没做对 ——
回头查分流,不要改期望值。**
