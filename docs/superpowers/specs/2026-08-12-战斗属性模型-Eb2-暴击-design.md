# E-b2 暴击 设计

> 战斗属性模型五步拆分的第 2 步。父项目:把玩家从「字牌数值即伤害」改造成持有真实属性的战斗实体。
> 本步给属性集补上第一条**带随机性**的轴。

**日期**:2026-08-12
**上游**:E-b1 属性载体(已合并);用户裁定「属性集 = HP / ATK / DEF / 暴击 / 命中 / 闪避,单一五行轴」
**下游**:E-b3 Buff 组 5 字(`锋` = 暴击 +20%,直接吃本步的通道)→ E-b4 命中/闪避/DEF 改造 → E-b5 全面重新平衡

---

## 一 · 为什么是这一步

E-b1 已经把「玩家造成的伤害」收进一条可放大的链路(`ScaleByAttack`)。暴击是同一条链路上的
第二个乘数,但它引入了一个 E-b1 没有的东西:**摇随机数**。

这件事必须单独一步,因为它是全项目里唯一会**平移随机流**的改动。`BattleEngine._random`
今天只有两个消费方(构造时的 Boss 阈值浮动、`StartTurn` 的回合掉字)和一个条件消费方
(`AttackHits`,且既有战斗全走短路)。任何无条件的新摇点都会让掉字序列整体位移,
827 条现有断言里凡是依赖种子的都会跟着红——而那批红跟暴击本身的对错毫无关系。

`锋`(暴击 +20%)在 E-b3,所以本步只搭管道与随机流,不出字。

## 三 · 暴击的语义

**暴击只作用于出牌那一记直接伤害。**

E-b1 的口径是「ATK 只放大你造成的伤害」;暴击比它**更窄**一层,再加一条约束:

> 暴击是**一次挥击**的结果。没有可辨认的挥击瞬间的伤害,就没有暴击。

逐个结算点的判断:

| 结算点 | 吃暴击 | 理由 |
|---|---|---|
| 单体伤害 `DamageSingle` | ✅ | 就是那一记挥击。多段(`剁`)每段各自判 |
| 群体伤害 `DamageAll` | ✅ | 同上,每个目标各自判 |
| 流血每回合 `Bleed` | ❌ | 出牌时快照的是 `Magnitude`,一次暴击会把**三回合**全部放大 1.5 倍且全程无提示。挥击瞬间与伤害兑现瞬间分离,暴击读不出来 |
| 召唤物攻击 | ❌ | 召唤物是独立实体,暴击是**玩家**属性。且它在 `EndTurn` 出手,每只每次都要摇,随机流消耗随场面规模浮动 |
| 灼烧每层 | ❌ | 全场标量 `_burnPerStack` × 层数,回溯生效(炽 口径)。它根本没有「一次挥击」 |
| 引爆 `Detonate` | ❌ | 它是灼烧层数的**提前兑现**,总量口径与回合末结算是同一条(「只改兑现时机,不改总量」)。让引爆能暴而灼烧不能,等于把 E-b1 刻意绑在一起的这对拆开 |
| 召唤物反击 | ❌ | 同召唤物攻击 |
| 护盾 | ❌ | 沿用 E-b1:护盾/治疗改吃 DEF/HP |
| 治疗 | ❌ | 同上 |
| 反弹(`镜`)/ 反伤(`荆`) | ❌ | 沿用 E-b1:按挨到的伤害反,不是玩家输出 |
| 处决直接击杀 `TryExecuteKill` | ❌ | 目标直接归零,没有可乘的伤害数。**摇点必须排在这个判定之后**,免得白摇一次 |

### 3.1 已知代价:火系与木系吃不到暴击

火系(灼烧/引爆)与木系(召唤)拿不到暴击收益,`锋` 在这两个流派里是废牌。

**这与 E-b1 的立场一致**——「水系(治疗)与土系(护盾)吃不到 ATK 是刻意的,
不同流派堆不同属性」。金系单攻线堆暴击、火系堆 `炽`/`BurnPotency`、木系堆召唤数量。
但这条在 E-b1 那里只影响两个防御系,在 E-b2 会同时打到两个**输出**系,分量更重。

真正的解法不在 E-b2:E-b5 重平衡时要么给 DoT/召唤一条对应的放大轴,要么接受
「暴击是金/心系的专属轴」。本步先把口径钉死并用负向测试守住,不提前发明机制。

### 3.2 敌人侧

**敌人没有暴击。** 三条理由:

1. `EnemyState` 没有暴击字段,加了就要进 `EnemySnapshot`(**新增快照字段**),破掉「零新增字段」;
2. 敌人普攻会**无条件**摇一次暴击,随机流从此每回合都在动——恒等性硬线当场失守;
3. 敌人真正缺的是 DEF(E-b1 §二已裁定),不是暴击。

玩家侧的「被暴击」体验将来由 E-b4 的 Boss 大招承担,那条本来就该是确定性的预警式重击,
比随机暴击更适合这个游戏的节奏。

## 四 · 数据流

与 E-b1 同形,不发明新形状:

```
MetaState.CharacterXp
  → MetaRules.CharacterLevel(xp)              既有
  → MetaRules.CritFor(level)                  【新】角色属性
  + <被动技能加成>                             【口子】本次恒为 0
  → BattleConfig.PlayerCritChance             【新字段,默认 0】
  → BattleEngine.EffectiveCritChance          = PlayerCritChance + CritBuff 状态之和,钳到 [0,100]
  → RollCrit()                                两端短路,中间才摇
  → DamageEnemy(..., crit: true/false)        最末一步 ×CritMultiplierPercent/100
```

### 4.1 成长曲线 —— ⚠ **整节作废**(2026-08-12 用户裁定,见 §十三·1)

> 用户否掉了下面这条曲线:**暴击率不随等级成长,基准恒 0**。
> `MetaRules` 不加 `CritFor`,`GameRoot` 一行都不用改。本节保留原文供追溯,
> 但它描述的不是已实现的行为。

```csharp
/// <summary>暴击成长:0 + 1×(等级−1),上限 25(19.2.1 角色属性)。
/// 与 MaxHpFor / AttackFor 同形同封顶级(26 级)——三条角色属性曲线口径一致。
/// 起点 0:1 级时 CritFor(1) == BattleConfig 的默认值 0,与引入暴击之前逐字节恒等。</summary>
public static int CritFor(int level) => Math.Min(25, level - 1);
```

| 等级 | HP | ATK | 暴击率 | 期望伤害倍率(×1.5 倍率) |
|---|---|---|---|---|
| 1 | 50 | 100 | 0% | ×1.000 |
| 11 | 70 | 120 | 10% | ×1.050 |
| 26 | 100 | 150 | 25% | ×1.125(封顶) |

**起点 0 是刻意的**,它让 `CritFor(1)` 恰好等于 `BattleConfig.PlayerCritChance` 的默认值,
于是恒等性不止在测试里成立,在 `GameRoot` 注入真实等级的**生产路径**上同样成立
(E-b1 的 `AttackFor(1) == 100 == AttackBaseline` 是同一个设计)。

代价:1 级玩家永远不会暴击。暴击这条轴要到 E-b3 的 `锋` 或角色升级后才可见。
**这条是待拍板项 §十三·1。**

### 4.2 暴击倍率

```csharp
/// <summary>暴击伤害倍率(百分比)。150 = ×1.5。</summary>
public const int CritMultiplierPercent = 150;
```

放 `BattleConfig` 上的 `const`(与 `AttackBaseline` 并排),不做成可配置字段:
它现在只有一个取值来源,做成字段就要进快照或靠 config 传,是给单次使用做抽象。
E-b5 要调就改这个常量。**倍率取值是待拍板项 §十三·2。**

### 4.3 局内增益通道

**新增 `StatusKind.CritBuff`**,与 E-b1 复用 `AttackBuff` 的做法不同——攻击加成与暴击率
是两个语义,挤进同一个 Kind 会让 `TotalMagnitude(AttackBuff)` 同时被两边读到。

> ⚠ **新枚举值必须追加在 `StatusKind` 末尾。** `StatusEffect` 会随 `EndlessSaveState.CarriedStatuses`
> 与 `BattleSnapshot.PlayerStatuses` 进 JSON 存档,Newtonsoft 默认把枚举序列化成**整数**。
> 在中间插值会把所有旧存档里的状态整体错位(减伤变成破甲之类),而且是静默的。
> 这是 `CarriedDamageReductions` 改名事故(2026-08-05)的同型风险,只是这次连异常都不会抛。

增益走加法,与 E-b1 的 `AttackBuff` 同款:`锋` 的「+20%」就写成 `+20`。
`SourceId` 铸自增序号使其可叠。

> 落地订正(2026-08-12):
> 1. 属性名最终叫 **`EffectiveCrit`**(下文与 §五 里的 `EffectiveCritChance` 是同一个东西);
> 2. **没有** `internal ApplyPlayerCritBuff` —— `锋` 与本步一起落地(§十三·1),
>    `EffectKind.CritBuff` 的效果分支就是真实入口,再开一个只为测试存在的 API 是多余的。
>    (E-b1 需要它是因为 `剡` 当时还没做。)

```csharp
/// <summary>本场生效的暴击率 = 角色属性(config)+ 局内增益,钳到 [0,100]。
/// 上钳到 100 而不是放任溢出:100 以上摇不出更多暴击,但钳住才能让 RollCrit
/// 的 >= 100 短路成为一条**必然到达**的路径(E-b3 的 锋 叠满时靠它省掉摇点)。</summary>
public int EffectiveCritChance =>
    Math.Clamp(_config.PlayerCritChance + _playerStatuses.TotalMagnitude(StatusKind.CritBuff), 0, 100);
```

## 五 · 摇点与恒等性(本项目的核心约束)

### 5.1 硬线

> **E-b2 守得住 E-b1 的验收硬线:基准值下逐字节恒等,`Tests/` 纯追加零删除。**

守得住的**充要条件**是两条:

1. `BattleConfig.PlayerCritChance` 默认 **0**;
2. `RollCrit()` 在 `chance <= 0` 时**直接返回 false,一次随机都不摇**。

现有 827 条测试一律 `new BattleConfig()`(或在其上只设 `PlayerAttack`/`PlayerMaxHp`),
暴击率取默认 0 → 全部走短路 → `_random` 的调用序列一次都没变 → 掉字序列、Boss 阈值浮动、
`AttackHits` 的取数全部逐位不变。

### 5.2 短路怎么写

```csharp
/// <summary>一次暴击判定。**两端都短路,一次随机都不摇**。
///
/// 下端(chance <= 0)是 E-b2 的恒等性硬线:_random 的既有消费方是构造时的 Boss 阈值浮动
/// 与 StartTurn 的回合掉字,无条件摇会平移整条流,让所有依赖种子的既有测试全红
/// (与 AttackHits 的 hitRate >= 100 那条短路是同一个坑,同一个解法)。
///
/// 上端(chance >= 100)对称处理:必暴时摇不摇结果都一样,不摇能让「暴击叠满」的
/// 玩法路径同样不扰动随机流,也让测试可以在不注入 RNG 的前提下断言必暴。</summary>
private bool RollCrit()
{
    int chance = EffectiveCritChance;
    if (chance <= 0) return false;
    if (chance >= 100) return true;
    return _random.Next(100) < chance;
}
```

比较式抄 `AttackHits` 的 `_random.Next(100) < chance`:`Next(100)` 吐 [0,99],
`chance = 1` 即 1%,`chance = 99` 即 99%,无偏。

### 5.3 摇点放在哪(调用点,不是 `DamageEnemy` 内部)

`DamageEnemy` 有 **6 个调用点**,其中只有 2 个该暴击:

| 调用点 | 行 | 暴击 |
|---|---|---|
| `ApplyEffects` / `DamageSingle` | ~896 | ✅ |
| `ApplyEffects` / `DamageAll` | ~908 | ✅ |
| 召唤物反击 | ~665 | ❌ |
| `DamagePlayerDirect` 的反弹(`镜`) | ~1540 | ❌ |
| `DamageSummon` 的反伤(`荆`) | ~1586 | ❌ |
| `DamageSummon` 的反弹(`镜`) | ~1607 | ❌ |

所以暴击判定**不能写进 `DamageEnemy` 内部**(那样 6 条全会暴),必须是一个
`bool crit = false` 的可选参数,由前两个调用点显式传 `RollCrit()`。
默认 false 让另外 4 个调用点一个字都不用改——这同时也是恒等性的一部分。

> 这是 E-b1 终审教训的同型陷阱:「吃不吃」不存在白名单数据结构,纯粹取决于
> **哪些调用点传了 true**,所以变异要在调用点上做,负向测试要逐条盯住那 4 个不该暴的。

摇点在调用点内的**精确位置**同样重要,顺序必须是:

```csharp
if (!_enemies[targetIndex].Alive) break;        // ① 死目标不摇
if (TryExecuteKill(effect, targetIndex)) break; // ② 处决走掉不摇
DamageEnemy(..., crit: RollCrit());             // ③ 真要打了才摇
```

摇点排在 ①② 之前的话,「这一发消耗几个随机数」会取决于目标死没死、够不够斩杀线,
调试和复现都会变成噩梦。

### 5.4 存档兼容

**不破。** `_random.State` 本来就在 `BattleSnapshot.RandomState` 里,`GameRandom.FromState`
接着原流摇下去——加不加新消费方都一样。旧存档恢复后只是**接下来**的随机流与旧版本不同,
不会解析失败、不会崩溃。

一条要说清的:遭遇生成走的是另一条流(`EndlessGenerator.BuildSegment(endless, fromDepth, snapshot.Seed, ...)`),
战斗内 RNG 是 `seed: towerSeed * 17 + fromDepth` 现开的。所以暴击摇点**只会平移某一场战斗内部的掉字序列**,
不会改变层段布局与遭遇顺序——旧存档续爬看到的怪还是同一批。

### 5.5 摇点粒度

推荐:**每记伤害独立摇**。

- 多段(`剁` `HitCount = 3`)三段各摇一次,可能一暴两平,读数有层次;
- 群体伤害每个目标各摇一次(`aoeCount` 已在循环前取快照,分裂出的新怪不吃这一发,摇点数也随之确定)。

代价:一次出牌消耗的随机数随场面敌人数浮动。这不影响恒等性(基准值 0 摇点为零),
只是仿真工装的方差会略大——工装本来就跑多种子取 P50/P90,吸收得住。

**这条是待拍板项 §十三·4**(备选:每张牌只摇一次,全段/全体同暴同平)。

## 六 · 乘法顺序与取整点

### 6.1 插在最末

现有顺序(E-b1 后):

```
卡等级 → 灼烧翻倍(DoubleVsBurning) → 残血加伤(ExecuteBonus) → ATK 缩放
  → [DamageEnemy] 生克 → 减伤/穿甲/破甲 → Math.Floor
```

暴击插在**最末,`Math.Floor` 之后**:

```
… → 减伤/穿甲/破甲 → Math.Floor → 暴击 ×150/100(整数除)
```

```csharp
if (taken != 1f)
    damage = (int)Math.Floor(damage * taken);
// 暴击排在最末(2026-08-12):它是「这一记最终打出去的伤害翻倍」,不是某一层的基础值加成。
// 放最后同时把截断损失压到最小 —— 放在 ScaleByAttack 旁边(生克之前)的话,
// 相生 ×3 会把整数除丢掉的那部分放大三倍(基础 5 → 暴击 7 → ×3 = 21,而正解是 22)。
if (crit) damage = damage * BattleConfig.CritMultiplierPercent / 100;
```

### 6.2 为什么是整数除而不是折进 `taken`

看起来更省事的写法是把暴击折进既有的浮点系数:`if (crit) taken *= 1.5f;`,
共用同一个 `Math.Floor`,一个截断点都不多。**不采用**,两条理由:

1. **浮点误差会被放大。** `taken` 这条链里已经有不精确的项(`PierceBonusPercent / 100f` = 0.15f
   二进制不可表示),再乘一个系数会把既有误差抬进整数位。`EnemyState.Attack` 的诅咒算式
   已经因为 `1 - 0.1f = 0.89999997` 被 floor 拉低过 1 点,改成整数式子修掉(2026-08-06 M1)——
   同一个坑不该在暴击上再踩一次。
2. **口径一致。** E-b1 已经裁定:直接伤害这条链走**整数除**(`ScaleByAttack`),
   浮点晚截断只在灼烧那条既有的浮点式子里用(`attack-scaling-two-code-paths`)。
   暴击落在直接伤害链上,就跟直接伤害的口径。

### 6.3 与灼烧那条链的关系

**没有关系**——暴击不落在灼烧/引爆上(§三),所以 E-b1 那对「整数除 vs `(double)` 晚截断」
的分叉,E-b2 一条都不碰。这是把暴击范围收窄到直接伤害的一个额外好处:
新增的取整点只有一个,且在最末。

### 6.4 与既有 ×2 的叠乘

暴击与 `灼烧翻倍 ×2`、`残血加伤 ×2`、`相生 ×3`、`相克 ×1.5` 全部**相乘**。
今天的理论天花板是 `×2 × ×2 × ×3 × ×1.5 = ×18`,暴击 ×1.5 把它抬到 ×27。
这是选 ×1.5 而不是 ×2(那会到 ×36)的一条理由,见 §十三·2。

## 七 · 表现层

### 7.1 事件:给 `BattleEvent` 加字段,不加枚举值

```csharp
public bool Crit { get; }   // Damage 事件专用;其余恒 false

public BattleEvent(BattleEventKind kind, int targetIndex, int amount,
    int secondIndex = -1, int absorbed = 0, bool crit = false)
```

**不新增 `BattleEventKind.Crit`。** 单独发一条暴击事件会逼表现层做事件配对
(「刚才那条 Damage 是不是这条 Crit 的」),而这套代码库已经在配对判据上栽过两次:
`EnemyDied` 必须紧跟致死伤害、`lastDamageTarget` 不能只看 `events[idx-1]` 是否紧邻。
暴击是那一记伤害的**属性**,就该长在那条事件上。

加字段是**纯追加**:`_events.Add` 的其余全部调用点用默认值 `false`,一行都不改。

## 十一 · 测试策略

沿用 `AttackStatTests.cs` 的做法:测试字一律 `Element.Heart` 且不给配方
(心对全属性生克 1.0x、无配方则无相生 ×3),断言里看到的数字就是暴击缩放本身。

### 11.1 随机性怎么控:不需要注入 RNG

`RollCrit` 的两端短路直接给了确定性:

- `PlayerCritChance = 0` → 必不暴,且**不摇**
- `PlayerCritChance = 100` → 必暴,且**不摇**

于是正向与负向断言全部可以在零随机的前提下写死数字。`BattleEngine` 那个接受 `GameRandom`
的私有构造重载(`:238`)是 `Restore` 专用的,**不需要**为测试开成可注入——
开了反而是给单次用途造抽象。

中间档(真的摇)只需要两条测试:一条证明它确实在摇(§11.2 的统计边界),
一条证明它确实消耗了随机流(`RandomState` 变了)。

### 11.2 「摇了几次」可以直接观测

`BattleSnapshot.RandomState` 是 public 的,`engine.Capture().RandomState` 就是当前随机流状态。
配上 `UnlockedChars = null`(不掉字,构造后零消耗)的测试配置,可以精确断言摇点数:

```
造引擎 → 记 state0 → Cast 若干次 → Capture().RandomState 与 state0 比
```

这把「一次随机都不摇」从一句注释变成一条**可执行的断言**,是 E-b1 时做不到的。

### 11.3.1 第 9 条为什么必须存在(且为什么要这么挑数字)

生克全 1.0x 的测试字上,**暴击放在生克之前还是之后,结果完全一样**
(`floor(v × 1.0) = v`,两个顺序都得 `v × 150 ÷ 100`)。也就是说:
其余 28 条测试**全绿也守不住乘法顺序**。必须有一条在暴击与取整之间夹一个非 1 的系数。

用**破甲**当那个系数,好处是不必打破「测试字一律 `Element.Heart` 且不给配方」的约定。
**基础值必须是 6**——它是同时分得开两种变异的那个值:

| | 本设计<br>暴击在最末、整数除 | 变异 ①<br>暴击挪到生克之前 | 变异 ②<br>暴击折进 `taken` 浮点乘 |
|---|---|---|---|
| 基础值 | 6 | `6 × 150 ÷ 100 = 9` | 6 |
| 生克(心,1.0) | 6 | 9 | 6 |
| 承伤系数 | `floor(6 × 1.25) = 7` | `floor(9 × 1.25) = 11` | `taken = 1.25 × 1.5 = 1.875`<br>`floor(6 × 1.875) = 11` |
| 暴击 | `7 × 150 ÷ 100 = 10` | — | — |
| **结果** | **10** | **11** | **11** |

换成基础 5 只分得开变异 ①(9 / 8 / 9),换成基础 7 只分得开变异 ②(12 / 12 / 13)。
**这条测试的数字不能随手改**,注释里要写清为什么是 6。

(备选写法是用一个带相生 ×3 的字,基础 5 → 22 / 21 / 22:同样只分得开变异 ①,
且要引进配方、破坏那条约定,不推荐。)
