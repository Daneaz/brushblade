# 技能树环形星域 · 设计规格(2026-09-08)

> 基线提交:`8ba17da`。本文是本次改造的唯一规格,实现以此为准。
> 触发:用户裁定「当前太扁平化」,参考《黑神话:悟空》技能树的拓扑手法重做。
> **上游规格**:`docs/superpowers/specs/2026-09-07-技能树重构-design.md` —— 那份仍然有效,
> 它管**节点的内容**(40 个节点各自的效果、门槛、定价、以及全部 Core 注入)。
> 本文只管**拓扑与呈现**:节点之间怎么连、怎么排、怎么看。

## 0 · 结论摘要

| 项 | 改前(2026-09-07,已合并) | 改后 |
|---|---|---|
| 拓扑 | 5 列 × 4 行规则网格,每枝一条直链 | **环形星域**:中心 → 三个树根 → 各自扇区展开 |
| 树之间 | 完全独立 | **3 个跨树节点**,要两棵树各一个前置 |
| 节点数 | 40 | **43** |
| 前置模型 | 「同枝 `Depth−1`」隐式推导 | 隐式为默认,**跨树节点用显式谓词覆盖** |
| 效果值 | 常数 | 跨树节点是**已点亮节点数的函数** |
| 视图 | 三页签,各自一屏 | **一张可平移缩放的画布**(逻辑 1120×1120) |
| 节点呈现 | 名字 + 色块 | **图标 + 名字** |
| 全树总价 | 43,600 | **46,600** |

## 1 · 为什么改

2026-09-07 那版的拓扑是**规则网格**:枝干为列、深度为行,5 条互不相交的直链。
抉择只有两个维度 —— 点哪几枝、各点多深 —— 而走法的差异全部由墨锭预算决定。
**路径本身不携带任何信息**,这就是「扁平」。

用户在三个方向(A 星盘 / B 主干与岔路 / C 环形星域)里选了 **C**。C 的代价最高、
新意也最大:它是唯一让**三棵树互相咬合**的方案。

## 2 · 拓扑:环形星域

### 2.1 扇区按节点数分,不等分 120°

| 树 | 角度区间(屏幕角,y 向下,270° = 正上) | 枝数 × 层数 | 节点 |
|---|---|---|---|
| 五行 | 180° ~ 360°(上半) | 5 × 4 | 20 |
| 被动 | 0° ~ 108°(右下) | 4 × 3 | 12 |
| 机制 | 108° ~ 180°(左下) | 4 × 2 | 8 |

枝在扇区内均分角度,节点沿半径向外分层。

### 2.2 半径体系:最外层对齐,内层各自起跳

逻辑画布 **1120 × 1120**,中心 `(560, 560)`。

| 用途 | 半径 |
|---|---|
| 中心「斗」 | 44 |
| 三个树根 | **100** |
| 五行第一圈(4 层) | 190 |
| 被动第一圈(3 层) | 200 |
| 机制第一圈(2 层) | 280 |
| 各树最外层 | **475**(共用) |
| 跨树节点 | **530** |

⚠ **三棵树的第一圈不共用一个半径** —— 层数少的树起点更远,好让每棵树的层距都够宽。
最外层共用 475,所以层数不同(4/3/2)的三棵树看起来仍是齐的。

这条是从一次失败里得来的:初稿让所有枝的 L1 共用半径 52,那一圈上要挤 13 个节点,
枝间距只剩 32px(节点直径 20),机制树更是压到 16px —— 直接重叠。

### 2.3 间距(节点直径 46~52)

| 树 | 层距 | 同圈枝距(最内 → 最外) |
|---|---|---|
| 五行 | 95.0 | 119.4 → 298.5 |
| 被动 | 137.5 | 94.2 → 223.8 |
| 机制 | 195.0 | 88.0 → 149.2 |

最紧处 88px,节点直径 52,余 36px。**节点里放得下两个字的名字**,这是从
「挤在一屏」改成「可滑动大画布」换来的:同样的排布在 414×373 的视口里,
最紧处只有 30px,节点只能是纯色块。

### 2.4 三个树根是**纯分区标记**,不是可解锁节点

空心圆 + 「五行 / 被动 / 机制」三个标签,不占节点数、不定价、不设门槛。

裁决依据:三棵树的第一层门槛已经是 Lv2 / Lv4 / Lv6,再加一道入门闸是**重复收费**;
而作为视觉分区,空心标记已经够用。

## 3 · 跨树节点

三个,各在两棵树的扇区交界上。**这是 C 方向的全部意义** —— 没有它们,环形只是换个形状的网格。

| id | 名字 | 位置(角度) | 前置 | 效果 |
|---|---|---|---|---|
| `cross_vigor` | 相济 | 0°(五行 ↔ 被动) | 五行任一 L3 **+** 被动任一 L2 | 每点亮一个五行 L3/L4,**攻击 +2%** |
| `cross_edge` | 贯通 | 108°(被动 ↔ 机制) | 被动任一 L2 **+** 机制任一 L1 | 每点亮一个机制节点,**暴击率 +2%** |
| `cross_draw` | 博采 | 180°(机制 ↔ 五行) | 机制任一 L1 **+** 五行任一 L2 | 每有一系专精到 L2,**起手抽取次数 +1**(上限 +2) |

### 3.0 它们属于第四类,不属于任何一棵树

`PerkTree` 加第四个枚举值 **`Cross`**。跨树节点的 `Tree = PerkTree.Cross`,
`Branch` 各自独立(`"xvigor"` / `"xedge"` / `"xdraw"`),`Depth = 1`。

⚠ **这会让既有测试 `Nodes_AreFortyAcrossThreeTrees` 必然变红** —— 它断言
「40 个节点分属三棵树,五行 20 / 被动 12 / 机制 8」。表的形状真的变了,这条断言该跟着变成
「43 个节点分属四类,五行 20 / 被动 12 / 机制 8 / 跨树 3」。

这是本次改造**唯一一条必须改的既有断言**,与 §10.1 的恒等性硬线不冲突:硬线守的是
「没点任何新节点时**行为**不变」,而这条断言描述的是**表的形状**,表变了它就该变。
除它之外任何既有断言变红,都是 bug 而不是预期。

### 3.1 为什么效果是「缩放器」而不是固定加成

写死「金脉 L3 + 锋枝 L2 = 某个具体加成」会把跨树节点变成**第四棵树的固定路径** ——
玩家只有一条正确走法,抉择反而没了。

缩放器的效果值是**你在两侧树上已投资量的函数**:专精两系走到底(8 个五行 L3/L4)
就是 +16% 攻击;广种薄收的人拿不到。**它放大你已有的投资,不要求特定组合** ——
这正是想奖励的取舍。

⚠ 由此产生一个必须在 UI 上讲清的后果:**刚点亮时收益可能是 0**。
玩家在只有 L2 的时候点开「相济」,看到的是「+0%」。详情面板必须显式说出
「当前已点亮 0 个五行 L3/L4,所以现在是 +0%,得先把某一系走深」,否则会被当成 bug。

## 4 · 前置模型的改造

### 4.1 隐式为默认,显式为覆盖

上游规格刻意没做显式依赖图,理由是「每枝是一条直链、无交叉,显式依赖图是给任意 DAG 用的
抽象,此处是给单次使用造抽象」。**跨树节点推翻了那个前提**,但只推翻了三个节点那么多。

所以:40 个普通节点**照旧**走「同枝 `Depth−1`」的隐式推导,只有跨树节点带显式前置。

```csharp
/// <summary>跨树节点的前置谓词;null = 走「同枝 Depth−1」的隐式推导。
///
/// 不是「某个具体节点的 id 列表」而是谓词 —— 跨树节点要的是「任一五行 L3」,
/// 不是「金脉 L3」。写成 id 列表就等于把它绑死在某一枝上,那正是 §3.1 要避免的。</summary>
public IReadOnlyList<PerkRequirement> Prereq { get; }

public sealed class PerkRequirement
{
    public PerkTree Tree { get; }     // 哪棵树
    public int MinDepth { get; }      // 至少点到第几层(1 起)
    public int Count { get; }         // 至少几个,缺省 1
}
```

`CanUnlock` 的前置判定改成:

```csharp
var def = Get(id);
if (def.Prereq == null)
{
    // 普通节点:同枝 Depth−1(与上游规格逐字相同)
    var prereq = def.Depth <= 1 ? null : $"{def.Branch}_{def.Depth - 1}";
    if (prereq != null && !IsUnlocked(meta, prereq)) return false;
}
else
{
    foreach (var req in def.Prereq)
        if (CountOwned(meta, req.Tree, req.MinDepth) < req.Count) return false;
}
```

⚠ **`CountOwned` 必须遍历固定顺序的 `Nodes` 而不是 `meta.UnlockedPerks`** ——
后者的顺序取决于玩家点技能的先后。这条与上游规格 §3.2 的
`GuaranteedLootElements` 同一个理由(同种子同结果),虽然这里只是计数、顺序不影响结果,
但保持一致的遍历习惯能免掉下一个人重新推一遍。

## 5 · 效果缩放

跨树节点**不新增 `PerkEffect` 枚举值** —— 它们注入的仍是既有的
`AttackPercent` / `CritChance` / `DrawRolls`。变的只是**值怎么算**。

```csharp
/// <summary>效果值的缩放方式。None = 值就是 Value(全部 40 个普通节点)。
/// 其余三种:值 = Value × 计数,计数由 Scaling 决定。</summary>
public enum PerkScaling
{
    None,
    PerWuxingDeep,        // 每个已点亮的五行 L3/L4
    PerMechanicNode,      // 每个已点亮的机制树节点
    PerSpecializedElement // 每个专精到 L2 的五行系
}
```

`PerkRules.Bonus` 的求和改成:

```csharp
foreach (var id in meta.UnlockedPerks)
    if (ById.TryGetValue(id, out var def) && def.Effect == effect)
        sum += def.Scaling == PerkScaling.None
            ? def.Value
            : def.Value * ScaleCount(meta, def.Scaling);
```

`ScaleCount` 的签名与三种计数的口径:

```csharp
/// <summary>缩放节点的计数。遍历固定顺序的 Nodes(不是 meta.UnlockedPerks),
/// 与 §4.1 的 CountOwned 同一条理由。</summary>
private static int ScaleCount(MetaState meta, PerkScaling scaling) => scaling switch
{
    // 已点亮的五行 L3/L4 个数(只数深层,L1/L2 不算 —— 那两层是供给不是强化)
    PerkScaling.PerWuxingDeep => CountOwned(meta, PerkTree.Wuxing, minDepth: 3),
    // 已点亮的机制树节点个数(该树只有两层,全算)
    PerkScaling.PerMechanicNode => CountOwned(meta, PerkTree.Mechanic, minDepth: 1),
    // 专精到 L2 的五行系数,**夹上限 2**
    PerkScaling.PerSpecializedElement => Math.Min(2, CountSpecializedElements(meta)),
    _ => 1,
};
```

⚠ **`PerSpecializedElement` 的上限 2 夹在 `ScaleCount` 里,不是夹在调用点** ——
起手抽取次数有四个来源(基础 1 + 慧眼 + 该系五行 L1 + 博采),夹在调用点会漏掉其中几条。

⚠ `CountSpecializedElements` 数的是**系**不是节点:金木水火土五系里,有几系点到了 L2 或更深。
一系点满 4 层也只算 1。

## 6 · 门槛与定价

三个跨树节点的**等级门槛由前置隐含**,不再单设:

| 节点 | 前置隐含的最低等级 | 显式门槛 | 定价 |
|---|---|---|---|
| 相济 | 五行 L3 = Lv16 | **Lv16** | **1,200** |
| 贯通 | 被动 L2 = Lv8 | **Lv8** | **900** |
| 博采 | 五行 L2 = Lv10 | **Lv10** | **900** |

显式写出来(而不是留给前置隐含)是为了 UI 能直接印「Lv.16 解锁」,
以及让 `AllNodes_UnlockByLevel22` 那条守卫仍然管得到它们。

相济贵 300 是因为它挂在五行 L3(最贵的一档 1,200)之后,且攻击是最直接的收益。

**全树总价 43,600 → 46,600**。按上游规格 §1.2 的经济测算(Lv26 时技能树可分到
5,000~7,000 墨锭),可点比例从 10~13/40 变成 10~13/43,**基本不变**。

## 7 · 图标系统

**15 枚图标撑起 43 个节点。**

### 7.1 复用既有 6 枚

路径从 `tools/icons/build_icons.py` **逐字节照抄**,不重画:

| 图标 | 用在 |
|---|---|
| `morale` | 金脉 L4(战意上限) |
| `speed` | 木脉 L4(召唤物速度) |
| `burn` | 火脉 L4(灼烧每层) |
| `attack` | 被动「力」枝 · 跨树「相济」 |
| `crit` | 被动「锋」枝 · 跨树「贯通」 |
| `defense` | 被动「御」枝 |

玩家在战斗里见过的状态图标,和技能树里是同一枚 —— 这条认知联系是白捡的,不要为了
「技能树该有自己一套」而重画。

### 7.2 新画 9 枚

`perk_draw`(抽两次取好)、`perk_loot`(候选保底)、`perk_amplify`(效果放大)、
`perk_wellspring`(泉)、`perk_heft`(厚)、`perk_hp`(生命上限)、
`perk_library`(字库格)、`perk_hand`(起手扇牌)、`perk_ap`(行动点槽)。

SVG 路径见设计稿(画布「技能树」页),坐标系与 `build_icons.py` **完全一致**
(64×64、内容留 8px 边距、`stroke-width 6` 圆头圆角),可逐字节搬 —— 手改坐标必然和稿漂开。
唯一差别:管线里描边是 `#fff`(底色由 C# 上色),稿里用 `currentColor` 以便按枝着色。

### 7.3 为什么 15 枚够

**五行 L1/L2/L3 三层跨五系共用同一枚** —— 图形表达「效果类型」,颜色表达「哪一系」。
这正是 `build_icons.py` 开头写的约定:「图形一律白色,底色由 C# 侧上色 —— 一张图跨底色复用」。
五个系的 L1 长得一样但五种颜色,玩家一眼看出「这是五个系各自的供给节点」。

跨树节点 = **外圈虚线环**(表示跨) + **内部放它所放大的那个效果的图标**。
图标本身就说明了它放大什么。

### 7.4 落地时的三处对账(CLAUDE.md 硬线)

加一枚图标要同时改:`build_icons.ICONS`(SVG 片段)、`test_icons.EXPECTED`、
`Icons.cs` 的 `Glyphs`(PNG 取不到时的兜底汉字,新汉字还要重跑字体子集)。
**缺任一处的后果不是编译错,是上线渲染成「?」。**

## 8 · UI:一张可平移缩放的画布

### 8.1 屏幕只是视口

逻辑画布 1120×1120,932×430 的屏幕显示其中一块。**这个前提是拥挤问题的真正解药** ——
在它之前所有布局努力都在和 350px 的垂直空间搏斗。

### 8.2 导航

- **左下四个胶囊**(五行 / 被动 / 机制 / 跨树)= 跳转锚点,点一下把视口平移过去。
  **不是页签** —— 画布始终是同一张。跨树节点本来就跨在两棵树的边界上,切页会把它切碎。
- **右下圆形缩略图** = 全局位置,红框标出当前视口。
- **捏合到底** = 俯瞰全貌,43 个节点一屏看完(看形态不看细节,此时不画图标与名字)。

### 8.3 详情从右侧推出,不常驻

宽 396,盖在画布上。**画布能滑之后,常驻面板就是白占视野**。

### 8.4 顶栏浮在画布之上

底下垫一道宣纸色渐隐(`linear-gradient(#F6F1E7 32%, transparent)`,高 76),
免得节点滑到标题后面糊成一团。

## 10 · 测试与验收

### 10.1 恒等性硬线(仍然适用)

**没点任何跨树节点时,`Bonus()` 的结果与改前逐字节相同** ——
`Scaling == None` 时 `sum += def.Value`,与上游规格的实现逐字相同。
40 个普通节点的前置判定同理:`Prereq == null` 时走的还是原来那条隐式推导。

Tests **纯追加**。既有的 1680 条一条不改、一条不红。

### 10.2 必须有的新测试

- `CrossNodeTests`:
  - 三个跨树节点的前置**两侧都要满足**(只满足一侧时 `CanUnlock` 为 false)
  - 前置是**谓词不是具体节点**:金脉 L3 与火脉 L3 都能满足「五行任一 L3」
  - `CountOwned` 遍历固定顺序,不受 `UnlockedPerks` 插入顺序影响
- `PerkScalingTests`:
  - `PerWuxingDeep` 的计数只数 L3/L4,不数 L1/L2
  - `PerSpecializedElement` **夹上限 2**(点满五系 L2 时仍是 2 不是 5)
  - 缩放节点未点亮时,`Bonus()` 与改前逐字节相同
- `AllNodes_UnlockByLevel22` 追加覆盖 3 个跨树节点

### 10.3 断言 API 限制(CLAUDE.md,仍然适用)

禁用 `Is.AnyOf` / `Is.All.AnyOf`;`Does.Not.Contain(x)` 只在 x 是 string 时可用;
集合判包含写 `Assert.That(list.Contains(x), Is.True/False, "…")`;
定位仓库根只能用 `TestContext.CurrentContext.TestDirectory`;测试禁止直接引用 Newtonsoft。

### 10.4 Presentation 没有自动化测试

改完必过离线编译,且**人眼过一遍**:五态在极坐标下的视觉、跳转锚点、缩略图视口框、
详情推出、跨树节点的双前置连线。CLAUDE.md 记的两类静默缺陷(三处同时接、
共享状态的所有读取点)仍然适用。
