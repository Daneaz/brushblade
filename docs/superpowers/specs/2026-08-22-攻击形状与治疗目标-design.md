# 攻击形状与治疗目标 — 设计稿

日期:2026-08-22
状态:已与用户逐节确认,待写实现计划

## 1. 目标

两件事,共用一个「目标裁定」的改造:

1. **攻击模式多样化**:把今天只有「单体 / 全体」两档的伤害,扩成一套**目标形状库**——单体、全体、横扫(整排)、顺劈(左右相邻)、贯穿(整列)、连发(N 发循环)。作用于**玩家出字**与**召唤物普攻**两侧。
2. **治疗可选目标**:单体治疗从「只能治自己」改为出字时选一个目标(玩家或某只存活召唤物)。

## 2. 范围

**做**:`TargetShape` 模型、`Targeting.ExpandTargets` 纯函数、`ApplyEffects` 伤害分支重构、敌人列坐标与固定格位、召唤物侧形状字段(含存档)、治疗目标选择(Core + UI)、`BossSkill.Pierce` 改名、管线三个新 token、字表重新分配与配值、配套测试。

**不做**:
- 敌人普攻的形状多样化(用户 2026-08-22 明确排除;`AttackRange`/`AttackFocus` 一行不动)。
- 存档迁移(项目未上线,见记忆「存档不需要兼容」)。
- 新增箭矢类字(见 §11 未决 U1)。
- `BattleView.cs` 的整体拆分重构。

## 3. 形状库

### 3.1 建模:正交修饰,不是新的 EffectKind

在 `EffectDef` 上新增一个字段:

```csharp
public TargetShape Shape { get; }        // 缺省 Single
public int ShapePercent { get; }         // 非主目标的伤害百分比,缺省 100
public int Shots { get; }                // Volley 专用,发数
```

```csharp
public enum TargetShape
{
    Single,   // 单体(缺省)
    Sweep,    // 横扫:主目标所在整排
    Cleave,   // 顺劈:主目标 + 同排左右相邻
    Skewer,   // 贯穿:主目标所在整列(前 + 后)
    Volley,   // 连发:后排优先依次 N 发,不足则循环补足
}
```

**`EffectKind.DamageAll` 保留为独立 kind,不并入 `Shape.All`**。21 张全体字因此一个字节不改——这条是本设计的**恒等性基线**(见 §10)。付出的代价是模型里有两种表达「打多个」的方式,收益是改造期间「现有伤害逐位不变」这条守卫始终可断言。

**为什么不给每种形状加一个 `EffectKind`**:`ApplyEffects` 里那段伤害循环含斩杀、暴击、护甲、多段四层逻辑,复制五份必然腐化;更要命的是 `NeedsTarget`、`RestrictedToFrontRow`、`CanTarget` 三处**白名单**要各加一笔,而 [BattleEngine.cs:823](../../../Brushblade/Assets/_Project/Core/BattleEngine.cs) 那条注释记的正是 2026-08-06 单体驱散漏在白名单外导致 `_enemies[-1]` 越界崩溃。形状做成正交字段,这三处判据只需各改一行「看 `Shape`」,不随形状数量增长。

### 3.2 几何定义

坐标系:敌方 3 列 × 2 排。`EnemyState.Row`(已有)+ `EnemyState.Column`(新增,0..2)。

| 形状 | 中文 | 覆盖 | 主目标 | 上限 |
|---|---|---|---|---|
| `Single` | 单体 | 主目标 | 必选 | 1 |
| `Sweep` | 横扫 | 主目标那一排的全部存活者 | 必选 | 3 |
| `Cleave` | 顺劈 | 主目标 + 同排 Column±1 的存活者 | 必选 | 3 |
| `Skewer` | 贯穿 | 主目标那一列的全部存活者(前 + 后) | 必选 | 2 |
| `Volley` | 连发 | 后排优先按列序取,循环补足 N 发 | **免选** | N 发 |

「全体」不在这张表里——它是 `EffectKind.DamageAll`,不是形状(见 §3.1)。

- **空位不递补**:顺劈打边上那格只溅一侧;整排只剩 1 只,横扫就只中 1 只。形状是几何,不是「保证打满 K 个」。
- **顺劈与横扫的区别**只在边缘格与残阵:满编前排两者等价(都是 3 只),打边格时顺劈只中 2 只。这是刻意的——顺劈奖励「瞄准中间」,横扫不吃站位。
- **连发免选**:目标全自动,不进选目标态,点了就打,交互上与 AOE 同档。这是它与其余形状在手感上的分工——形状类问「你瞄哪」,连发问「打几发」。

### 3.3 连发的循环补足

`Targeting` 先排出候选表(后排按 Column 递增,再前排按 Column 递增,只收存活者),然后**从头循环发射直到打满 N 发**。3 只怪打 4 发 = A、B、C、A。

- **确定性,不摇随机数**。这一条是硬要求:上千条带种子的既有测试靠随机流不位移才不会整体变红(见 [Targeting.cs:20](../../../Brushblade/Assets/_Project/Core/Targeting.cs) 关于「候选只有一个时不摇随机数」的同类推理)。
- **后果:单敌 Boss 战时连发退化为满额 N 倍单体**。这是好消息(它不会在 Boss 战废掉),但也是数值陷阱——见 §9 配值口径。

### 3.4 排位限制

| 形状 | 受前排阻挡? | 理由 |
|---|---|---|
| `Single` | 是(现状) | 不变 |
| `Sweep` / `Cleave` | 是,**只判主目标** | 溅到的必然同排,判完主目标就够 |
| `Skewer` | 是,**只判主目标** | 它打的是「主目标那一列」,前排未清空时主目标只能是前排,穿到后排是这个形状的全部意义 |
| `Volley` | 否 | 远程,天然越阵 |

`RestrictedToFrontRow` 因此改为:含 `DamageSingle` 且 `Shape != Volley` 且未标偷袭 → 受限。偷袭(`CanStrikeBackline`)与形状正交,可共存(「偷袭的顺劈」= 直接点后排再溅它左右,规则自洽)。

## 4. 目标裁定:`Targeting.ExpandTargets`

新增纯函数,住在 `Targeting`——「打谁」的唯一裁定处这条纪律不破:

```csharp
public static IReadOnlyList<int> ExpandTargets(
    IReadOnlyList<EnemyState> enemies, int primaryIndex,
    TargetShape shape, int shots);
```

- 返回**敌人下标**的有序表,首项恒为主目标(`Volley` 除外,它没有主目标)。
- **表内可含重复下标**——`Volley` 循环补足时同一只怪会出现多次,调用方按「每项一次结算」处理即可,不去重。形状类(`Sweep`/`Cleave`/`Skewer`)返回的表则恒不重复。
- 只读、不摇随机、不碰引擎状态,可独立单测。
- 引擎与表现层共用:UI 的「会打到哪几格」预览高亮直接调它,**不自己推几何**。这与 `CanTarget` 同一条理由——玩家看到能打的和引擎认为能打的一旦分头计算,迟早失配。

## 5. 结算规则

`ApplyEffects` 的 `DamageSingle` 分支改成两层:先 `ExpandTargets` 求目标表,再对每个目标跑**原来那段**循环。目标表长度为 1 时逐位等价于今天。

| 规则 | 裁定 | 理由 |
|---|---|---|
| 主目标伤害 | 100% | |
| 非主目标伤害 | `ShapePercent`(字表配) | 横扫/贯穿可配 100,顺劈建议 50 |
| 护甲 | **逐目标各减各自护甲** | 与 AOE 同口径([BattleEngine.cs:1444](../../../Brushblade/Assets/_Project/Core/BattleEngine.cs)),「把总量摊成多份」对点数甲的天然惩罚正是形状类伤害的代价 |
| 暴击 | 逐目标独立摇 | 与 AOE 同口径 |
| 生克 | 逐目标独立结算 | 目标属性各异 |
| 斩杀 / 多段(`HitCount`)/ 穿透(`Pierce`) | **只作用主目标** | 否则一张字能三连处决;多段 × 形状的组合复杂度也不值得 |
| 连发的每一发 | 各自减护甲、各自摇暴击、各自过生克 | 与形状同构;斩杀/多段同样只作用于**第一发** |

**摇点顺序**:暴击的摇点排在「目标存活」与「处决」两条守卫之后,与现状一致——目标死了不该白摇一次,否则「这一发消耗几个随机数」会取决于血量。

## 6. 敌人固定格位(列坐标)

贯穿要求「列」在视觉上读得出来,而今天两排都是 `HorizontalLayoutGroup` + `MiddleCenter` 居中排列([Ui.cs:48](../../../Brushblade/Assets/_Project/Presentation/UI/Ui.cs)),前排 2 只、后排 3 只时前排会落在后排的缝上。用户 2026-08-22 拍板改**固定格位**。

### 6.1 Core

- `EnemyState.Column`(0..2,`internal set`)**进 `EnemySnapshot`** ——与 `Row` 同理:同一个 Id 的两只怪列不同,而 `Restore` 是按 Id 查 `Def` 的,不存就会在读档时被合并。
- `AssignRows()` 改名 `AssignSlots()`,分排的同时按该排已占列数依次分列。
- **分裂(`Split`)产生的克隆要找空列**:`RowWithSpace` 旁边加 `ColumnWithSpace`。两排都满(6 只)时分裂本就被 `场上敌人 <4` 的守卫挡住,但守卫在别处,这里仍要兜底——找不到空列则不分裂。

### 6.2 Presentation

`BattleView` 画敌人从「遍历 `Battle.Enemies` 顺序塞进两个 Row」改为**按 (Row, Column) 塞进 3 个固定格位**,空格位放透明 `LayoutElement` 占位(不画占位块——用户不喜欢常驻占位块,见 commit `03ef408`)。

**顺带修掉**:敌人死后剩下的怪居中重排导致的「跳位」。固定格位后尸体留在原地,视觉稳定。

## 7. 召唤物侧

`SummonPassive` 新增三个字段,与已有的 `Ranged` **正交**:

```csharp
public TargetShape Shape { get; set; }   // 缺省 Single
public int ShapePercent { get; set; }    // 缺省 100
public int Shots { get; set; }           // Volley 用
```

- **`Ranged` 保留不动**:它管「能不能越过前排」,形状管「打几个」。合并会重演 `EnemyAbility` 那种互斥陷阱([EnemyDef.cs:24](../../../Brushblade/Assets/_Project/Core/EnemyDef.cs) 的注释就是这个教训)——「远程的顺劈」是完全合理的组合。
- 召唤物出手时:`PickEnemyTargetForSummon` 求主目标(现状不变),再 `ExpandTargets` 展开。**两侧共用同一个几何函数**,不写第二份。
- `SummonPassive` 进存档,`Clone()` 与快照要一并补新字段。**这是本设计唯一碰存档结构的地方**(加上 §6.1 的 `Column`)。

## 8. 治疗可选目标

### 8.1 接口

- `Cast(...)` 新增可选参数 `int allySlot = Targeting.PlayerTarget`(−1 = 玩家,0..5 = 召唤物槽)。
- 新增静态判据 `NeedsAllyTarget(def, attackMode)`,与 `NeedsTarget` 对称,UI 据此进入「选友方」态。
- **免选**:场上没有存活召唤物 → 自动锁玩家,不弹选择。与「单敌免选」同一条口径。
- 目标槽为空 / 是尸体 → `BattleError.InvalidTarget`。死者归 `Revive` 管,治疗不负责。

### 8.2 治疗量

走同一个 `WuxingResolver.ResolveEffect`。**生克算的是配方内部的元素关系,与目标是谁无关**,所以治召唤物与治玩家同值,超出 `MaxHp` 的部分丢弃。

### 8.3 持续治疗(沐)

`StatusEffect` 新增 `TargetSlot`(缺省 −1 = 玩家),与已有的 `TargetAll` 同构。HoT 仍挂在**玩家的 `StatusBag`** 上,结算时按槽位分发。

**为什么不给 `SummonState` 加状态容器**:那要新增 `SummonSnapshot` 字段,而漏补是静默的([RunSnapshot.cs:9](../../../Brushblade/Assets/_Project/Core/RunSnapshot.cs) 那条警告)。全字表只有 1 张 HoT 字,不值得为它引入一整套召唤物状态系统。

**目标召唤物死亡 → 该条 HoT 立即失效**,不空转到期。空转会让玩家的一次出字被隐形浪费。

### 8.4 群治不动

`HealAll`(淋)仍是无需选目标的全体治疗,作为稀有度更高的上位档。

### 8.5 事件与 UI

- `Heal` 事件用 `SecondIndex` 带槽位(−1 = 玩家),与 `Summon` 事件报落位槽的写法一致,**不新增事件类型**。
- UI 复用已有的槽位点选交互(`_slotPicking`,拖字召唤时点亮空槽),点亮对象改成「玩家头像 + 存活召唤物格」。

## 9. 数据管线与字表

### 9.1 新 token(写进《技能机制详表》)

| token | 落到 `chars.json` | 备注 |
|---|---|---|
| `Sweep` / `Cleave` / `Skewer` | `shape="Sweep"` … | 无数值布尔标记,只修饰 `DamageSingle` |
| `ShapePercent N` | `shapePercent=N` | 缺省 100 |
| `Shots N` | `shape="Volley"` + `shots=N` | |

⚠️ 三个 token **绝不能进 `VALUELESS_EFFECTS`**:那会让它落成一条 `kind="Sweep"` 的独立效果,而 `EffectKind` 里没有这个值,`ConfigLoader` 在加载期直接抛 `ConfigException`(与 [extract_values.py:134](../../../tools/pipeline/extract_values.py) 头上 `Backline` 那条注释同一个坑)。它们是**修饰位**,与 `Backline` / `Pierce` / `HitCount` 同类。

⚠️ `extract_values.py` 的手写映射表认不得的标记会**静默消失**,新 token 要逐张表核一遍(记忆「管线 token 表静默丢弃」)。

### 9.2 字表分配(口径,配值时逐字拍板)

| 形状 | 属性 | 候选字 | 字义 |
|---|---|---|---|
| 顺劈 Cleave | 金 | 劈、铡、镰 | 挥砍带到旁边 |
| 横扫 Sweep | 金 / 土 | 锬、剿(现 `DamageAll`,**降档**)、砸、碾 | 横向扫荡 / 重击震荡 |
| 贯穿 Skewer | 金 | 锥、鍂、刲 | 直刺穿透 |
| 连发 Volley | 水 / 土 | 涛、洪、沏、崩、碎 | 浪头一波波 / 碎石连砸 |
| 全体(`DamageAll`,非形状) | 火(不动) | 燚、焱、焚、燊、爆、烈 | |
| 单体 Single | 金系高伤 + 水系控制(不动) | | |

**刺 不改贯穿**:它已标 `Backline`(偷袭,直接点后排),与贯穿(打前排穿到后排)是两种破阵思路,同字承载会互相抵消。

**剁 不改形状**:它已是 `HitCount 2` 的多段单体,多段 × 形状读起来绕(§5 已裁定多段只作用主目标),保持多段。

### 9.3 配值口径

- **降档是刻意的重平衡**:锬 / 剿 从全体(6 只)降到横扫(3 只),数值要按第 10 章基础值规矩重定,不是照抄现值。
- **连发字必须按「N 发全中」定基础值**,约为同稀有度单体字的 1/N 再上浮补护甲损耗。涛 现在是 `DamageAll 50`,直接挂 `Shots 3` 会变成对单目标 150——那是新字,不是改字。
- `chars.json` 是产物,改字表走**详表 → `extract_values` → `export_chars`**(记忆「chars.json 是管线产物」)。

## 10. 命名冲突:Boss 技改名

「贯穿」这个中文名归新形状(用户 2026-08-22 拍板)。冲突有两处:

| 标识符 | 处置 | 理由 |
|---|---|---|
| `EffectDef.Pierce`(护甲穿透点数) | **不动** | 它是「穿甲」不是「贯穿」,中文文案本就不叫贯穿;且它是 `chars.json` 的 `pierce` 字段,改名要动管线与 87 张字 |
| `BossSkill.Pierce`(Boss 蓄力技) | **改名 `BossSkill.Impale`,中文「洞穿」** | 让出「贯穿」这个中文名 |
| 新形状 | 代码 `TargetShape.Skewer`,中文**「贯穿」** | 代码名不叫 `Pierce`——`effect.Shape == TargetShape.Pierce` 与 `effect.Pierce = 15` 在同一个类上并存极易读错 |

`BossSkill` 改名波及:枚举定义、`BattleEngine` 的 case、`EnemyInfo` 两处中文文案、`enemies.json` 的 6 个 Boss 字映射(雷/霆/钧/刀/石/飞)、5 处测试。它进快照(`ChargingSkill`),但项目未上线不需要迁移。

## 11. 恒等性与测试

### 11.1 恒等性硬线

**基准种子下,全部现有伤害字的伤害序列与改前逐字节相同**。守法:

- 现有 87 张伤害字 `Shape` 全部缺省 `Single`,`ExpandTargets` 返回单元素表,循环退化为原路径;
- 连发与形状都不摇新随机数,随机流不位移;
- P1 阶段**只接线不配值**——字表一个数不改,新形状零张字在用。配值单独放 P4。

放弃这条就要把改造拆成「接线 / 配值」两步分别验证(记忆「恒等性硬线」),成本更高。

### 11.2 测试

- `TargetingTests`:`ExpandTargets` 的几何用例——四种形状 × (满编 / 残阵 / 边缘格 / 空位不递补);连发的循环补足与单敌退化。
- `DamageVariantTests`:逐目标独立护甲、斩杀与多段只作用主目标、`ShapePercent` 的取整。
- 治疗:选目标合法性、免选、溢出丢弃、尸体拒治、HoT 目标死亡即失效。

## 13. 未决与风险

- **U1 箭矢字缺位**:全字表 178 字里没有任何箭/矢/射/弓/弹字,连发只能靠机制立身份(水系浪头、土系碎石),字义上不如「射击」贴切。真要补一批箭矢字,需要新部件入池 + 配方,单开子项目——且会撞上已知的「没配方的字拿不到」问题(炼/杨/戟/塌 4 个待补配方)。
- **R1 顺劈与横扫区分度偏小**:满编前排两者等价。若实测下来玩家读不出差别,退路是砍掉顺劈只留横扫(形状是正交枚举值,删一个不影响其余)。
- **R2 固定格位的视觉回归**:敌人不再居中,残阵时会偏在一侧。P6 需要 Play 验收,退路是给整排加一个整体居中的偏移(保持列间距不变即可维持列对齐)。
- **R3 P5 配值工作量**:降档 + 连发重定基础值涉及约 14 张字,是本设计里最耗人工判断的一期,不适合交给 subagent 自动配。
