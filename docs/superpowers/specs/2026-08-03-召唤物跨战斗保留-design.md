# 召唤物跨战斗保留 —— 设计（2026-08-03 拍板）

## 问题

召唤物（木系主打，前排承伤 + 回合末反击）活不过一场战斗。`BattleEngine._summons` 是战斗内私有
List，`RunEngine.NewBattle` 每层新建引擎即归零；只有战斗内断点存档（`BattleSnapshot.Summons`）
能把它复原，层间一律清空。

护盾则是全程延续的：`RunEngine._carriedNormalShield` 在战斗打赢时从 `Battle.ShieldNormal`
抓走（RunEngine.cs:451），开下一层时灌回 `BattleEngine` 构造（RunEngine.cs:631），并写进
`EndlessSaveState.NormalShield` 跨段、跨挂起续爬保留。

## 拍板结论

召唤物改为与**普通护盾等价**的全程延续：层间保留、段末结算后仍在、退出游戏读档回来还在，
**直到死亡或整次登塔结束**。

配套语义：

- **带走残血，不回满**：挨过打的召唤物按当前 Hp 进下一场（`MaxHp` 另存，两者脱钩）。
- **死掉的不带走**：只带 `Alive` 的，槽位释放，下一场从 0 号索引重新排布。
- **上限不变**：`SummonCap = 4` 照旧。带进来的算进存活数，满编再召唤仍走
  `BattleError.SummonCapFull` 强阻断 → UI 确认后 `replaceSummon` 顶替，判定逻辑无需改动。

## 携带载体

复用现成的 `SummonSnapshot`（Core/RunSnapshot.cs:48，字段 Char / Element / Hp / MaxHp / Attack）。
不新增类型：这个结构本来就是给战斗内断点存档用的，直接拿来当跨战斗携带态，两级存档都能
原样序列化，也省掉一层 State ↔ Snapshot 转换。

## 三条传递路径

召唤物要覆盖与盾相同的三条路径，缺一条就会出现"某种退出方式下召唤物凭空消失"：

| 路径 | 承载者 | 触发时机 |
|---|---|---|
| 段内跨层 | `RunEngine._carriedSummons` | 打赢一层 → 开下一层 |
| 跨段 | `EndlessSaveState.CarriedSummons` | 段末结算 → 下一段建新 `RunEngine` |
| 战斗中挂起 | `InProgressRun.Run`（已有，含 `BattleSnapshot.Summons`） | 无需改动 |

## 改动清单

### 1. Core / `BattleEngine`

- 构造函数新增可选参 `IReadOnlyList<SummonSnapshot> startingSummons = null`，紧跟
  `startingNormalShield` / `startingPersistShield` 之后（语义并列）。ctor 内用
  `SummonState.Restore` 逐个灌进 `_summons`。
- 其余不动：`SummonCap`、`AliveSummons()`、`SummonReplaceCountOf`、承伤/反击逻辑全部照旧。

### 2. Core / `RunEngine`

- 新增字段 `List<SummonSnapshot> _carriedSummons`，与 `_carriedNormalShield` 并列。
- 构造函数新增可选参 `IReadOnlyList<SummonSnapshot> startingSummons = null`。
- `AdvanceAfterBattle`（RunEngine.cs:450 一带，与 `_carriedNormalShield = Battle.ShieldNormal`
  同处）：打赢时把 `Battle.Summons` 中 `Alive` 的逐个 `Capture()` 存进 `_carriedSummons`，
  死尸丢弃。
- `NewBattle`：把 `_carriedSummons` 传给 `BattleEngine`。
- 公开 `IReadOnlyList<SummonSnapshot> CarriedSummons`（与 `CarriedNormalShield` 并列）。
- `Capture()` / `Restore()` 各加一条；`RunSnapshot` 新增 `List<SummonSnapshot> CarriedSummons`。

### 3. Data / 存档

- `EndlessSaveState` 新增 `List<SummonSnapshot> CarriedSummons { get; set; } = new()`。
- 旧档兼容不需要迁移代码：`SaveSerializer` 无自定义 converter，Newtonsoft 默认行为下缺失字段
  保持属性初始值（空 list），等价于"旧档没有携带召唤物"。

### 4. Presentation / `GameRoot`

- `WriteCarriedSnapshot`、`OnFloorAdvanced`、`OnSegmentEnded` 三处各写一行
  `snapshot.CarriedSummons = ...`，位置紧邻现有的 `snapshot.NormalShield`。
  （`OnFloorAdvanced` 时新战斗已开，此刻 `Battle.Summons` 与 `CarriedSummons` 同值，
  统一取 `run.CarriedSummons` 口径一致。）
- `StartSegment` 建新 `RunEngine` 时传 `startingSummons: snapshot.CarriedSummons`。
- 塔结算把 `_meta.Endless` 置 null，下次登塔自然空场 —— "直到整次登塔结束"落在这里，无需额外清理。

### 5. 表现层

无改动。`BattleView.DrawSummons()` 每帧按 `Battle.Summons` 重绘，血条/攻力全数据驱动，
带过来的召唤物开场即正确显示。（`GameRoot` 属 Presentation 层，改完仍须跑离线编译。）

## 已知的平衡影响（本次不处理）

木系召唤的实际强度会上一个台阶：玩家可以在杂兵层攒满 4 只满血前排再踏进 Boss 层，而前排是
"整次攻击由首个存活召唤物承受、不溢出"（BattleEngine.cs:461），等于能把 Boss 的单体大招整段吃掉。
若后续需要回调，首选旋钮是给带走的召唤物加衰减（例如带走时血量减半），而不是退回每场清空。

## 顺带发现的既有问题（不在本次范围）

`OnFloorAdvanced` 确实不写 `snapshot.NormalShield`（金汤每关补的盾要到 `OnFloorCleared`/
`OnSegmentEnded` 才落进 `EndlessSaveState`），而 `RunEngine.BeginNextBattle` 每层都会
`_carriedNormalShield += _perFloorNormalShield`。原以为这是个 bug：新层刚开打就挂起，
`EndlessSaveState.NormalShield` 还是上一层结束的旧值，会丢当层补的盾。

最终评审证明这个场景走不通：`snapshot.NormalShield` 只在 `resume == null` 的段首被消费
（GameRoot.cs:207-208），而段内挂起一律走 `InProgress`（`onProgress: SaveNow` 每次玩家
行动后都落盘，摊平的是 `RunEngine.Capture()` 里的 `CarriedNormalShield`，与
`EndlessSaveState.NormalShield` 是两个字段），`RunEngine.Restore` 根本不读
`EndlessSaveState` 的这些中段字段——那一刻 `InProgress.Run.CarriedNormalShield` 已经是
当层补过盾的准值，不会用到那个滞后的 `EndlessSaveState.NormalShield`。

真正的问题是**字段口径不一致**：`EndlessSaveState` 的中段字段有的每层写（`Library`/
`Pool`/`PlayerHp`/`CarriedSummons` 等，见 `OnFloorAdvanced`），有的只在层清算/段末写
（`NormalShield`/`PersistShield`，见 `OnFloorCleared`/`OnSegmentEnded`）。眼下无害是因为
断点续爬全程走 `InProgress` 这条更准的路径，`EndlessSaveState` 的中段字段本就不是
唯一真相；但下次再加携带字段前，值得先把这套口径统一，省得每次都要重新论证
"为什么不会丢"。记录待办，与本次改动无关。
