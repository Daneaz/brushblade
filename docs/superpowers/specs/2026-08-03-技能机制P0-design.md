# 技能机制 P0 落地 · 设计规格

> 2026-08-03 · 配套 `docs/design/字选型/技能机制详表.md`(139 字实现规格)
> 与 `技能四类判定-评分版.md`(判类 + 评分 + 稀有度)

## 一 · 背景与目标

`技能机制详表.md` 给出了 139 字的完整实现规格,但它包含 8 块彼此独立的工作
(稀有度/AP、战场上限、掉落改造、灼烧生克、14 类新 EffectKind、数值落地、HP 封顶、RewardPool 冲突),
不是一轮能做完的。本 spec 只切其中一块。

**目标:让 85 字可用(占全表 61%),并验证第 30 层的数值手感。**

数值重定标的动因是实测发现旧锚点在 30 层全面失效:

| 旧值 | 30 层现实 | 结果 |
|---|---|---|
| 金档护盾 20 | Boss 一击 28~35 | 挡不住 |
| 金档召唤 10 血/只 | 杂兵一击 15 | 一击必死 |
| 金档单攻 45 | 杂兵 53 血 | 秒不掉 |

## 二 · 范围

### 做

| 块 | 内容 |
|---|---|
| A | `CardRarity` 加 `Gold=7`;AP 一律 1;拆解免费 |
| B | 召唤物上限 4→6;新增敌人同屏上限 6 |
| D | 灼烧接入生克(改 `BurnTick`) |
| F | 65 字数值 + 配方落地 `chars.json` |
| E-P0 | 6 个新 `EffectKind`,再解锁 20 字 |

### 不做(各自独立成 spec)

- **掉落改造**(回合掉落改随机字、战利品 5 选 2、复活 5 选 2 ×2)——依赖新增「出战牌组」字段,
  且与 `enemies.json` 里按层段写死的 `RewardPool` 冲突,需单独设计。
- **P1~P3 扩展**(`Dispel`/`Immunity`/`ArmorBreak`/`Execute`/`Buff`/召唤物被动等 14 类)。
- **玩家 HP 封顶方向**:`MetaRules.MaxHpFor` 硬封顶 100,而怪物 scale 无上限线性增长,
  50 层后满血活不过一轮。三个方向(解除封顶 / 玩家数值随深度缩放 / 接受靠盾生存)待定。
- **字表本身的增删**:139 字的评分与判类不在本轮变更范围内。

## 三 · 已定口径

| # | 口径 | 理由 |
|---|---|---|
| 1 | **Slow = 半速**(每 2 回合行动一次);Root 归入 Freeze | 引擎敌方回合是「所有存活敌人依次各出手一次」的简单循环,**没有出手顺序概念**,「延后出手」不产生任何区别 |
| 2 | 减伤**乘法**叠加 | 天然趋近但不达 0,无需硬上限。六字集齐 ≈ 减伤 65% |
| 3 | **同字减伤不叠加**,重复施放只刷新 | 否则跨段持久下六字各出 5 次 ≈ 承伤 0.5%,等于免疫 |
| 4 | 减伤**本段持久**(跨战斗);控制/DOT 走固定回合数 | 与护盾「段内持久」(v0.7)同口径 |
| 5 | **多步合成**;配方 = IDS 一级拆解 | 推翻 `第4章 4.3` 的 Mode A 一步合成 |
| 6 | **五系叠字链 15 条配方人工写死**,不走 IDS | IDS 会把 燚 拆成 `炏+炏`,污染叠字链并可能成环 |
| 7 | 非五行部件入库为叶子部件;**部件池固定 10**,超出由玩家丢弃 | 105 种部件不需要都有复用价值;配方提示只对池内 ≤12 个部件做倒排匹配 |

### 3.1 灼烧 vs 流血

| 状态 | 属性 | 生克 | 对金系 |
|---|---|---|---|
| 灼烧 | 火 | 走生克(**只克制,不相生**) | ×1.5 |
| 流血 | **无属性** | **不走** | ×1 |

层数是平值,相生已在施加时体现过,故 tick 只结算克制。
两者是不同的 DOT,**不可互相降级替代**。

### 3.2 五系叠字链配方(部件在前、低阶字在后)

| 系 | 二叠 | 三叠 | 四叠 |
|---|---|---|---|
| 木 | 林 = 木+木 | 森 = 木+林 | 𣛧 = 木+森 |
| 水 | 沝 = 水+水 | 淼 = 水+沝 | 㵘 = 水+淼 |
| 火 | 炎 = 火+火 | 焱 = 火+炎 | 燚 = 火+焱 |
| 金 | 鍂 = 金+金 | 鑫 = 金+鍂 | 𨰻 = 金+鑫 |
| 土 | 圭 = 土+土 | 垚 = 土+圭 | 㙓 = 土+垚 |

已校验:DAG 无环,四叠字需 3 步(3 AP)+ 4 个同系部件。
**实装 `chars.json` 有 10 个字原料顺序相反**(森/淼/焱/鑫/垚 与 𣛧/㵘/燚/𨰻/㙓),需一并修正。

## 四 · 分步设计

四步按**风险递增**排列,每步独立可验证、可随时停止。

### 第 1 步 · 常量层

| 文件 | 改动 |
|---|---|
| `Core/CharDef.cs` | `CardRarity` 加 `Gold = 7`;`ApCostFor(rarity) => 1` |
| `Core/BattleEngine.cs` | `SummonCap` 4 → 6;新增 `EnemyCap = 6` |
| `Core/BattleEngine.cs` | `Dismantle()` 去掉 `if (Ap < 1)` 检查与 `Ap -= 1`(合 `Compose()` 保持 1 AP) |
| `Core/Endless.cs` | `BuildFloor` 敌人数 `1+min(3,…)` → `1+min(5,…)` |

⚠ 不改 `Endless.BuildFloor` 的话 `EnemyCap` 形同虚设 —— 生成侧硬上限仍是 4。

**验证**:490 个现有测试全绿。预计需改断言的文件:
`BattleEngineTests` / `BossSkillTests` / `ConfigLoaderTests`(AP)、
`RarityTests` / `BattleEventTests` / `EventTests` / `MetaTests` / `RunEngineTests`(稀有度)、
`BattleEngineTests` / `RunEngineTests`(召唤上限)。

⚠ `第10章 10.1` 的「稀有度 → AP」表与 `ApCostFor` 是同一个真相,必须同步作废。

### 第 2 步 · 灼烧接入生克

`BattleEngine.EndTurn()` 现在是:

```csharp
int tick = enemy.Burn * _burnPerStack;   // 无任何属性判定
```

改为以火属性对目标属性结算克制:

```csharp
int tick = (int)Math.Floor(enemy.Burn * _burnPerStack
           * WuxingResolver.KeMultiplier(Element.Fire, enemy.Element));
```

**验证**:新增三例 —— 火对金 ×1.5、火对水 ×0.5、火对心 ×1.0。

⚠ 这会改变火系 18 字的实际强度,对水系敌人 DOT 收益砍半,数值需实测复核。

### 第 3 步 · 数值 + 配方落地

**产出**:`chars.json` 从 20 条扩到约 123 条(65 个字 + ~58 个非五行部件)。

- 15 个已实装字:改数值 + 修正配方顺序
- 50 个新字:`effects` / `rarity` / `recipe` / `pinyin` / `gloss`
- ~58 个非五行部件:叶子条目(`element: null`、无 `effects`)

> 58 是**本轮 65 字**的实测值(已用 `split_once` 跑过)。全 139 字则需 105 种,
> 其中 86% 只服务一个字 —— 这是口径 7「用不上就丢」的由来,不是缺陷。

**相生字必须填基础值**(锚点 ÷ 3),引擎会自动 ×3。填错直接三倍超模。
受影响 16 字,其中本轮落地的 9 个:焚 燊 灿 蒸 溎 沏 刲 嶘,加降级版 崟/铠/漜。

**实现方式**:新增管线导出脚本(`tools/pipeline/export_chars.py` 或扩展现有 `export_config.py`),
按以下顺序生成,避免手写 170 条 JSON:

1. 先写死 3.2 的 15 条叠字配方
2. 其余字用 `decompose.split_once` 生成配方
3. 收集所有非五行部件,生成叶子条目
4. 合并数值表(来自 `技能机制详表.md` 二~六章)

**验证**:`ConfigLoaderTests` 全绿 + 配方 DAG 无环校验 + 抽样验算相生字最终值不越上一档。

### 第 4 步 · P0 五类机制 + 20 字

**新增 6 个 `EffectKind`**:`Bleed` / `HealAll` / `HealOverTime` / `Freeze` / `Slow` / `DamageReduction`。

**状态存储逐字段加**(不引通用状态容器 —— 这些状态语义异构:减伤要按字 ID 去重、
HoT 是「每回合量+剩余回合」二元组,强行塞进 `Dictionary<Kind,int>` 反而更复杂。
等 P1~P3 状态涨到十几种时再重构):

| 位置 | 新字段 |
|---|---|
| `EnemyState` | `Bleed`、`BleedTurns`、`FreezeTurns`、`SlowTurns` |
| `BattleEngine` | `_hots`(每回合量/剩余回合/是否群体)、`_damageReductions`(`Dictionary<字ID, 百分比>`) |

`_damageReductions` 用字 ID 作键,**天然满足口径 3「同字不叠加」**;取值时对所有 value 连乘。

**`EndTurn` 结算顺序**:

1. 灼烧 tick(走生克)
2. **流血 tick(不走生克)**
3. HoT 回复(玩家 / 群体含召唤物)
4. 召唤物反击
5. 敌方行动(判 `FreezeTurns` 跳过、`SlowTurns` 半速)
6. 所有状态回合数递减

**解锁 20 字**:锯(Bleed)、淋润(HealAll)、沐滋(HoT)、冰冻溺埋坑藤(Freeze/Stun)、
洼凝冷(Slow)、铠崊崟磐巍(DamageReduction)、漜(减伤+Slow)。

⚠ **这 20 字的 `chars.json` 条目在本步一并写入**,不在第 3 步 —— 它们的 `effects` 引用新
`EffectKind`,提前写入会让 `ConfigLoader` 解析失败(`Enum.TryParse<EffectKind>` 认不出)。
第 3 步只落地那 65 个用现有 8 种效果就能表达的字。

**收尾三件事**(缺一会漏到 Unity 才炸):

1. `RunSnapshot` 加字段并过 `SnapshotRoundTripTests`
2. `Presentation/CharInfo.cs` 补 6 条中文文案 —— 该 switch 有兜底 `_ => e.Kind.ToString()`,
   **不会编译失败但会显示英文枚举名**
3. 跑 `tools/prescompile` 离线编译

## 六 · 风险

| # | 风险 | 应对 |
|---|---|---|
| 1 | 第 2 步改变火系 18 字实际强度,对水系敌人 DOT 收益砍半 | 第 3 步落地后实测复核 |
| 2 | 减伤跨战斗持久:一段 5 层,前期铺满后 4 层明显变轻松 | 口径 4 的必然结果,实测观察 |
| 3 | IDS 拆出的中间字与叠字链混用会使配方 DAG 成环 | 口径 6 已规避;第 3 步加无环校验 |
| 4 | AP 统一为 1 后,一回合能出 3 张金卡 | 爆发上限需实测;必要时回到「AP 按部件数计价」 |
| 5 | 拆解免费后可能无限刷部件 | 唯一约束是部件池容量 10;若失控则加次数限制 |

## 七 · 验收标准

1. `coretests` 490+ 全绿,`prescompile` 无 `error CS`
2. `chars.json` 载入无误,配方 DAG 无环
3. 抽样验算:相生字最终值(基础值 ×3)落在本档区间,且不触及上一档锚点
4. 手动验证第 30 层:金档护盾能挡 Boss 一击(28~35)、金档单攻能秒杀杂兵(53 血)、
   金档召唤物(30 血)挨杂兵一击(15)不死
