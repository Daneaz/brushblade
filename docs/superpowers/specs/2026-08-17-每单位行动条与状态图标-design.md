# 每单位行动条 · 状态图标化 · 设计规格

> 2026-08-17 · 废止 `2026-08-15-ATB回合制改造-design.md` §4.4 的顶部行动条(`TurnBar`)

## 一 · 背景

ATB 改造(2026-08-15)给战斗装上了 CTB 调度,行动顺序的表现落在**顶部一条全局行动条**上:
最左是当前行动者,往右是 `Forecast` 出的未来 7 拍(`TurnBar.cs`)。

这条带有两个问题:

1. **信息与单位分离**。玩家要判断「这只怪什么时候打我」,得在顶部一排 chip 里找到它的 id,
   再数它排第几 —— 而它的血量、状态、属性全在下面的卡片上。同一只怪的信息被劈成两处。
2. **它是预测,不是状态**。`Forecast` 读的是当前计量器往前推演,场面一变就失效
   (`TurnScheduler.cs:143` 的注释明写「不许缓存」)。玩家看到的是一串会跳变的名字,
   而不是「谁攒了多少」这个真实且连续的量。

本 spec 把行动条**下沉到每个单位自己身上**:玩家、每个召唤物、每个敌人各有一条,
读各自的 `ActionMeter`,并让它在推进时**匀速流动**而不是跳变。

同一批改动顺带把战斗界面的**状态 chip 换成图标**——不是审美偏好,是版面预算:
每个单位多一条行动条要吃 12–15px,而状态 chip 是敌人卡里最占宽的一项
(「减速 −50」「致盲 −20%」),图标化把它压窄,换行概率随之下降。

### 1.1 现状

| 处 | 现在 | 位置 |
|---|---|---|
| 行动顺序 | 顶部全局条,8 格 chip,读 `Forecast(7)` + `LastActor` | `TurnBar.cs`,屏高 0.855–0.900 |
| 敌人状态 | 文字 chip 走 `Ui.ChipFlow`,最多 2 行,超出从**尾部**丢弃并补「+N」 | `BattleView.cs:859-907` |
| 玩家状态 | 文字 chip 走 `Ui.Chip`,单行 `PlayerStatus` Row,按需创建 | `BattleView.cs:619-701` |
| 召唤物 | 无状态显示;攻/盾/被动各占一行文字 | `BattleView.cs:741-746` |

计量器本身**已经全部就位**,Core 侧不缺数据:

- `BattleEngine.PlayerActionMeter`(public get)
- `EnemyState.ActionMeter` / `SummonState.ActionMeter`(public get,`internal set`)
- 满值 `TurnScheduler.Threshold = 100`,速度钳在 `[25, 400]`

## 二 · 范围

### 做

| 块 | 内容 |
|---|---|
| 1 | 删 `TurnBar`,敌人区收回它占的屏高 |
| 2 | 17 个状态图标:程序化出图(SVG → `rsvg-convert` → PNG) |
| 3 | `Icons` 加载器 + `ChipSpec` 支持图标,带汉字兜底 |
| 4 | 战斗界面**状态类** chip → 图标(+ 数值);其余 chip 一律不动 |
| 5 | 三处行动条:敌人卡、召唤物格、玩家区 |
| 6 | Core:`SchedulerStep` 加 `Ticks`,`BattleEngine` 暴露 `LastAdvanceTicks` |
| 7 | 匀速流动动画:`AdvanceRoutine` 里按 `Ticks × BaseMs` 插值 |
| 8 | 版面重排:敌人卡 / 召唤物格 / 玩家区的像素预算重新闭合 |

### 不做

- **不动 `Ui.Chip` / `Ui.ChipFlow` 本身的既有行为**。它们还有五个消费方
  (`BestiaryView` / `CollectionView` / `MapView` / `EnemyPreview` / `GlyphTile`),
  本次只**追加**可选的图标字段,既有调用点一行不改。
- **不图标化非状态类 chip**。属性(火/水/木/金/土/心)、`攻 12`、`护甲 3`、
  敌人能力(缺笔/叠字/标点/通假/生僻/自燃/灼身)、Boss 蓄力预告 —— 全部保持文字 chip。
- **不改这五个界面**:图鉴、收藏、地图、敌人预览弹窗、字牌。状态图标只上战斗界面。
- **不删 `Forecast`**。`BattleEngine.Forecast` / `TurnScheduler.Forecast` 及其测试保留
  ——`TurnBar` 是它眼下唯一的消费方,删掉后它成死代码,但它是 Core 的公共 API 且零维护成本,
  以后要做「接下来谁动」的提示随时能用。
- **不改任何战斗数值、不新增字、不动平衡**。
- **不出手绘美术**。图标是程序化生成的扁平矢量图形;要更高质量的美术随时可按同名替换 PNG,
  代码零改动(见 §5.4)。

## 三 · 已定口径

| # | 口径 | 理由 |
|---|---|---|
| 1 | 行动条读 `ActionMeter / 100`,显示**百分比数字** | 用户拍板。条 + 数字比纯条更好读,尤其召唤物那种窄条 |
| 2 | 敌人的行动条放在**血条下方**,不是卡片顶部 | 用户拍板。与血条成一组「这个单位的状态条」 |
| 3 | 推进时**匀速流动**,不跳变;动画播放期间条冻结 | 用户拍板。ATB 的观感全在这条上 |
| 4 | 动画时长 = `Ticks × BaseMs`,`Ticks` 由调度器给 | 只有这样「速度 100 从 0 攒满」才恒等于 `BaseMs`,严格匀速 |
| 5 | 图标只改**状态类**,带量值的做成「图标 + 数值」并排 | 用户拍板。属性/攻/甲/能力是数值与名词,图标化反而读不出来 |
| 5b | 玩家的护甲 / 闪避 / 速度**只在有增益时出**,不再常驻 | 用户拍板。角色等级给的基础值白占一行版面 —— 而版面正是本次要省的东西。详见 §5.1.1 |
| 6 | 图标取不到时**回落汉字徽章**,不留空白 | `WuxingChart.cs:37` 的注释:`Resources.Load` 取不到会静默变空 |
| 7 | 图标走 `ChipSpec` 的可选字段,不新建 `IconFlow` | 换行、优先级、尾部丢弃 + 「+N」这套逻辑一份就够,不复制 |
| 8 | Boss 蓄力预告**保持文字 chip** | 它是长文本预告(「蓄力 · 下回合:排山倒海」),`BattleView.cs:866` 的注释明写它信息价值最高、不该被丢。技能名另有 `_message` 播报,卡内这条是冗余但有用的强调 |

## 四 · 像素预算

这是本次最容易出错的部分:三个区域都在加内容,而屏高是零和的。全部按 900px 基准
(`CanvasScaler` 1600×900 按高匹配)。chip 行高 = `Ui.ChipHeight` = `fontSize + padY` = `11 + 8` = **19px**。

### 4.2 敌人卡:形象 150 → 138px

| 形象 | info 可用 | 常见(状态 ≤ 1 行) | 最坏(状态 2 行) |

| 保持 150 | 82px | 需 78px ✓ | 需 100px,**溢出 18px** |

> 纯观感取舍,审阅时可直接推翻,改动只是一个常量。

#### 5.1.1 护甲 / 闪避 / 速度:只在有增益时出(2026-08-17 用户拍板)

现在这三条读的是 `Effective*`(基础 + 增益),角色等级给的基础值也会让 chip 常驻:

```csharp
if (Battle.EffectivePlayerDefense > 0)  // 4 级角色恒有 4 点甲 → 恒显示
if (Battle.EffectiveDodge > 0)
if (Battle.EffectivePlayerSpeed != 100)
```

改为读**状态总量**,没有增益就不占版面:

| 图标 | 新条件 | 显示 |
|---|---|---|
| `defense` | `TotalMagnitude(DefenseBuff) > 0` | `+N` |
| `dodge` | `TotalMagnitude(DodgeBuff) > 0` | `+N%` |
| `speed` | `TotalMagnitude(SpeedModifier) != 0` | `+N` / `−N` |

`speed` 取 `!= 0` 而非 `> 0`:被减速是坏消息,恰恰更该让玩家看见
——「除非是 buff」的意图是「基础值不必常驻」,不是「隐藏负面」。

> ⚠ 这条**推翻** `BattleView.cs:676-684` 现有注释里的取舍(原话:「只显示增益会让 0 级增益时
> 整条消失,玩家看不到自己本来就有 4 点甲;显示合计才对得上实际结算」)。实现时**必须同步改写
> 那段注释**,否则代码与注释互相矛盾 —— 下一个读到的人会以为是 bug 改回去。
> 改完后三者与 `pierce` 同口径(读状态总量),注释可以合并说明。

底色沿用各 chip **现在的颜色**,一个不改 —— 「朱砂 = 危险 / 墨 = 控制 / 翡翠 = 增益 /
赭金 = 攻势」这层语义是既有的,图标化不该把它丢掉。

> `slow`(敌方减速,朱砂系语义)与 `speed`(玩家速度,翡翠)都源自 `StatusKind.SpeedModifier`,
> 但一个只显示负值、一个显示 `Effective` 合计值,是两条不同的信息,故给两个图标。

### 5.5 `ChipSpec` 扩展

`Ui.ChipSpec` 追加 `IconKey`(默认 `null`):

- `null` → 现有行为,一个字符没变;五个既有消费方零改动
- 非 `null` → 画 `图标(18px) + 间距 + 文字`,文字只放**量值**(`3` / `−50` / `−20%`),没量值就只画图标
- `Ui.ChipWidth` 相应加上 `18 + 间距`,`ChipFlow` 的换行/优先级/尾部丢弃/「+N」逻辑一字不改

这是「不新建 `IconFlow`」这条口径的落点:换行与丢弃规则只有一份实现。

## 六 · 行动条

### 6.1 三处规格

| 单位 | 位置 | 尺寸 | 百分比字号 |
|---|---|---|---|
| 敌人 | 血条**下方**,同 `info` VStack | 140×12 | 9 |
| 召唤物 | 血条下方 | 54×8 | 8 |
| 玩家 | 血条下方(护盾条之上) | 260×14 | 10 |

条本身复用 `Ui.Bar`(`PaperDim` 底 + 填充 + 圆角),百分比文字叠其上并加 `Outline`
——与 `HpBar` 完全同款,包括描边保对比度那一层。

填充色用 **`Theme.Gold`(赭金)**:血条是朱砂、护盾条是翡翠,行动条须与两者都可区分。

### 6.2 Core 改动:`Ticks`

`TurnScheduler.Advance` 内部已经算出了推进拍数(`TicksUntilAnyFull`),但算完就丢。
表现层需要它来定动画时长。

```csharp
// SchedulerStep 追加
public int Ticks { get; }   // 本次推进跨了多少拍;已有人满格时为 0
```

`BattleEngine` 追加 `public int LastAdvanceTicks { get; private set; }`,在 `AdvanceOnce`
里随 `LastActor` 一起写。

**这是本次唯一的 Core 改动**,纯追加,不改任何既有行为。TDD:先写失败测试。

> `Forecast` 内部也调 `Advance`,拿到的 `Ticks` 直接丢弃即可 —— 它的返回类型不变。

### 6.3 动画

`AdvanceRoutine`(`BattleView.cs:2123`)每轮循环改为:

```
拍 pre-meters(全场)
  → Battle.AdvanceOnce()            # meters 已跳到 post,行动已结算
  → 条动画:pre → post,时长 Ticks × BaseMs   # 行动者涨到 100% 停住
  → _juice.Play(...)                # 全场条冻结
  → 行动者的条回落到余额(post)
  → Refresh()
```

要点:

1. **时长 `Ticks × BaseMs`**。`BaseMs = 500`(速度 100 的单位从 0% 攒到 100% 用 500ms),
   集中成一个常量。速度 200 的走一半时间 —— 这就是「与速度挂钩」的落点。
2. **行动者涨满 100% 停住,不立刻清零**。播完它的动作才回落到 `post`
   (`post = pre + speed×ticks − 100`,可能不是 0,超出部分带到下一拍)。
   这样玩家看得出「是它满了才动」。
3. **条引用来自上一次 `Refresh`**,动画期间不重绘,与现有的血条推进(`SetHpBar`)同一个模式。
   循环第一轮的引用来自玩家回合那次 `Refresh`,有效。
4. **玩家回合期间条静止**。玩家出牌不推进计量器,按「结束回合」才开始流动
   —— 这是 CTB 的既有语义,不是本次引入的。
5. `Ticks == 0`(已有人满格,无需推进)时跳过条动画,直接播动作。

### 6.4 死亡与新单位

- 死掉的单位不进调度(`BuildSlots` 已经跳过),它的条随卡片一起进死亡表现
- 召唤物上场 / 敌人分裂时 `ActionMeter` 从 0 起(`BattleEngine.cs:1315` 已有先例:
  复活的召唤物 `ActionMeter = 0`),新单位的条从 0% 开始涨,不需特例
