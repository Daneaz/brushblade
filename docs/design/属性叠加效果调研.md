## 一 · 问题定义

需求给的 4 个样例其实是**两种不同的机制**,先拆开再谈方案:

| # | 样例 | 读什么 | 何时判定 | 收益形态 |
|---|---|---|---|---|
| 1 | 冷:目标处于冰冻 → 减速 3 回合、伤害 ×3 | **敌方状态** | 出字瞬间,一次性 | 倍率 + 时长 |
| 2 | 冻:目标处于减速 → 冻结 2 回合、伤害 ×2 | **敌方状态** | 出字瞬间,一次性 | 倍率 + 时长 |
| 3 | 松:柏在场 → 攻 +20%、HP +30% | **己方场面** | 持续,场面变了要跟着变 | 属性百分比 |
| 4 | 柏:松在场 → 攻 +10%、HP +10% | **己方场面** | 持续,场面变了要跟着变 | 属性百分比 |

1/2 是**一次性的条件放大**(下称「状态引信」),3/4 是**持续的场面光环**(下称「在场羁绊」)。
两者的判定时机、存续方式、存档影响完全不同,**不该塞进同一套字段**。这是本篇的第一条结论。

### 需求约束(照抄并落到执行口径)

- **C1 跨属性可以有,但要稀少** → 本篇给 25 个案例,其中**恰好 5 个跨属性**(每系 1 个),且 5 个全部挂到第 6 章已有的十条组合上,不新造概念。
- **C2 每系最多 5 个 case** → 按**字**计数(松、柏 算 2 个),五系各 5 个,合计 25,不超。

## 二 · 现状盘点:引擎已经有什么

| 已有 | 位置 | 与本需求的关系 |
|---|---|---|
| `EffectDef.DoubleVsBurning` | `EffectDef.cs` / `BattleEngine.BaseValue()` | **方案 A 的第一个实例**——「目标带灼烧则基础值 ×2」,灼/烬/爆在用。泛化它就是方案 A。 |
| `StatusBag` / `StatusKind`(21 种) | `StatusEffect.cs` | 引信要读的状态**全都有**:Burn / Freeze / SpeedModifier / ArmorBreak / Blind / Morale / Immunity… 不需要新增枚举值。 |
| `SummonPassive`(速度/荆棘/回血/挂灼烧/诅咒/闪避) | `SummonPassive.cs` | 召唤物被动**只读自己**,没有任何「看别人」的字段 → 方案 B 是纯新增。 |
| 生克倍率(相生 ×3 / 相克 ×1.5,理论 ×4.5) | `WuxingResolver.cs` | **最大风险源**:条件倍率若与它相乘,冷 会到 ×13.5。见裁定 R1。 |
| `ExecuteBelowPercent` / `HitCount` 的逐次判定 | `BattleEngine.ApplyEffects` | 「AOE 逐目标判、多段逐段判」的现成口径,引信直接沿用,不新造规则。 |

**缺什么**:一个能读「目标状态 / 自身状态 / 场面构成」的**条件求值器**,以及把求值结果喂进各 case 的通道。
今天 `ApplyEffects` 的 switch 里,每个 case 各自读 `value`,没有统一的「条件修正后再进 case」的收口点。

## 三 · 五个方案

### 方案 A · 状态引信(读目标状态 → 一次性放大)

- **机制**:效果带一个条件块;出字结算瞬间求值,真则按配置放大**本次**结果。
- **收益形态**(四种,够覆盖全部样例):倍率 `valueMul`、平加 `valueAdd`、时长 `turnsAdd`、追加一条效果 `extra`;可选 `consume`(消耗掉触发条件的那条状态)。
- **数据形状**:`EffectDef` 加两个字段 `When` / `Then`,`EffectDto` 同步加两个子 DTO。
- **引擎钩子**:`BattleEngine.BaseValue()`(约 :1922)已经是「条件基础值」的钩子,把它泛化成
  `ConditionalScale(effect, value, target)`;非伤害类(Freeze/Slow/Shield/Burn…)在 `ApplyEffects` 的
  `foreach` 顶部统一算一次修正后的 `value` / `turns`,各 case 只读修正后的值——**不在 25 个 case 里各写一遍 if**。
- **成本**:Core 约 150~200 行 + ConfigLoader 约 40 行 + 卡面文案生成。**存档零改动**(条件从 `chars.json` 按名字解析,和 `EffectKind` 一样从不进存档)。
- **风险**:与生克倍率叠乘(R1);卡面文案变长(R8)。
- **适配**:火(灼烧层数)、水(冻结/减速)、土(破甲)、金(穿透/斩杀)——**四系通吃**。

### 方案 B · 在场羁绊(读己方场面 → 持续光环)

- **机制**:召唤字带 `Bond`,声明「同场有 X 时,我攻 +a%、血 +b%」。样例 3/4 就是它。
- **三种实现,只有第三种能用**:
  - **B-1 进场快照**:召唤瞬间把加成焊进 hp/attack 常量。最省(零派生),但**顺序敏感**——先松后柏,松永远吃不到柏的加成。玩家看不懂,**否决**。
  - **B-2 挂状态**:伙伴进场时给对方挂一条 `AttackBuff`。问题是 `SummonState` **没有 `StatusBag`**(只有 Char/Element/Hp/MaxHp/Attack/Speed/ActionMeter/Shield/Passive),要加就得动 `SummonSnapshot` → **新增存档字段**,为一个光环不值,**否决**。
  - **B-3 动态派生**(推荐):存的永远是**基础值**,用的时候现算。
    `summon.Attack` 全库只有 2 个读取点(`BattleEngine.cs:1133/1135` 的召唤物出手),换成 `EffectiveSummonAttack(i)` 即可;
    `summon.MaxHp` 3 个点(:1458 复活、:1879 治疗上限,加表现层血条)换成 `EffectiveSummonMaxHp(i)`。
    **存档零改动**——存的是基础值,读档后光环自然重算,顺序天然无关。
- **成本**:Core 约 80~120 行 + 表现层血条改读派生上限。
- **风险**:伙伴阵亡时 MaxHp 回落,当前 Hp 要 clamp(见未决 Q2);百分比加成是**比值**,量级 ×10 时**永不跟着乘**(与 `AttackBuff` 同一条既有纪律)。
- **适配**:木系(唯一的召唤载体);火系的 灶/烓 两只召唤物可蹭。

### 方案 C · 自身蓄势(读玩家自己的状态 → 一次性放大)

- **机制**:与 A 同一套条件块,只把 `on` 从 `target` 换成 `self`:战意层数、护盾量、护甲点、暴击/穿透增益、免疫层。
- **成本**:**A 做完它就是免费的**(同一个求值器多一个数据源),不单独排期。
- **适配**:金(战意)、土(护盾/护甲)。给这两系一条「先攒后爆」的节奏,而不是又一个「看敌人脸色」。
- **定位**:辅线。全篇 25 例里占 5 例(垚/堡/镰/𨰻/煤)。

### 方案 D · 连招(读上一张出的字 / 上一张的属性)

- **机制**:「上一张是水字 → 本张 ×2」。
- **否决理由**:需要在战斗态里新增「本回合已出字序列」并**进快照**(`BattleSnapshot` 新字段 = 存档改动);
  玩家要记牌序,教学成本高于 A;而 A 已经能表达绝大多数同类手感(把「上一张打了冻」表达成「目标身上有冻结」),**收益重叠、成本更高**。本期不做。

### 方案 E · 字库共鸣(读字库/牌库构成)

- **机制**:「字库里每有 1 个木字,召唤物 +5 攻」。
- **否决理由**:这是 **build 级**加成,和第 20 章无尽的「字库随时被替换/满库丢弃」直接打架——
  数值会在玩家看不见的地方跳变;而且它与「法宝」(第 7 章)的定位重合。留给法宝,不进字表。本期不做。

### 方案对比

| | A 状态引信 | B 在场羁绊 | C 自身蓄势 | D 连招 | E 字库共鸣 |
|---|---|---|---|---|---|
| 覆盖样例 | 1、2 | 3、4 | — | — | — |
| 存档影响 | **无** | **无**(走 B-3) | 无 | 新增快照字段 | 无 |
| Core 成本 | 中 | 中 | **0**(附赠) | 中 | 低 |
| 表现层成本 | 高(卡面条件行 + 激活态) | 中(血条改派生) | 高(同 A) | 高 | 低 |
| 玩家可读性 | 高(状态图标就在敌人身上) | 高(两只都在场上) | 中 | 低 | 低 |
| 结论 | **做** | **做** | **做(附赠)** | 不做 | 不做 |

## 四 · 统一裁定(实现前必须先拍这 8 条)

- **R1 条件倍率与相生 ×3「取大不叠乘」,相克 ×1.5 照常乘。**
  依据:`wuxing-reference` 第 4 条「多对相生不叠乘」是同一条哲学。若相乘,含相生的 焚 会到 ×4.5×条件,单字打穿全场。
  推论(**配置口径**):**含相生的字(燊/焚/蒸/炑/沏/刲)一律不配倍率型条件**——配了也被取大吃掉,白配。
  它们的条件奖励只走**加量型**(`valueAdd` / `turnsAdd` / `extra`)。本篇 焚 的案例就是照这条设计的。
- **R2 一张字最多一条条件。** 卡面塞不下第二个 if,玩家也算不清。
- **R3 条件只读结算瞬间的场面。** 不追溯(「这回合曾经冻结过」不算)、不预约(「下回合若…」不做)。
- **R4 AOE 逐目标判、多段逐段判**——与暴击、斩杀完全同口径(`ApplyEffects` 现成)。
  `consume` 型条件**只在第一次命中时消耗**,后续段/目标按未消耗前的判定结果走(否则 剁 的第二段会莫名其妙掉档)。
- **R5 条件不满足不惩罚。** 基础效果照常发生,只是没有加成。字表里不出现「没触发就是废牌」的设计。
- **R6 敌人不吃这套机制。** 引信/羁绊是玩家侧专属;敌人技能继续走 `Bestiary` 那套。理由:双向条件会让战场状态爆炸,玩家无法预判。
- **R7 存档纪律。** 条件与羁绊**全部从 `chars.json` 按名字解析、从不进存档**;若将来确需新增 `StatusKind`,**一律追加末尾**(`CritStatTests.StatusKindOrdinals_AreLockedForSaveCompatibility` 会拦)。方案 B 走 B-3 动态派生正是为了守住这条。
- **R8 卡面必须显示条件行,且战斗中条件满足时高亮 + 数字实时改写。** 做不到这条,机制等于不存在——
  玩家不会为一个看不见的 ×3 去调整出牌顺序。这是本需求**最大的一笔表现层成本**,排期时不要漏。

## 五 · 数值校准公式

样例给的量级(冷 40→120)是否超模?按下面这条口径算,**结论是不超,甚至偏保守**:

> **组合触发后的单张总量,对齐「组合中较高稀有度 + 1 档」的同档基准。**

- 冷(白 40)要触发,得先有冻结源——最低是蓝档的 冻/藤 → 较高者 = 蓝 → 目标档 = 紫(基准 130~210)。
  冷 触发后 120,**略低于紫档下沿**,合理。
- 冻(蓝 85)要触发,得先有减速源——最低是白档的 冷 → 较高者 = 蓝 → 目标档 = 紫。
  冻 触发后 170,落在紫档中位,合理。
- 整条链:2 AP 打出 85 + 120 = 205 伤害 + 冻结 1 + 减速 3;对照 1 AP 的紫档 沏(210)。
  **单纯比伤害是亏的,赚在两条硬控上**——这正是「组合要有额外操作成本、也要有额外回报」的正确形状。

配套上限(防止后续加字时失控):

| 档位 | 条件倍率上限 | 说明 |
|---|---|---|
| 白 / 绿 | ×3 | 基数小,倍率大才有翻身感;绝对值仍被上面的公式压住 |
| 蓝 / 紫 | ×2 | |
| 金 / 橙 / 红 | ×1.5 | 基数已经很大,再乘就穿场 |

**平值型奖励**(层数、回合数、破甲点数)不吃上表,按「不超过同档同类字的一张牌量」控——
例如「+1 层灼烧」上限对齐 焦(2 层)那一档,别一次给 5 层。

## 六 · 案例清单(五系 × 5 = 25,其中跨属性 5)

字全部取自现有字表(`字表功能解析.md`),**不新增字、不新增字形**——这是这份清单最大的落地优势。
「现状」列 = 今天配置表里的效果;「条件 / 触发后」= 本篇提案。

### 6.1 水系 · 控场(冻结 ⇄ 减速 的对偶闭环)

| 字 | 档 | 现状 | 条件 | 触发后 | 方案 |
|---|---|---|---|---|---|
| 冷 | 白 | 减速 2;伤 40 | 目标**冻结中** | 减速 **3** 回合;伤害 **×3 = 120** | A(原案) |
| 冻 | 蓝 | 冻结 1;伤 85 | 目标**减速中** | 冻结 **2** 回合;伤害 **×2 = 170** | A(原案) |
| 冰 | 紫 | 伤 150;冻结 1 | 目标**减速中** | **消耗**减速,伤害 ×2 = 300,冻结照常 1 回合 | A + `consume` |
| 洼 | 金 | AOE 140;减速 2 | 场上**每有 1 个减速中的敌人** | 本次全体伤害 **+15%,上限 +60%** | A(计数式) |
| 淋 | 金 | 群疗 155;AOE 70 | **己方有召唤物在场**〔跨〕 | 群疗 **+50% = 232**,召唤物同享 | A(`on: field`) |

- 三档递进很干净:**冷(白)启动 → 冻(蓝)闭环 → 冰(紫)收割**。玩家第一次撞出「冻完再冷」会很爽。
- 洼 是本篇唯一的**计数式**条件,验证求值器能不能表达「场面数量」;上限 +60% 防 AOE 失控。
- 淋 = 第 6 章 6.3.5 **润木**(水生木)。

### 6.2 火系 · 灼烧(阈值型,不再是又一个「×2」)

火系已经有 `DoubleVsBurning`(灼/烬/爆),**新案例一律不做简单翻倍**,只做既有机制表达不了的形状。

| 字 | 档 | 现状 | 条件 | 触发后 | 方案 |
|---|---|---|---|---|---|
| 焰 | 绿 | 伤 70;灼烧 1 层 | 目标灼烧 **≥3 层** | 灼烧改挂 **3 层** | A(阈值 → 平加) |
| 灱 | 紫 | 灼烧 3 层;引爆全部剩余灼烧 | 引爆时目标灼烧 **≥5 层** | 引爆伤害 **×1.5**(轰燃) | A(阈值 → 倍率) |
| 熣 | 紫 | 伤 80;灼烧 2;致盲 −50%×2 | 目标**已致盲** | 灼烧改 **4 层**,致盲延长到 **3 回合** | A(同状态自叠) |
| 煤 | 紫 | 灼烧威力 +20/层;伤 80 | **自身已有**「灼烧威力」增益 | 本次改为 **+40/层** | C(读自身) |
| 焚 | 金 | AOE 30×3=90;全体灼烧 3 层 | **己方每有 1 只召唤物**〔跨〕 | 全体**额外 +1 层**灼烧,上限 +3 | A(平加;**受 R1 约束不给倍率**) |

- 焰/灱 的阈值(3 层 / 5 层)刚好卡在「铺了两三张火字之后」,把火系从「无脑叠层」推向「层数是资源,要择时兑现」。
- 煤 是自身蓄势的样板:第一张 +20/层,第二张吃到条件变 +40/层,**累计 +60 而不是 +40** —— 给堆叠一个非线性的甜点。
- 焚 = 第 6 章 6.3.1 **焚林**(木生火);它含相生 ×3,**按 R1 只能给平加**,这条案例本身就是 R1 的活教材。

### 6.3 木系 · 召唤(羁绊主场)

| 字 | 档 | 现状 | 条件 | 触发后 | 方案 |
|---|---|---|---|---|---|
| 松 | 绿 | 召 1(血 120/攻 30) | **柏**在场 | 攻 **+20%**、HP **+30%** | B(原案) |
| 柏 | 蓝 | 召 1(血 160/攻 40) | **松**在场 | 攻 **+10%**、HP **+10%** | B(原案) |
| 林 | 紫 | 召 2(血 110/攻 50) | 己方召唤物 **≥3 只** | 全场召唤物各 **+10 攻**(成林) | B(计数光环) |
| 荆 | 紫 | 召 1(血 180/攻 60,荆棘 30) | **另有召唤物在场** | 荆棘升到 **45**,且**替队友挨的那一下也反弹** | B(改行为) |
| 柘 | 紫 | 召 1(血 320/攻 40) | **自身有护盾**〔跨〕 | 召唤物 HP **+30%**(扎根) | B(`on: self`) |

- 松/柏 的不对称(松吃 20%/30%,柏吃 10%/10%)是对的:**低档字从组合里拿走更多**,才有理由带着一张绿卡进后期。
- 林 的「≥3 只」自己就能凑到(召 2 只 + 场上 1 只),不强迫玩家先备场——**羁绊不该有前置门槛**。
- 荆 是唯一改**行为**而非改数值的羁绊,用来验证 B 的表达力上限。
- 柘 = 第 6 章 6.4.4 **破土而出**(木克土)。
- 备选(超出 5 个上限,留档):柳(闪避 50)+ 桤(速度 150)同场 → 双方速度 +30。

### 6.4 土系 · 攻防转换(蓄势主场)

| 字 | 档 | 现状 | 条件 | 触发后 | 方案 |
|---|---|---|---|---|---|
| 碎 | 白 | 伤 40;破甲 10 | 目标**已带破甲** | 破甲改 **20**,伤害 **×2 = 80** | A(自叠引信) |
| 破 | 绿 | 伤 60;破甲 15 | 目标**护甲已被削到 0** | 伤害 **×2 = 120**(甲碎则身裂) | A(读派生量) |
| 堡 | 蓝 | 盾 55(免一次清盾);伤 45 | **自身已有护盾** | 护盾 **×1.5 = 82**,「免一次清盾」升级为**免两次** | C |
| 垚 | 金 | 盾 300;伤 320 | **自身护盾 ≥200** | 伤害 **×1.5 = 480**(以盾为矛) | C |
| 塔 | 紫 | 盾 100;伤 70 | 场上**有灼烧中的敌人**〔跨〕 | 护盾 **+50% = 150** | A(`on: field`) |

- 碎 → 破 是一条**自己喂自己**的链:碎 先挂破甲、破 把甲清零后翻倍,两张白绿字在中期仍有位置。

## 七 · 数据结构草案

### chars.json(方案 A / C)

```json
{ "id": "冷", "element": "Water", "rarity": "White", "recipe": ["冫", "令"],
  "effects": [
    { "kind": "DamageSingle", "value": 40,
      "when": { "on": "target", "has": "Freeze" },
      "then": { "valueMul": 3.0 } },
    { "kind": "Slow", "value": 2,
      "when": { "on": "target", "has": "Freeze" },
      "then": { "valueAdd": 1 } }
  ] }
```

- `when.on`:`target` | `self` | `field`
- `when` 谓词(**一条效果只允许一个**,R2):
  `has`(某状态存在)、`atLeast: { status, n }`(层数/点数阈值)、`countAtLeast: { of, n }`(场面计数)、
  `summon: "柏"`(指定召唤字在场)、`shieldAtLeast: n`、`armorZero`(目标护甲被削到 0)
- `then`:`valueMul`(倍率)、`valueAdd`(平加)、`turnsAdd`(时长)、`extra`(追加一条完整 EffectDef)、`consume`(消耗触发它的那条状态)
- 计数式(洼)用 `then.perUnit`:`{ "countOf": "SlowedEnemy", "valueMulPerUnit": 0.15, "cap": 0.60 }`

### chars.json(方案 B)

```json
{ "id": "松", "element": "Wood", "rarity": "Green", "recipe": ["木", "公"],
  "effects": [
    { "kind": "Summon", "value": 120, "attack": 30, "summonChar": "木",
      "bond": { "with": "柏", "attackPct": 20, "hpPct": 30 } }
  ] }
```

`bond` 挂在 `Summon` 效果上、随 `SummonPassive` 一起拷进 `SummonState`(**存基础值 + 声明,不存算好的结果**)。

### C# 侧

- `EffectDef` 新增 `Condition When` / `ConditionBonus Then`(两个不可变小类,与 `SummonPassive` 同构)。
- `SummonPassive` 新增 `Bond Bond`(同样是 POCO,`Clone()` 要跟着拷)。
- `BattleEngine` 新增:
  - `private ConditionResult Evaluate(EffectDef e, int targetIndex, in CastScratch scratch)` —— 唯一求值点;
  - `EffectiveSummonAttack(int i)` / `EffectiveSummonMaxHp(int i)` —— 羁绊的唯一出口,替换掉 `:1133/1135/1458/1879` 的直读。
- `ConfigLoader.EffectDto` 加 `When` / `Then` / `Bond` 三个子 DTO;**未知谓词一律抛 `ConfigException`**,不静默忽略。
