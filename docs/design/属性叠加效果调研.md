## 一 · 问题定义

需求给的 4 个样例是**两种不同的机制**,先拆开再谈方案(样例本身按反馈①只作形状参考,数值与条件全部重做):

| 样例形状 | 读什么 | 何时判定 | 存续 |
|---|---|---|---|
| 「目标处于某状态 → 本次效果放大」 | **敌方状态** | 出字瞬间,一次性 | 不留状态 |
| 「同场有某单位 → 我持续更强」 | **己方场面** | 持续,场面变了跟着变 | 随场面存续 |

前者下称**状态引信**,后者下称**在场羁绊**。两者判定时机、存续方式、存档影响完全不同,**不该塞进同一套字段**。

## 二 · 现状盘点:引擎已经有什么

| 已有 | 位置 | 与本需求的关系 |
|---|---|---|
| `EffectDef.DoubleVsBurning` | `EffectDef.cs` / `BattleEngine.BaseValue()` | **方案 A 的第一个实例**——「目标带灼烧则基础值 ×2」,灼/烬/爆在用。泛化它就是方案 A。 |
| `StatusBag` / `StatusKind`(21 种) | `StatusEffect.cs` | 引信要读的状态**全都有**:Burn / Freeze / SpeedModifier / ArmorBreak / Blind / Morale / Immunity… 不需要新增枚举值。 |
| `SummonPassive`(速度/荆棘/回血/挂灼烧/诅咒/闪避) | `SummonPassive.cs` | 召唤物被动**只读自己**,没有任何「看别人」的字段 → 方案 B 是纯新增。 |
| 生克倍率(相生 ×3 / 相克 ×1.5,理论 ×4.5) | `WuxingResolver.cs` | **最大风险源**:条件倍率若与它相乘,单字会打穿全场。见裁定 R1。 |
| `ExecuteBelowPercent` / `HitCount` 的逐次判定 | `BattleEngine.ApplyEffects` | 「AOE 逐目标判、多段逐段判」的现成口径,引信直接沿用,不新造规则。 |

**缺什么**:一个能读「目标状态 / 自身状态 / 场面构成」的**条件求值器**,以及把求值结果喂进各 case 的通道。
今天 `ApplyEffects` 的 switch 里,每个 case 各自读 `value`,没有统一的「条件修正后再进 case」的收口点。

## 三 · 与词组系统的边界(反馈③)

`词组补全建议.md` 已经把「**哪两张字凑成一个词**」盘成了一套将来要做机制的资产:🟢 已闭合 41 条 + 🟩 已纳入 14 条,现在就能用。
两套系统必须分地盘,否则同一次出牌被奖励两次:

> **词组系统吃「哪两张字」,叠加系统吃「场上是什么状态」。**

落到可执行的两条口径:

- **R10-a 叠加条件不得指名具体字。** 只能读状态(`has Freeze`)、计数(`召唤物 ≥3`)、派生量(`护甲 = 0`)、自身资源(`战意 ≥3`)。
  「柏在场」这种写法**是词组的表达方式**,一律改成「另有召唤物在场」。
- **R10-b 条件的 provider 必须 ≥3 个字,且至少 2 个与本字不成词。** 防止「不指名字」只是把词组换了个马甲——
  provider 只有两三个、其中恰好一对成词的条件(例:减速的来源只有 冷/凝/洼,而 **冷凝** 是词),等于偷偷做了词组。
- **R10-c 真撞上了取大不叠加。** 将来词组系统上线后,若一张字同时凑成词组又满足叠加条件,**两套加成取更强的一套**,不叠乘。

### 原案为什么全废

按 R10 复检初稿,水木两系的案例正好压在词组最密的两块地上:

| 原案 | 命中的词组 | 处置 |
|---|---|---|
| 冷(读冻结)、冻(读减速)、冰(读减速) | 冷冻 / 冷凝 / 冰冷 / 冰冻 / 冰凝 —— 水·控制组 5 字互相成词,是全池最密的一块 | **整条删除**,水系改用「破甲 / 控制中 / 敌人数 / 自身减益」四条轴 |
| 松(柏在场)、柏(松在场)、林(≥3 只) | 松柏 / 松林 / 柏林 / 森林 | 羁绊改读「另有召唤物」的**计数**,不指名字 |
| 碎(读破甲)、堡(读自身护盾) | 崩碎 / 碾碎 / 砸碎;碉堡 / 堡垒 / 城堡 | 碎 改读「目标有护盾」;土系防御线整个让给词组,**不再有任何「读自身护盾」的土字** |
| 焚(读召唤物)、塔(读灼烧)、刺(读灼烧)、淋(读召唤物)、柘(读自身护盾) | 焚烧 / 淋浴 —— 且这 5 张全是蓝档以上,与反馈② 的绿卡目标不符 | 删除,跨属性名额重新分配(见 §7.6) |

反馈① 的问题也一并解决:原案「目标冻结中 → 减速 3 回合」是**奖励与条件同质**——目标本来就不能动,减速一分钱不值。新裁定 R9 直接禁掉这一类。

### 收工复检:案例字之间的 5 对词组,互不喂条件

新案例里仍有 5 对字**本身成词**(避不开——18 张绿卡里 5 张挂在词组上,躲开就等于放弃反馈②的覆盖目标)。
关键不是「两张字不能同时出现在两套系统里」,而是**一张字的词组伙伴不能顺手把另一张的叠加条件也喂了**。逐对复检:

| 词组对 | 前字的条件 | 后字的条件 | 会互相喂吗 |
|---|---|---|---|
| 烧焦 | 灼烧 **= 0** | 灼烧 **≥6** | **互斥**——烧 触发时目标 0 层,焦 永远不可能同时成立 |
| 炽焰 | **自身**有灼烧威力增益 | **目标**灼烧 ≥3 | 一个读自身、一个读目标,两条轴 |
| 墙壁 | 自身 HP <50% | 自身带减益 | 墙 不会给自己上减益,壁 不会扣自己血 |
| 砸碎 | 目标护甲 **>0** | 目标有护盾 | 反向——碎 的破甲还会把 砸 的条件**关掉** |
| 松涛 | 己方召唤物 ≥1 | 敌方数量 ≥3 | 一个数己方、一个数敌方 |

5 对全部通过:词组给的是「这两张字凑成词」的奖励,叠加给的是「场上是什么状态」的奖励,**同一次出牌不会被同一个理由奖励两次**。
真出现例外(将来加字时),按 R10-c 取大不叠加兜底。

## 四 · 五个方案

### 方案 A · 状态引信(读目标状态 → 一次性放大)

- **机制**:效果带一个条件块;出字结算瞬间求值,真则按配置改写**本次**结果。
- **收益形态**(六种,够覆盖全部案例):倍率 `valueMul`、平加 `valueAdd`、时长 `turnsAdd`、
  追加一条效果 `extra`、**整条替换 `replaceWith`**(凝 的「减速改冻结」)、消耗触发条件 `consume`。
- **数据形状**:`EffectDef` 加 `When` / `Then` 两个字段,`EffectDto` 同步加两个子 DTO。
- **引擎钩子**:`BattleEngine.BaseValue()`(约 :1922)已经是「条件基础值」的钩子,把它泛化成
  `ConditionalScale(effect, value, target)`;非伤害类(Freeze/Slow/Shield/Burn…)在 `ApplyEffects` 的
  `foreach` 顶部统一算一次修正后的 `value` / `turns`,各 case 只读修正后的值——**不在 20 多个 case 里各写一遍 if**。
- **成本**:Core 约 150~200 行 + ConfigLoader 约 40 行 + 卡面文案生成。**存档零改动**(条件从 `chars.json` 按名字解析,和 `EffectKind` 一样从不进存档)。
- **适配**:五系通吃,是本期主力(24 例里 20 例走它)。

### 方案 B · 在场羁绊(读己方场面 → 持续光环)

- **机制**:召唤字带 `Bond`,声明「同场召唤物达到 N 只时,我攻 +a%、血 +b%」。**按 R10-a 只读计数,不读字**。
- **三种实现,只有第三种能用**:
  - **B-1 进场快照**:召唤瞬间把加成焊进 hp/attack 常量。最省,但**顺序敏感**——先召的那只永远吃不到后来者的加成。**否决**。
  - **B-2 挂状态**:伙伴进场时给对方挂一条 `AttackBuff`。但 `SummonState` **没有 `StatusBag`**(只有 Char/Element/Hp/MaxHp/Attack/Speed/ActionMeter/Shield/Passive),要加就得动 `SummonSnapshot` → **新增存档字段**,为一个光环不值。**否决**。
  - **B-3 动态派生**(推荐):存的永远是**基础值**,用的时候现算。
    `summon.Attack` 全库只有 2 个读取点(`BattleEngine.cs:1133/1135`),换成 `EffectiveSummonAttack(i)`;
    `summon.MaxHp` 3 个点(:1458 复活、:1879 治疗上限,加表现层血条)换成 `EffectiveSummonMaxHp(i)`。
    **存档零改动**——存基础值,读档后光环自然重算,顺序天然无关。
- **风险**:伙伴阵亡时 MaxHp 回落,当前 Hp 要 clamp(见未决 Q2);百分比加成是**比值**,量级 ×10 时**永不跟着乘**。
- **适配**:木系 3 例(松/柳/梅)。

### 方案 C · 自身蓄势(读玩家自己的状态 → 一次性放大)

- **机制**:与 A 同一套条件块,`on` 从 `target` 换成 `self`:战意层数、当前 HP%、自身减益条数、增益是否已有。
- **成本**:**A 做完它就是免费的**(同一个求值器多一个数据源),不单独排期。
- **适配**:金(战意)、土(残血)、火(灼烧威力堆叠)、水(自身减益)。本篇占 7 例。

### 方案 D · 连招(读上一张出的字 / 上一张的属性)—— 不做

需要在战斗态里新增「本回合已出字序列」并**进快照**(存档改动);而且「按顺序打两张字」正是**词组系统的形状**(R10),
本期做它等于提前占了词组的地盘。**否决**。

### 方案 E · 字库共鸣(读字库/牌库构成)—— 不做

build 级加成,与第 20 章无尽的「字库随时被替换/满库丢弃」直接打架,数值会在玩家看不见的地方跳变;定位又与第 7 章法宝重合。**否决**。

### 方案对比

| | A 状态引信 | B 在场羁绊 | C 自身蓄势 | D 连招 | E 字库共鸣 |
|---|---|---|---|---|---|
| 本篇用例数 | 20 | 3 | 7(与 A 有重合计数) | — | — |
| 存档影响 | **无** | **无**(走 B-3) | 无 | 新增快照字段 | 无 |
| Core 成本 | 中 | 中 | **0**(附赠) | 中 | 低 |
| 与词组系统 | 不冲突(读状态) | 不冲突(读计数) | 不冲突(读自身) | **同形状,冲突** | 不冲突但定位撞法宝 |
| 结论 | **做** | **做** | **做(附赠)** | 不做 | 不做 |

## 五 · 统一裁定(实现前必须先拍这 10 条)

- **R1 条件倍率与相生 ×3「取大不叠乘」,相克 ×1.5 照常乘。**
  依据:`wuxing-reference` 第 4 条「多对相生不叠乘」是同一条哲学。
  推论(**配置口径**):**含相生的字(燊/焚/蒸/炑/沏/刲)一律不配倍率型条件**——配了也被取大吃掉。
  这 6 个字全在紫档以上,本期案例层不碰它们,该口径留给后续加字时用。
- **R2 一张字最多一条条件。** 卡面塞不下第二个 if,玩家也算不清。
- **R3 条件只读结算瞬间的场面。** 不追溯(「这回合曾经冻结过」不算)、不预约(「下回合若…」不做)。
- **R4 AOE 逐目标判、多段逐段判**——与暴击、斩杀完全同口径。`consume` 型条件**只在第一次命中时消耗**。
- **R5 条件不满足不惩罚。** 基础效果照常发生,只是没有加成。不做「没触发就是废牌」的设计。
- **R6 敌人不吃这套机制。** 引信/羁绊是玩家侧专属;双向条件会让战场状态爆炸,玩家无法预判。
- **R7 存档纪律。** 条件与羁绊**全部从 `chars.json` 按名字解析、从不进存档**;若将来确需新增 `StatusKind`,**一律追加末尾**(`CritStatTests.StatusKindOrdinals_AreLockedForSaveCompatibility` 会拦)。
- **R8 卡面必须显示条件行,且战斗中条件满足时高亮 + 数字实时改写。** 做不到这条,机制等于不存在——
  玩家不会为一个看不见的加成去调整出牌顺序。这是本需求**最大的一笔表现层成本**。
- **R9 奖励不得与条件同质**(反馈①)。目标已冻结就别再给减速、已致盲就别再给致盲——
  条件成立时那份收益**必须是条件本身给不了的东西**。三种合法形状:
  **升级**(减速 → 冻结)、**转化**(破甲 → 穿透 / 净化 → 治疗)、**开新机制**(引爆、无视护甲、状态转全体)。
  纯倍率也合法,但要能说清「为什么这个状态下伤害该更高」(砸不中会动的东西、烧红了才好淬)。
- **R10 与词组系统分地盘**(反馈③):条件不指名具体字(a)、provider ≥3 且至少 2 个与本字不成词(b)、真撞上取大不叠加(c)。详见 §三。

## 六 · 案例层:为什么押在绿卡上(反馈②)

### 绿卡今天为什么没人带

不是「绿卡弱」,是**绿卡被上位字整张替代**——形状一样、数值全面低一档:

| 绿卡 | 上位替代 | 差距 |
|---|---|---|
| 焰 伤 70 + 灼 1 | 炸(蓝)伤 110 + 灼 1 | 同形状,伤害 −36% |
| 墙 盾 45 + 伤 35 | 碉(蓝)盾 60 + 伤 50 | 同形状,两项都低 |
| 涛 AOE 50 | 海 / 洪(蓝)AOE 70 | 同形状,−29% |
| 淬 伤 90 | 刺(蓝)伤 135 + 穿透 | 同形状,还少一个穿透 |

只要「形状一样」,玩家就永远选数值高的那张,绿卡在字库里是纯占位。

### 解法:给绿卡**紫卡没有的机制**,而不是给它更高的数值

绿卡的条件收益一律走 R9 的「升级 / 转化 / 开新机制」,让绿卡在**特定场面**里做紫卡做不到的事:

- 凝(绿)在目标破甲时**能造冻结** —— 冻结本来蓝档起步。
- 焰(绿)在目标 3 层灼烧时**能引爆** —— 引爆本来是紫档 灱 的独门。
- 砸(绿)对带甲目标**无视全部护甲** —— 全字表没有第二张这么干的。
- 梅(白)在空场时血 ×3 —— 团灭后重开的唯一解。

**校准口径(替代初稿的「+1 档」公式)**:

> **绿卡触发后 ≈ 紫档同类的 90~100%,且必须多花至少 1 张牌铺垫。**

这样绿卡「值得带」——在它擅长的场面里能顶一张紫卡;但**不会顶替紫卡**——需要铺垫、且场面不对时它还是绿卡。
逐条对照见下表的「触发后 vs 上位档」列。

## 七 · 案例清单(24 例:绿卡 18 张全覆盖 + 白卡 6)

「现状」= 今天配置表里的效果;「条件 / 触发后」= 本篇提案。**没有一条指名具体字**(R10-a)。

### 7.1 水系 · 5 例(绿卡 5/5 全覆盖)

| 字 | 档 | 现状 | 条件 | 触发后 | 触发后 vs 上位档 |
|---|---|---|---|---|---|
| 凝 | 绿 | 减速 2;伤 65 | 目标**已破甲** | 减速**整条换成冻结 1 回合**;伤 65 不变 | 冻(蓝)冻结 1 + 伤 85 —— 伤害仍低一截 |
| 淬 | 绿 | 伤 90 | 目标**冻结或减速中** | 伤害 **×2 = 180** | 灿(紫)180,追平 |
| 溶 | 绿 | 伤 60;破甲 15 | 目标**已破甲** | 破甲改 **30 且转为全体** | 全字表唯一的 AOE 破甲 |
| 涛 | 绿 | AOE 50 | 场上**敌人 ≥3** | 全体伤害 **+50% = 75** | 海/洪(蓝)70,略超但要 3 怪 |
| 浴 | 绿 | 伤 70;净化自身 | **自身带减益** | 每清 1 条减益**回血 40**,上限 3 条 = 120 | 澡(紫)治 50 + 净化,重减益场才超它 |

- **凝 → 淬 是一条纯绿卡内循环**:凝 造冻结、淬 收割冻结,两张绿卡合计 2 AP 打 180 + 冻结 1。且 **凝淬 不成词**,不与词组撞车。
- 凝 的条件是「破甲」而不是「减速」,正是为了绕开 冷凝 / 冷冻 那一窝词组(R10-b:减速的 provider 只有 冷/凝/洼 三张,其中 冷凝 成词,不合格)。
- 溶 的破甲 provider 是 碎/破(土)+ 溃(水),天然跨土水〔跨〕。

### 7.2 火系 · 5 例(绿卡 3/3 全覆盖 + 白 2)

## 八 · 数据结构草案

### chars.json(方案 A / C)

```json
{ "id": "凝", "element": "Water", "rarity": "Green", "recipe": ["冫", "疑"],
  "effects": [
    { "kind": "DamageSingle", "value": 65 },
    { "kind": "Slow", "value": 2,
      "when": { "on": "target", "has": "ArmorBreak" },
      "then": { "replaceWith": { "kind": "Freeze", "value": 1 } } }
  ] }
```

- `when.on`:`target` | `self` | `field`
- `when` 谓词(**一条效果只允许一个**,R2;**一律不接受字 ID**,R10-a):
  `has`(某状态存在)、`none`(某状态不存在,烧/梅 的逆向条件)、`atLeast: { status, n }`(层数/点数阈值)、
  `countAtLeast: { of, n }`(场面计数:`Enemy` / `Summon` / `SlowedEnemy`)、`armorZero` / `armorAbove: n`、
  `shieldAbove: n`、`hpBelowPercent: n`、`debuffAtLeast: n`
- `then`:`valueMul`、`valueAdd`、`turnsAdd`、`extra`(追加一条完整 EffectDef)、`replaceWith`(整条替换)、
  `consume`(消耗触发它的那条状态)、`targetAll: true`(把本条转成全体,溶 用)
- 按结果计价的条件(灭「清掉 ≥2 条」、剿「斩杀 ≥2 个」)在效果**执行后**回判,记 `when.on: "outcome"`。

### chars.json(方案 B)

```json
{ "id": "松", "element": "Wood", "rarity": "Green", "recipe": ["木", "公"],
  "effects": [
    { "kind": "Summon", "value": 120, "attack": 30, "summonChar": "木",
      "bond": { "othersAtLeast": 1, "attackPct": 20, "hpPct": 30 } }
  ] }
```

`bond` 只认**计数**(`othersAtLeast`),不认字 ID —— 这是 R10-a 在数据层的强制形状。
它随 `SummonPassive` 一起拷进 `SummonState`(**存基础值 + 声明,不存算好的结果**)。

### C# 侧

- `EffectDef` 新增 `Condition When` / `ConditionBonus Then`(不可变小类,与 `SummonPassive` 同构)。
- `SummonPassive` 新增 `Bond Bond`(POCO,`Clone()` 要跟着拷)。
- `BattleEngine` 新增:
  - `private ConditionResult Evaluate(EffectDef e, int targetIndex, in CastScratch scratch)` —— 唯一求值点;
  - `EffectiveSummonAttack(int i)` / `EffectiveSummonMaxHp(int i)` —— 羁绊的唯一出口,替换掉 `:1133/1135/1458/1879` 的直读。
- `ConfigLoader.EffectDto` 加 `When` / `Then` / `Bond` 三个子 DTO;**未知谓词、以及任何看起来像字 ID 的条件值,一律抛 `ConfigException`**——
  R10-a 要有工具兜底,光靠文档记不住。
