# E-b6 方案:攻击模式多样化 + 治疗目标可选

> 状态:**方案草案(v1),待用户拍板后再开工**。2026-08-20 提出。
> 范围:①玩家出字的攻击模式扩到 单体 / 群体 / 溅射 / 多重 四种;②所有单体治疗改为可选目标(玩家 或 某只召唤物)。
> 规则唯一来源不动:五行生克仍以 [wuxing-reference](wuxing-reference.md) 为准,数值锚点仍以
> [技能机制详表](字选型/技能机制详表.md) 「锚点(最终值,对中立目标)」那张表为准 —— 本方案只在其上**扩两行**。

---

## 0. 摘要

| 项 | 现状 | 方案 |
|---|---|---|
| 攻击模式 | 只有 `DamageSingle`(66 条)/ `DamageAll`(21 条)两种,分别是 `ApplyEffects` 里两段各写各的分支 | 抽出**目标选择器 + 单条 per-target 结算管线**,模式变成 `EffectDef.Pattern` 的四个取值:`Single / All / Splash / Multi` |
| 溅射 | 无。详表里 爆 的备注写着「全体低倍表达『溅射』」—— 是缺机制时的代偿 | 主目标满额 + 左右最近存活各 50%,代偿退场 |
| 多重射击 | 无。`HitCount`(剁 = 2)只能对**同一个**目标连打 | `Pattern.Multi` 复用 `HitCount` 作为**发数**,从主目标起轮转分给不同目标 |
| 治疗目标 | `HealSelf` 硬编码治玩家、`HealAll` 治玩家+全召唤物,召唤物**永远不能被单点治疗** | 单体治疗/单体 HoT 带友方目标(玩家 = −1 / 召唤物下标),群疗不变 |

两件事的共同点:**都是"目标"这一层的扩展**。现在引擎里"目标"只有一个裸 `int targetIndex`(敌人下标),
攻击模式要它变成"一组敌人 + 各自的系数",治疗要它多出一个"友方轴"。所以两件事共用同一次接口调整,
一起做比分两次做便宜。

## 2. 攻击模式

### 2.1 模型选型

| 方案 | 做法 | 评价 |
|---|---|---|
| A | 新增 `EffectKind.DamageSplash` / `DamageMulti` | 最小改动,但 kind 组合爆炸:哪天要"溅射灼烧""多重破甲",就得再加 4 个 kind;`NeedsTarget` 白名单继续膨胀 |
| **B(推荐)** | `EffectDef` 加一个 `AttackPattern Pattern` 字段;引擎里加 `ResolveTargets(pattern, primaryIndex)` 返回 **(敌人下标, 系数)** 列表,伤害走**一条** per-target 管线 | 模式与效果类型正交;`DamageAll` 归一成 `DamageSingle + Pattern.All` 后,那两段重复循环合并成一段;`NeedsTarget` 从白名单改成"看 Pattern 是不是 All" |
| C | 完全数据驱动的 targeting DSL(表达式/脚本) | 过度设计,本项目的字表规模(178 字)撑不起 |

**推荐 B。** 迁移路径保证 chars.json **一行不用改**:`ConfigLoader` 解析时把 `"kind": "DamageAll"`
归一成 `DamageSingle + Pattern.All`(`EffectKind` 不进存档,所以这层归一没有兼容包袱)。
新字表可以写 `"kind": "DamageSingle", "pattern": "Splash"`,老写法继续有效。

```csharp
public enum AttackPattern
{
    Single,  // 单体:只打主目标(默认)
    All,     // 群体:全部存活敌人,各 100%
    Splash,  // 溅射:主目标 100%,左右最近的存活敌人各 SplashPercent%
    Multi,   // 多重:HitCount 发,从主目标起轮转分给不同的存活敌人
}
```

`EffectDef` 新增两个字段:`AttackPattern Pattern`(默认 `Single`)、`int SplashPercent`(默认 50)。
`HitCount` **不新增**,直接复用。

### 2.2 逐模式规则裁定

四种模式共用同一条 per-target 结算管线,因此下列规则对每个目标**各算各的**,不因模式改变:
生克(`WuxingResolver`)、护甲与破甲与穿透、暴击摇点、`DoubleVsBurning` 翻倍、斩杀的"打之前判血"、
分裂触发。这条是本方案的**核心不变量** —— 它保证「攻击模式」只影响"打谁、打几成",不影响"怎么算"。

#### ① 单体 Single
与现状完全一致(即 `HitCount` 段数照旧全部落在主目标身上)。

#### ② 群体 All
与现有 `DamageAll` 完全一致,含那条既有裁定:`aoeCount` 在循环前取快照,**分裂产生的新怪不吃同一发 AOE**。

#### ③ 溅射 Splash
- **"左右"= 敌人列表的下标序**,与 UI 那一排从左到右的绘制顺序一一对应(`BattleView.DrawEnemies` 按下标铺)。
- **尸体跳过**:向左/向右各取**最近的存活者**,而不是死板的 `index ± 1`。
  - 理由:敌人死后尸体仍留在排面上(`BattleView.cs:988`),若按下标硬取,战斗后半段溅射会莫名其妙地
    "溅到尸体上"变成纯单体,玩家无法从画面上预判 —— 那是最坏的一种不可读。
  - 代价:分裂克隆接在队尾,所以"原体与克隆"不相邻、不会互相溅射。可接受(视觉上它们本来就分开画)。
- **系数**:主 100%,左右各 `SplashPercent`(默认 50)。侧翼系数作用在**基础值**上,乘在生克/暴击之前。
- **结算顺序**:主 → 左 → 右。事件按此顺序发,表现层据此做"中心炸开、两侧后跟"的节奏。
- **只有两侧**:即使左边有 3 只,也只溅最近那 1 只。要"溅一片"请用 All。
- **与 HitCount 的关系**:`HitCount = 2 + Splash` = **每一段都完整溅射一次**(2 段 × 3 目标 = 6 次结算)。
- **主目标中途死亡**:溅射照发 —— 侧翼那两下不是"传导",是同一次爆开。
- **斩杀**:三个目标各自判"打之前判血"(与 AOE 同口径)。

#### ④ 多重 Multi
- **发数 = `HitCount`**(复用既有字段,`剁` 那套多段逻辑就是它)。
- **分配 = 从主目标起、按下标轮转到存活敌人**,不足则**回卷**:
  - 3 只敌人 + 3 发 → 每只 1 发;
  - 3 只 + 4 发 → 主目标吃 2 发;
  - **1 只(Boss 单挑)+ 3 发 → 全部落在它身上**,等价于现有的多段单体。
    这条是刻意的:多重射击在单目标场不该"打空",否则玩家在 Boss 战会觉得抽到了废牌。
- **不摇随机数**:分配是确定性的轮转。理由与 `chars.json` 里已有的"暴击摇点排在守卫之后"同一条 ——
  「这一发消耗几个随机数」不该取决于场面,否则复现与调试变噩梦(见 `BattleEngine.cs:1330` 的注释)。
- **中途死亡**:轮转时跳过已死者继续找下一个存活者;**全场清空则剩余发数作废**。
- **每发独立减一次护甲** —— 与 AOE 同口径。这对带甲怪是实打实的惩罚,是定价里要补偿的那一项(见 2.3)。

### 2.3 数值折算(锚点表扩两行)

以同档「单攻」锚点 A 为 1.0(A 见详表:红 600 / 橙 480 / 金 400 / 紫 200 / 蓝 130 / 绿 90 / 白 60)。

| 模式 | 每目标系数 | 期望命中数 | 期望总量 | 说明 |
|---|---|---|---|---|
| 单体 | **1.00 A** | 1 | 1.00 A | 基准;能吃满"相克即破甲" |
| 群体 | **0.50 A** | 1~6 | 0.5~3.0 A | 现行锚点,不动 |
| **溅射** | 主 **0.70 A** / 侧 **0.35 A** | 1~3 | 0.70~1.40 A | 半个 AOE:比单体强、比群体弱,且**打不动带甲群**(逐目标各减一次甲) |
| **多重** | M=2 → **0.55 A**/发<br>M=3 → **0.40 A**/发<br>M=4 → **0.32 A**/发 | M | 1.10 / 1.20 / 1.28 A | 系数略高于"总量 = 1.0 A"的平价,用以补偿"每发各减一次护甲";在无甲杂兵场是它的主场,在 60 甲的「山」面前是废牌 |

三条要守住的比例关系:

1. **对单个带甲目标**:单体 > 溅射 > 多重(护甲惩罚随命中次数放大);
2. **对无甲杂兵群**:群体 > 多重 > 溅射 > 单体;
3. **对 Boss 单挑**:单体 ≈ 多重(回卷后总量 1.1~1.3 A,略高,是它在单目标场的"不废牌"补贴)> 溅射 0.7 A > 群体 0.5 A。

> 这三条是**新的战术分工**,与详表既有的「AOE 清杂兵、单体破装甲」同构,只是把中间那段填满了。
> 所有具体数字标注**待实测**,首版按上表填,进游戏后按第 18 章 R6 的口径迭代。

### 2.4 字表落地(第一批建议,待裁定)

只动 4 张,先验证机制与手感,不做全表重排(全表重排应当是独立的一批,走"用户逐条裁定"的老流程)。

| 字 | 属性/档 | 现状 | 建议改为 | 理由 |
|---|---|---|---|---|
| **爆** | 火 · 🔵蓝 | `DamageAll 50` + `BurnAll 1` | `DamageSingle 90 (Splash 50%)` + `BurnSingle 1` | 详表原文:「全体低倍表达『溅射』」—— **代偿字,机制到位就该复原**。主 90 / 侧 45,总量 0.7~1.4 A(A=130) |
| **镰** | 金 · 🟢绿 | `DamageSingle 65` | `DamageSingle 63 (Splash 50%)` + `Morale 1` | 镰刀横扫左右,语义天成;金系补一张 AOE 与单体之间的过渡牌(A=90 × 0.70) |
| **剿** | 金 · 🟢绿 | `DamageAll 35` + `Morale 1` | `DamageSingle 50 (Multi ×2)` + `Morale 1` | 「分头剿灭」= 多重;绿档 A=90 × 0.55 |
| **锬** | 金 · 🟡金 | `DamageAll 180` + `Morale 1` | `DamageSingle 160 (Multi ×3)` + `Morale 1` | 锬为长矛,连刺三点;金档 A=400 × 0.40 |

保持不动:炸(单点爆破,语义就是集中)、崩/涛/海/洪(水土两系仅存的纯 AOE,动了就没 AOE 了)、
燚/燊/焚/焱(火系 AOE 主链,是燎原流的骨架)。

### 2.5 范围外(但要留门)

- **敌人侧的攻击模式**(Boss 溅射到玩家 + 召唤物、杂兵多重):`ResolveTargets` 的对偶实现,本次不做,
  但目标选择器的签名要写成"哪一侧"可换的形状,免得日后推倒重来。
- **溅射灼烧 / 多重破甲**等"非伤害效果也吃 Pattern":字段就位后是几行的事,但首批不配,免得同时验证太多变量。

## 3. 治疗目标可选

### 3.1 目标模型

引入**友方目标**这一轴,与既有的敌方 `targetIndex` 并列:

```
allyIndex:  −1 = 玩家(默认)   0..n = 召唤物下标
```

选 `−1 = 玩家` 而不是新造一个枚举,是为了与全代码库既有的约定对齐 ——
`BattleEvent.TargetIndex` 里 `−1` 一直就是"玩家侧"(`BattleEngine.cs:186`)。

### 3.2 接口扩展

```csharp
public BattleError Cast(string charId, int targetIndex = -1, bool replaceSummon = false,
    bool attackMode = false, int libraryIndex = -1, int allyIndex = -1)   // ← 新增,默认玩家
```

新参数加在**最后且有默认值** → 现存全部调用点与 1072 条测试**一行不改**、语义不变(默认治玩家)。

配套:
- `NeedsTarget(def, attackMode)` 保持"要不要选敌人"的语义;
- 新增 `NeedsAllyTarget(def, attackMode)` —— "要不要选友军"。它的实现**不再是手写白名单**
  (2026-08-06 那次越界崩溃的教训),而是问效果自己:`effect.HealsSingleAlly`。

### 3.3 受影响的效果

| 效果 | 现状 | 方案 |
|---|---|---|
| `HealSelf` | 硬编码玩家 | **改名 `Heal`**,按 `allyIndex` 落点(枚举不进存档,改名零成本) |
| `HealOverTime`(`targetAll = false`) | 挂 `_playerStatuses` | 按 `allyIndex` 挂到玩家或**召唤物的状态袋**(见 3.4) |
| `HealAll` / `HealOverTime(targetAll)` | 玩家 + 全召唤物 | **不变**(群疗本就无需选) |
| 召唤物光环治疗(桃,`Passive.HealAlly`) | 走 `HealPlayerAndSummons` | **不变** |
| `Shield` / `Cleanse` / `Immunity` | 只作用于玩家 | **本次不动**,但同一条 `allyIndex` 管线可直接复用(3.9 列为后续) |

### 3.4 关键依赖:召唤物状态容器

单体 HoT 要能挂在召唤物身上,`SummonState` 就必须有状态袋。这正是 `BattleEngine.cs:1028`
那条注释预留的口子:

- `SummonState` 加 `StatusBag Statuses`;
- 结算点放在 `ActSummonTurn` 里,**顺序 = 先结算 HoT → 再出手 → 最后自身状态递减**
  ——与敌人侧 `ActEnemyTurn` 的"结算在前、递减在后"同向(2026-08-16 那次时序统一的口径,别再造反向);
- 存档:`SummonSnapshot` 加 `Statuses`,与玩家侧同一套序列化;老存档缺该字段 → 反序列化成空袋,
  语义等价于"身上没状态",**不需要存档版本号变更**;
- 召唤物死亡即清袋(顶替进来的新召唤物不继承前任的 HoT)。

> ⚠ 这是本方案里**唯一一处真正的架构增量**,也是工作量与风险的大头(存档面 + 时序面)。
> 若要砍范围,可先只做即时治疗(`Heal`)、把单体 HoT 上召唤物留到下一批 —— 但那样 沐 就得
> 继续只治玩家,"所有治疗都可选目标"这条就不完整。**建议不砍**。

### 3.5 其余裁定

- **上限与溢出**:治召唤物钳到 `summon.MaxHp`,溢出丢弃、不转给玩家。
- **死者不可治**:目标召唤物已死 → 该条治疗**落空但不报错**(字照常消耗)。想救回来走 `Revive`(活)。
  UI 侧压根不给死者做选中态,正常玩不到这条;它只是引擎的防御性口径。
- **五行**:治疗量仍是 `ResolveEffect(value, 配方元素, 施术者元素)`,**与目标属性无关** ——
  不因为"水生木、治木召唤物 ×3"而改。理由:wuxing-reference 是唯一来源,本方案不碰它;
  真要做"对友方也吃生克"是一次独立的规则变更,得先改规格文档与 `WuxingResolverTests`。
- **目标下标失效**:出字瞬间到结算之间下标不会变(同一次 `Cast` 内),但"召唤满员顶替"会重排槽位 ——
  裁定:**先治疗后召唤**不成立(效果按 chars.json 顺序执行),所以若同一张字既召唤又治疗,
  治疗的 `allyIndex` 指的是**出字瞬间**的那只;被顶替掉了就落空(同 3.5 死者条)。首批字表里无此组合。

### 3.6 事件与表现

- `Heal` 事件:`TargetIndex = −1` 保持"玩家侧"语义,**新用 `SecondIndex` 标召唤物下标**(玩家为 −1),
  与 `SummonHit` / `Summon` 的既有用法一致(`BattleEngine.cs:188`)。
- `Juice` 飘绿字的锚点:玩家 → 玩家血条;召唤物 → `SummonAnchor(index)`(该回调已存在,`BattleView.cs:135`)。
- 召唤物血条的动画快照(`_summonAnimHp`)已按下标记账,治疗回血逐记**升**即可,与 `SummonHit` 逐记降对称。

### 3.7 UI 交互(重点)

因为 5/7 治疗字是"治疗 + 伤害"复合,交互必须一次说清两个目标:

1. 点字 → 进入**选择态**。顶部提示:`「澡」:①点敌人 ②点治疗目标`。
2. **敌方目标**:同现状(单敌免选,`AliveEnemyCount() > 1` 才要求点)。
3. **友方目标**:进入选择态时,引擎给出**默认建议 = 当前血量百分比最低的己方单位(含玩家)**,
   UI 高亮它。玩家可以点玩家头像/任一召唤物改选;**不改就直接出字** —— 即多数情况下
   一次点击都不多花。
4. **无存活召唤物** → 完全不进友方选择(默认玩家),提示语也不出现。
5. **攻击模式(把字拖到敌人身上)**:敌方目标由拖放给定,友方目标一律取默认建议 —— 拖放的卖点是快,
   不该在半路弹选择。

> 默认建议由 Core 提供(`SuggestHealTarget()`),不要在 Presentation 里现算 ——
> 那是规则,规则归 Core(架构硬规则:Presentation 只读 Core)。

## 4. 存档与兼容

| 面 | 影响 |
|---|---|
